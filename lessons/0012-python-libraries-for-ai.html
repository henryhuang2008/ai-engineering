Python Libraries Every AI Engineer Should Know

An AI application is not one framework. It is a stack of small contracts: data comes in, gets validated, is stored, is sent to a model, is traced, and is tested. The entries below cover that stack; the second half of this lesson adds the packages the usual list misses — agents, MCP, evals, local embeddings, and the plumbing that keeps flaky APIs from taking your service down.

Your win this lesson You'll leave with a layer-by-layer map: what each library is for, the shortest useful way to use it, and the moment it earns its place. You'll also get a gap table of 16 entries the usual library list omits — the packages a complete stack needs, from agents and MCP to evals and local embeddings.

Part 1 — Contracts and configuration

Pydantic

What: runtime validation built from type hints. A BaseModel declares the shape; invalid data raises before it reaches your logic. In AI work this is the boundary between messy model output and the rest of your program.

from pydantic import BaseModel, Field

class Ticket(BaseModel):
    order_id: str
    urgency: int = Field(ge=1, le=5)

ticket = Ticket.model_validate_json(llm_output)

Use when: any untrusted data enters — an HTTP body, an LLM's JSON, a config file. Don't use it as a dataframe replacement or for per-row validation of a million rows; that is pandas or a database constraint.

pydantic-settings

What: Pydantic's BaseSettings moved into its own package in Pydantic v2. It reads environment variables (and .env) into a typed settings object, so a missing key fails at startup instead of at the first request.

from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env")
    deepseek_api_key: str
    database_url: str

settings = Settings()   # raises if a required value is missing

Use when: the app has more than two settings, or a wrong value should stop the process. Don't use it for per-request values; settings are process-level.

python-dotenv

What: loads KEY=VALUE pairs from a local .env file into the environment. It is a convenience for development, not a secret manager.

from dotenv import load_dotenv
load_dotenv()   # existing environment variables win

Use when: local development with API keys you must not commit. Don't use it as production security: deployed services should get secrets from the platform's secret store. pydantic-settings can read .env itself, so you often need only one of the two in a service.

Part 2 — Service and background work

FastAPI (+ Uvicorn)

What: an HTTP framework whose request and response models are Pydantic, which gives you validation, serialization, and OpenAPI docs for free. Uvicorn is the ASGI server that actually runs it.

from fastapi import FastAPI

app = FastAPI()

@app.post("/tickets")
def create_ticket(ticket: Ticket) -> Ticket:
    return ticket

Use when: the product needs an HTTP API, especially one that streams or calls models asynchronously. Don't use it to hide slow work inside a request; a 40-second chain belongs in a queue (next entry).

Celery

What: a task queue. Your endpoint writes a job and returns; worker processes pick the job up, retry it, and scale independently. It needs a broker (Redis or RabbitMQ) and usually a result backend.

@celery.task(bind=True, max_retries=3)
def run_agent(self, ticket_id: str) -> None:
    ...   # multiple model calls, tools, writes

Use when: work outlives the request, can take seconds to minutes, or must survive a deploy. Don't use it for a 200 ms task; FastAPI's BackgroundTasks is enough, and Celery adds an operational component.

Part 3 — Data

psycopg (PostgreSQL)

What: the modern PostgreSQL driver for Python (psycopg 3). It gives you direct SQL, transactions, and access to Postgres-only features such as COPY and pgvector.

import psycopg

with psycopg.connect(dsn) as conn:
    conn.execute("INSERT INTO tickets (id, body) VALUES (%s, %s)", (tid, body))

Use when: you want SQL you can read, bulk operations, or an extension the ORM does not model well. Don't use it to hand-roll every query when an ORM would keep the schema coherent.

pymongo (MongoDB)

What: the official MongoDB driver. Documents map naturally to event payloads and model outputs whose shape changes.

collection.insert_one({"ticket_id": tid, "route": "billing", "raw": payload})

Use when: the data is document-shaped and the schema is still moving. Don't use it when you need joins, strong relational constraints, or multi-row transactions as the default path.

SQLAlchemy

What: Python's standard SQL toolkit and ORM. Models are classes; sessions manage transactions; the same code can target Postgres, SQLite, or MySQL.

class Ticket(Base):
    __tablename__ = "tickets"
    id: Mapped[str] = mapped_column(primary_key=True)
    body: Mapped[str]

session.add(Ticket(id=tid, body=body))
session.commit()

Use when: the app has real relational models and more than one developer. Don't use it to hide a query you do not understand; text() and raw SQL are legitimate escape hatches.

Alembic

What: migration control for SQLAlchemy schemas. You generate a revision from model changes, review it, and apply it — in order, in every environment.

alembic revision --autogenerate -m "add ticket route"
alembic upgrade head

Use when: the schema changes after the first deploy. Don't use it as a substitute for backups, and always review autogenerated migrations before production.

pandas

What: tabular data in memory. For AI engineering its daily use is evaluation sets, CSV/JSONL inspection, and joining model outputs with labels.

df = pd.read_json("evals.jsonl", lines=True)
df.groupby("route")["passed"].mean()

Use when: exploring a dataset or computing a metric over many rows. Don't use it in the request path for a single record, and don't treat it as a database.

Part 4 — Model access

Provider SDKs: OpenAI, Anthropic, Google, Ollama

What: the official clients. They expose the parts the quickstart hides: tool calling, structured output, vision, image generation, caching, and streaming. Ollama runs open models locally behind a similar chat interface.

from openai import OpenAI

client = OpenAI()
reply = client.chat.completions.create(
    model="...", messages=[{"role": "user", "content": "..."}]
)

Use when: you need a provider-specific capability, or you are learning what the frameworks abstract. Don't learn four SDKs on day one; go deep on one, then compare. Read the API reference beyond the first page — that is where tools and structured output live.

Instructor

What: structured output on top of provider clients. You pass a Pydantic model as response_model; Instructor validates the result and can retry when the model returns something malformed. It is model-agnostic.

from instructor import from_openai

client = from_openai(OpenAI())
ticket = client.chat.completions.create(
    model="...", response_model=Ticket, messages=[...]
)

Use when: several providers must return the same typed object, or you want validation-driven retries. Don't use it if your provider's native structured output already meets the contract; one less dependency is a feature.

Part 5 — Orchestration

LangChain

What: a toolkit of model, message, tool, and retriever abstractions with integrations for most providers and stores. Modern LangChain sits on top of LangGraph and uses create_agent for the agent harness.

from langchain_deepseek import ChatDeepSeek

model = ChatDeepSeek(model="deepseek-flash", temperature=0)

Use when: you want provider-neutral messages/tools and ready-made integrations, or your team already uses it. Don't use it before you understand the raw loop; abstractions are harder to debug when you cannot see the call underneath. This course uses it after lessons 2–3 for exactly that reason.

LlamaIndex

What: a data framework for RAG: readers, node parsers, indexes, retrievers, query engines, and response synthesizers.

index = VectorStoreIndex.from_documents(documents)
engine = index.as_query_engine()
answer = engine.query("What is the refund window?")

Use when: the project is document-heavy and you want its ingestion/query pipeline out of the box. Don't use it for a single query over one table; a direct store call is clearer.

Part 6 — Vector databases

What: stores for embeddings plus similarity search, usually with metadata filters. The RAG pipeline writes chunks and reads the nearest ones.

storeshapechoose it when
Pineconemanaged, serverlessyou want no index operations and can pay for managed service
Weaviateself-host or cloud, hybrid searchyou need hybrid/BM25 + vector in one engine and a schema
QdrantRust service, rich filtersfiltered search and self-hosting are first-class requirements
pgvectorPostgres extensionyou already run Postgres and want one database, not two
 
-- pgvector: one extension, one table
CREATE EXTENSION IF NOT EXISTS vector;
SELECT id FROM chunks ORDER BY embedding <=> %s LIMIT 6;

Use when: retrieval needs a dedicated index (scale, filters, hybrid search). Don't add one before measuring: pgvector or an embedded store often carries a small corpus, and a second database is a second backup/ops surface.

Part 7 — Observability

Langfuse and LangSmith

What: tracing for LLM applications. Every generation becomes a span with prompt, response, model, latency, token counts, and cost; you can attach user/session metadata and inspect a bad run end to end. Langfuse is open source and self-hostable; LangSmith is the LangChain-native platform.

# Langfuse (decorator style)
from langfuse import observe

@observe()
def answer(question: str) -> str:
    ...

Use when: any model call reaches a real user. Don't log raw prompts and responses containing PII or secrets without a policy; redact at the SDK boundary. Pick one — two tracers double the work.

Part 8 — Prompt optimization

DSPy

What: "programming, not prompting." You declare signatures and modules, provide a metric and examples, and an optimizer searches for better prompts or weights instead of you hand-tuning strings.

class Answer(dspy.Signature):
    question: str = dspy.InputField()
    answer: str = dspy.OutputField()

program = dspy.ChainOfThought(Answer)
optimized = dspy.BootstrapFewShot(metric=metric).compile(program, trainset=examples)

Use when: you already have a metric and a dataset, and prompt tuning has become the bottleneck. Don't use it on day one; without evals, the optimizer has nothing to optimize against.

Part 9 — Documents

PyMuPDF and pypdf

What: PDF text extraction. PyMuPDF (fitz) is fast and exposes layout blocks; pypdf is pure Python and simple. Both are local libraries.

import fitz
doc = fitz.open("policy.pdf")
text = "\n".join(page.get_text() for page in doc)

Use when: the PDFs are born-digital and you need text fast. Don't expect either to reconstruct complex tables or scanned pages; benchmark both on your documents.

Amazon Textract and Azure Document Intelligence

What: managed OCR/document services that return text, tables, forms, and layout for scans and messy documents. You call them through their SDKs/APIs and pay per page.

import boto3
textract = boto3.client("textract")
result = textract.detect_document_text(Document={"Bytes": pdf_bytes})

Use when: the documents are scanned, table-heavy, or the local parsers lose structure that matters. Don't reach for them before trying a local parser; managed OCR adds latency, cost, and a data-residency question.

Part 10 — Prompt templates

Jinja2

What: a mature templating engine. Prompts become templates with variables, conditionals, loops, and filters instead of a pile of f-strings.

from jinja2 import Environment

template = Environment().from_string(
    "Answer {{ customer }} using these facts:\n{% for f in facts %}- {{ f }}\n{% endfor %}"
)
prompt = template.render(customer="Dana", facts=facts)

Use when: prompts are reused, versioned, or assembled from context. Don't render templates from untrusted input — Jinja2 is powerful enough to be an injection surface; keep templates in your repo.

Part 11 — What the usual list misses

The entries above are a strong backend stack. They are weaker on the parts that define AI engineering in 2026: stateful agents, a standard tool protocol, evaluation, local embeddings, and the small plumbing that keeps provider calls alive. These are the gaps a production stack needs — several are used in this course.

Tooling, not libraries: uv (one lockfile, one environment per project), ruff (lint and format), and mypy (types) are not AI packages, but they are the difference between a demo and a repository someone else can run. This course uses uv for every lab.

On the radar, not on the list: Playwright or trafilatura for web extraction when an agent must read pages; Guardrails or LLM Guard for input/output policy; OpenTelemetry if your tracing must cross service boundaries; Pydantic AI, the Microsoft Agent Framework, and vendor agent SDKs when a job specifically demands them. Learn them against a project, not as collectibles.

The honest rule: every dependency is a liability you operate. Add a library when a measured problem demands it, not because a stack list has a slot for it. The entries above are a vocabulary; your project decides which sentences to use.
