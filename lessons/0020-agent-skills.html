Agent Skills: Run the Example

This lesson walks through the example in assets/examples/0020-agent-skills-python. You run five commands, see what each one prints, follow one question through the agent, and then write down the rules that keep your own skill working.

Your win this lesson You can run the example end to end without a key for four of the five steps, read a SKILL.md and know what each part is for, and recognize the four failures that break a skill when you write one.

Part 1 — What is in the folder

Two skills and a small Python agent:

skills/
├── csv-insights/
│   ├── SKILL.md              # the instructions
│   ├── references/metrics.md # definitions, read only when needed
│   └── scripts/profile.py    # code, run only when needed
└── release-notes/
    ├── SKILL.md
    ├── references/style.md
    └── scripts/lint_notes.py

app/       # catalog, linter, agent
data/sales.csv
tests/

A skill is a folder whose top level holds SKILL.md. The file opens with two fields:

---
name: csv-insights
description: Profile a CSV file and answer questions about its columns,
  types, missing values and numeric spread. Use when the user points at
  a .csv file and asks what is in it.
---

# CSV insights

1. Read `references/metrics.md` before answering.
2. Run `scripts/profile.py` on the user's file.
3. Never report a mean without the row count and the missing count.

Two rules for those fields: name must equal the folder name, and description must say when to use the skill, not only what it does. The body is a short numbered procedure; the detail lives in references/ and the code in scripts/.

Part 2 — Run it

From the repository root:

cd assets/examples/0020-agent-skills-python
uv sync

# Windows PowerShell
Copy-Item .env.example .env

# macOS / Linux
cp .env.example .env

Put your DeepSeek key in OPENAI_API_KEY inside .env. Only the ask command needs it.

Step 1 — list the catalog (no key)

uv run python main.py catalog
always-on catalog: ~128 tokens, 2 skills

csv-insights  (41 body lines, ~334 tokens on load)
  Profile a CSV file and answer questions about its columns...
release-notes  (42 body lines, ~409 tokens on load)
  Turn a list of merged changes into release notes...

Two lines. That is what every request carries before a skill is used.

Step 2 — ask a question (needs a key)

uv run python main.py ask "Using data/sales.csv, how many rows are there and what is the mean amount?"
Rows: 10
Mean amount: 236.1377777777778
Missing: 1  (the mean is over 9 values, not 10 rows)

The agent also repeats a warning that the spread is wide, because references/metrics.md tells it to.

Step 3 — run a skill script yourself (no key)

uv run python main.py run-script csv-insights profile.py --set csv=/absolute/path/to/data/sales.csv

This prints the same JSON the agent gets, with "rows": 10 and one entry per column. Use an absolute path: the script runs with its working directory inside skills/csv-insights/scripts/.

Step 4 — lint the library (no key)

uv run python main.py lint
0 blocking, 0 warnings

The linter checks the format: name versus folder, description size, body size, dead links, stale model ids. fixtures/broken-library/ is the failing example the tests use.

Step 5 — run the tests (no key)

uv run pytest -q
34 passed

Part 3 — Follow one question

When you run ask, the agent does five things. The output shows the tool calls as they happen.

  1. Reads the catalog. Two entries, no bodies.
  2. Calls load_capability('csv-insights'). The skill body enters the next request. ${SKILL_DIR} is replaced with the real folder, so the script path works from any directory.
  3. Calls read_skill_resource(...) for references/metrics.md. That file is where the rules live: quote the row count, quote the missing count, warn when the spread is wide.
  4. Calls run_skill_script(...) for profile.py. The script returns JSON with rows and a columns list.
  5. Answers. It quotes the numbers exactly and adds the warning the reference asked for.

Three tools serve both skills: load_capability, read_skill_resource, run_skill_script. If the model tries to read a file before loading the skill, the call is refused with a message telling it to load first, and it can correct itself.

The second skill works the same way. Ask it to turn three commits into release notes and it drops the internal chore line, keeps Added and Fixed, and runs lint_notes.py on its draft before returning it.

Part 4 — Write your own skill

Six rules, all visible in the two skills above:

  1. name equals the folder name. Lowercase letters, digits and single hyphens. The name is used as a tool argument, so two names for one skill means a broken call.
  2. The description says when to use it. It is the only text the model reads before deciding. Write “Use when the user …”, not a feature list.
  3. The body is a page, not a manual. Numbered steps, under 500 lines. Long explanations go in references/; long code goes in scripts/.
  4. Scripts take named flags. The runtime passes {"csv": "/path/file.csv"} as --csv /path/file.csv. There are no positional arguments.
  5. Scripts get absolute paths. The working directory is the script's own folder, not the project root.
  6. The workflow fits the tools the agent has. If a step says “write the draft to a file”, the agent needs a file-write tool. This example's agent has none.

Rule 6 is not hypothetical. The release-notes skill first told the model to save a draft and then lint the file. The live run refused to pretend:

I can't complete the "write it to a temp file" step: my available tools are
`load_capability`, `read_skill_resource`, and `run_skill_script`. None of them
can create a file.

The fix was in the skill: lint_notes.py gained a --text mode, and the instructions pass the draft inline. The agent gained no new tool.

Part 6 — What was verified

  • Live runs. Both skills were exercised with DeepSeek deepseek-chat: the CSV answer returned 10 rows and mean 236.1377777777778, and the release-notes answer ended with an empty problem list from the checker.
  • Offline. 34 tests pass with no network, no database and no key. lint is clean on the real library and fails on the fixture.
  • Not verified. The current harness on Windows cannot construct, so the pin is a workaround rather than a fix. Sandboxed script execution, Git/S3 registries, and any measure of “did the model pick the right skill” are not exercised.

Two repositories supply the material: langchain-ai/langchain-skills for the authoring rules and lint gates, and DougTrajano/pydantic-ai-skills for the runtime. The rule-by-rule table is in lint rules; the platform notes are in runtime notes.

What's next

This is the last lesson. You started with one API call; you end with a library the agent can carry: a folder per procedure, a description that says when to use it, and files that load only when a task gets there. If you write one skill of your own, copy csv-insights/SKILL.md, run lint, then run ask and read the tool calls. The skill map compresses the course into one page, the example page is the runbook, and lesson 1 is the way back to the start.

One rule to keep: a skill's steps must fit the tools the agent has. Write the workflow after you know the tool list, not before.
