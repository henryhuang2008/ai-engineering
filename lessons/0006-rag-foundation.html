RAG: The Pipeline, End to End

A RAG system is not "put documents in a prompt." It is eight stages, each with an input, an output, and a way to be wrong. This lesson is the map: the whole pipeline on one chart, the decision that matters at every stage, and the numbers to start with. There is no lab here — lesson 7 builds the whole chart, and later lessons take parts of it further.

Your win this lesson You'll be able to draw the pipeline from memory, say what each stage costs and where it breaks, and name the first stage to inspect when an answer is wrong — instead of rewriting the prompt and hoping.

Why RAG, and why not fine-tuning

A model's weights freeze at a training cutoff: your policies, your prices, this week's incident report were never in them. There are two ways to close that gap. Fine-tuning retrains the weights on your data — slow, expensive, and stale the moment the document changes. Retrieval-augmented generation fetches the relevant text at question time and puts it in the prompt — no training, updates by editing a file, and every claim can point at a source.

For facts that change or stay private, RAG wins decisively. Fine-tuning is for style and behaviour, and it is the last lever you pull, after context and retrieval have failed. The rest of this lesson is the retrieval half done properly. [Anthropic — Contextual Retrieval]

The workflow

Read the chart as two lanes, not eight boxes. Index once — parse, chunk, embed, store — runs when documents change and is allowed to take minutes. Answer every query — prepare, retrieve, rerank, generate — runs per question and must fit in a couple of seconds. Almost every RAG failure is one lane blamed for the other's problem.

The handoff between the lanes is deliberately boring: a chunk id plus metadata (source file, page, section, document hash). It is what makes citation checking possible later — the model never invents a source that is not in the retrieved set, because you verify it after generation.

The eight stages

1. Parse: documents to structured Markdown

Docling turns PDF, DOCX, PPTX, HTML and images into a structured document: blocks in reading order, heading hierarchy, tables as tables, figures with captions. Export to Markdown when you want to read it, JSON when you need page and section anchors. OCR is a switch, and scanned PDFs need it on. This stage is where most "the retrieval is bad" stories actually begin: a two-column PDF read left-to-right produces plausible, useless text.

Output structured Markdown/JSON with anchors. Breaks when OCR is off, reading order is guessed, or a table is flattened into a paragraph.

2. Chunk: structure first, token budget second

Docling's HybridChunker walks the document hierarchy, merges small items until the token budget, starts a new chunk at a heading boundary, and does not split a table across chunks. It can prepend the heading path to each chunk, so "the refund window is 48 hours" still carries Billing → Refunds when retrieved alone. Start at 400–600 tokens.

Fixed windows with overlap are the baseline you compare against: 400–600 tokens, 10–15% overlap. Simpler and tool-agnostic, but they cut mid-sentence and mid-table. HybridChunker does not need overlap the way sliding windows do, because it is not sliding — it is following the document.

Output chunk records with id, text, heading path, source. Breaks when chunks are too small to hold an answer or too large to stay specific, or when a table is cut in half.

3. Embed and index: two representations, one corpus

Each chunk gets two representations. A dense embedding captures meaning, so "money back" finds "refund". A lexical index — BM25 — captures exact tokens, so "E-204", "Sky Pro" or an invoice number are findable at all. Neither is optional in a real corpus: dense misses identifiers, lexical misses paraphrase.

In this course the embedder is Qwen text-embedding-v4 on Alibaba's DashScope: 1024 dimensions by default, 8,192 tokens per input, 100+ languages, strong on Chinese. DeepSeek has no embeddings endpoint — it is a chat model only — so generation and embedding come from two different vendors here. That is normal, and worth internalising early: nothing in RAG requires them to match, and swapping either one is an independent decision. Record the model name and dimension in the table's metadata; vectors from two models are not comparable, so a mixed table returns confident nonsense and nothing in the stack warns you.

The same model also distinguishes a document from a query at embed time (DashScope's text_type). Use it — it is the cheapest accuracy win in the pipeline, and it belongs to stage 5.

Output vectors plus a BM25 index over the same chunk text. Breaks when the embedding model changes without a re-index, or when the two indexes are built from different text.

4. Store: one table, two indexes

LanceDB keeps the whole corpus in one table: each row is a chunk — id, text, metadata, vector. Two indexes sit on that one table: a vector index for the dense side, and a BM25 full-text index on the text column, created with create_fts_index. That is the reason to pick it here. Chroma is a vector store, not a BM25 engine — its document filtering is substring matching, not ranked retrieval — so with Chroma you keep a lexical index beside it (BM25S, rank_bm25, SQLite FTS5) and join the two yourself. LanceDB removes that seam, and one metadata filter applies to both halves of a hybrid query.

The full-text analyser is configured when the index is built — language, stemming, stopword removal, ASCII folding. That choice is frozen into the index, which is exactly why the query side has its own stage (5).

Index incrementally: hash each document, re-embed only what changed, delete rows whose ids no longer exist. Re-embedding the corpus on every deploy is the most common way a RAG service quietly becomes expensive.

Output a persistent table plus document hashes. Breaks when documents are edited and old rows stay, when a re-index silently changes the embedding model, or when the full-text index is rebuilt with different analyser settings than the query side assumes.

5. Prepare the query: one question, two representations

Users do not type keywords. They type "my card got charged twice this month, can you sort it out?" — a sentence with pronouns, politeness and intent, and no overlap with the words your index was built from. Both retrievers need a representation of that sentence, and they need different ones:

  • Dense: embed the whole question with the exact model used at index time — same model, same normalisation, same instruction prefix if the model has one. Qwen text-embedding-v4 exposes that asymmetry directly as text_type="query" versus text_type="document". A different embedding model puts the query in a different vector space, and every result becomes noise.
  • BM25: run the same analyser the index was built with — lowercase, tokenise, strip punctuation, drop stopwords, stem — and keep the tokens that carry identity: numbers, error codes, product names, invoice ids. In LanceDB those settings live on create_fts_index, so the query must use the same language, stemming and stopword configuration; otherwise a term that is in the corpus is scored as absent.

The mismatch is the point: BM25 has no idea that "charged twice" and "duplicate charge" are the same complaint, and the embedding has no idea that "E-204" must match character for character. Preparing the query differently for each retriever is what lets the two disagree usefully. Cheap query shaping also belongs here — expand an abbreviation, strip "please", or rewrite a follow-up into a standalone question in a production system — but do it before retrieval, never after.

Output one query vector plus one analysed term list. Breaks when the query is embedded with a different model than the index, or the BM25 analyser disagrees with the one used at index time.

6. Retrieve: hybrid, then fuse by rank

Send both representations to the same table, take a generous candidate pool from each side (tens, not the final six), and apply the same filter to both. In LanceDB that is one hybrid query: query_type="hybrid" with the query vector and the query text, fused by reciprocal rank fusion — each candidate scores 1/(60 + rank) in each list, summed. RRF needs no score calibration and no weight tuning to start, which is why it is the default in most 2026 systems.

One naming trap: LanceDB calls the fusion step a reranker (RRFReranker). It fuses two ranked lists; it does not read the query and the chunk together. That is stage 7's job.

Return 30–50 candidates, not 5. The reranker can only reorder what retrieval handed it; a recall miss at this stage is unrecoverable later.

Output a fused candidate list. Breaks when a filter is applied to one half only, or when a single retriever is blamed for a corpus that needed the other.

7. Rerank: read the pair, not the vectors

A cross-encoder reads the query and each candidate together and scores relevance directly — more accurate than comparing two independently produced vectors, and far more expensive per pair. That is exactly why it runs on 50–80 candidates rather than the whole corpus, and returns the 5–8 that go into the prompt. LanceDB ships this too, as CrossEncoderReranker.

If answers are mediocre, check whether the right chunk was in the candidate set before touching the prompt. Rerank is the cheapest large quality gain in the pipeline — but skip it deliberately, not by accident.

Rerank is not an LLM feature. A cross-encoder is its own small model — Qwen3-Reranker, BGE-reranker-v2-m3, Cohere Rerank — deployed and billed separately from the chat model. DeepSeek offers neither embeddings nor reranking, so this course takes the reranker from DashScope with the same key as the embedder, or runs a local one. LanceDB's RRFReranker is not this: it is rank fusion with no model behind it, which is why hybrid search needs no extra provider at all.

If you skip it: keep the fused top 6–8 and accept that near-misses sit in the prompt. Cheaper substitutes are metadata boosts (recency, section priority), a score floor that drops weak candidates, or MMR when the top chunks are near-duplicates. Skipping is a reasonable first version — measure hit rate before and after (when you have an eval set), then decide whether 100–200 ms is worth paying for.

Output an ordered shortlist. Breaks when candidates are too few to matter, or rerank runs over hundreds of chunks and blows the latency budget.

8. Generate: evidence in, pydantic out

Compose the prompt from evidence: every chunk labelled with its id and source, an instruction to answer only from that evidence, cite ids, and say when the evidence is insufficient. Ask for a pydantic object — answer, citations, insufficient flag — through structured output, the same with_structured_output you used in lessons 2 and 5. In this course the generator is ChatDeepSeek, pinned at temperature=0 so two runs are comparable.

Then validate the object: every cited chunk id must exist in the retrieved set, and an answer that cites nothing while claiming enough context is reported rather than trusted. That check catches fabricated citations before a user does, and it is the difference between a demo and a product.

Output a typed answer with checkable citations. Breaks when the contract is prose-only, citations are free text, or "I don't know" is not an allowed answer.

The contract at the end

The pipeline is only as good as what it hands back. A typed answer is what makes the system checkable, loggable and safe to put behind a UI:

fieldtypewhy it exists
answerstringthe prose the user reads
citationslist of chunk id + sourcevalidated against the retrieved set; no free-text sources
insufficient_contextboolmakes "I don't know" a first-class answer instead of a failure
confidencefloat, optionalroutes low-confidence answers to a human queue
