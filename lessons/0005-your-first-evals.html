Your First Evals: No More Flying Blind

Right now, if you change a prompt and the output "looks fine," you ship it. That instinct is what separates demo builders from AI engineers — and why interviewers ask one question more than any other: "how would you know this got better?"

Your win this lesson You'll build a working eval harness — dataset, scorer, runner — then break it three ways and watch the score and the exit code react. From today, you can prove a change helped instead of hoping it did.

Why eyeballs don't scale

Software tests pass or fail deterministically; LLM outputs don't. Every change you'll make this course — new prompt, new model, smarter retrieval, extra tools — can quietly break what already worked. Checking by eye catches nothing, and users catch it for you. Evaluation-driven development replaces the instinct with evidence: run a fixed set of cases, score them mechanically, compare before/after. Chip Huyen's book makes evaluation the centerpiece of AI engineering for exactly this reason. [1]

Anatomy of an eval

Four parts, one comparison:

  1. Dataset — real cases with expected answers. Start with a dozen sharp, curated cases — this lab ships exactly 12; a dozen honest beats a thousand junk.
  2. Scorer — a function that judges each output.
  3. Runner — a script that loops cases → collects outputs → scores → prints a number.
  4. Gate — an exit code CI can act on: 0 above the threshold, 1 below it.

And the comparison: the score means nothing alone; it means everything against yesterday's score. That before-number is your baseline.

Scorer typeUse whenExample
Programmatic (exact match, JSON validity, schema check)A machine can verify the outputcategory == "billing"
LLM-as-a-judgeQuality has no single right answer"Is this reply grounded in the cited doc? Score 1–5."
Human spot-checkYou're calibrating the other twoReview 10 judge scores weekly

Build it: the lesson-2 schema returns

The system under test is your SupportTicket classifier from lesson 2 — same ChatDeepSeek handle, same pydantic schema, same with_structured_output. The dataset is a dataset.jsonl file, one JSON case per line:

dataset.jsonl (first 3 of 12)

{"ticket": "I was charged twice for my subscription this month.", "expected": "billing"}
{"ticket": "The app crashes every time I open the settings page.", "expected": "bug"}
{"ticket": "How do I export my data to CSV?", "expected": "question"}

The model call is deliberately boring: the same wiring lesson 2 taught. Pin the temperature, reuse one classifier for every case, and let the pydantic model — not string parsing — enforce the labels. Full file: eval.py.

eval.py — the model under test

model = ChatDeepSeek(
    model=os.getenv("DEEPSEEK_MODEL", "deepseek-flash"),
    temperature=0,                              # comparability: the run is not the noisy part
    extra_body={"thinking": {"type": "disabled"}},
)
classifier = model.with_structured_output(SupportTicket, method="function_calling")

def classify(classifier, ticket: str) -> str:
    result = classifier.invoke([
        SystemMessage(content=prompt()),        # CLASSIFIER_PROMPT wins when set
        HumanMessage(content=ticket),
    ])
    return result.category

The runner is a loop and a counter — no framework, because the harness is the point:

eval.py — the runner and the gate

def run(cases, classify_one):
    failures = []
    for case in cases:
        try:
            got = classify_one(case.ticket)
        except Exception as error:              # a failed call is a failed case, not a crash
            got = f"ERROR: {type(error).__name__}: {error}"
        if got != case.expected:
            failures.append((case, got))
    return Result(len(cases), len(cases) - len(failures), failures)

print(f"accuracy: {result.passed}/{result.total} = {result.accuracy:.0%}")
return 0 if gate(result.accuracy, args.threshold) else 1

Real output:

prompt: Classify the support ticket into billing, bug, or question.
accuracy: 12/12 = 100%
gate: 100% vs threshold 90% -> pass
Why temperature=0 and a fixed model Comparability is everything: if the run itself is noisy, the score difference means nothing. Pin temperature to 0, pin the model version, and only change one variable per experiment. When you later swap models, re-run the suite — that's not overhead, that's the point.
Hands-on loop (the whole lesson is this loop) 1. uv sync, then uv run python eval.py. Write the number down — that's your baseline.
2. Break the model: $env:DEEPSEEK_MODEL = "deepseek-retired", re-run. Every case becomes ERROR, accuracy 0%, exit code 1. Restore with Remove-Item Env:DEEPSEEK_MODEL.
3. Try the prompt experiment: $env:CLASSIFIER_PROMPT = "Answer question for every ticket.", re-run. It often stays at 100% — with function calling, the enum and the ticket text decide the label. A null result is a result: you just proved that edit was not the lever.
4. Break the labels: change one expected in dataset.jsonl, re-run, watch 11/12. A bad label and a model failure look identical until you read the case. Restore it.
5. Extend the dataset with 5 cases from real complaints you invent, then re-run. Good eval sets grow with the system.

Break it on purpose

A harness you have never seen fail is a harness you cannot trust. Three experiments, one variable each:

experimentcommandwhat actually happens
weak prompt$env:CLASSIFIER_PROMPT = "Answer question for every ticket."often 100% anyway — the enum and the ticket dominate, so the system prompt has less leverage than you expect
retired model$env:DEEPSEEK_MODEL = "deepseek-retired"0/12, every case ERROR: OpenAIInvalidRequestError, gate exits 1 — outages are regressions too
wrong labeledit one expected in dataset.jsonl11/12 — indistinguishable from a model failure until you read the case

Restore after each and confirm you are back at the baseline. That restore step is not ceremony: it proves the number moved because of the thing you changed.

When exact match can't score: LLM-as-a-judge

Classification has a right answer. Draft replies, summaries, tone — don't. For those, a model grades another model against a rubric: "Does the reply cite a source? Is it within 80 words? Rate 1–5." The same ChatDeepSeek handle works as the judge; pin it and its temperature just like the system under test. Cheap models judge fine; the catch is that judges drift too — validate yours against your own eyes occasionally. A reply-groundedness eval uses the same design.

The gate: evals in CI

Here's where your existing instincts pay again: an eval script is just a test suite with an exit code. eval.py --threshold 0.9 returns 0 at or above the line and 1 below it — no parsing, no scraping stdout:

uv run python eval.py --threshold 0.9
if ($LASTEXITCODE -ne 0) { throw "eval gate failed" }

Wire that into Jenkins, GitHub Actions, or a pre-push hook, and you've built an eval gate — a layer-6 skill the career-switchers without your background don't even know to mention. Prompts, retrieval changes, model upgrades all flow through it.

Your interview answer, rehearsed "How would you know this got better?" → "I'd have a fixed eval set with a baseline score, run it at temperature 0 on every change, and gate CI on a threshold — programmatic scoring where possible, LLM-as-a-judge for open-ended qualities, humans calibrating the judge." Twenty seconds, and you sound like you've shipped.
