Your First LLM Call: Messages, Streaming, Tools, Typed Output

Every AI product in this course is the same atom, dressed up: a list of messages goes in, one message comes out. Today you drive that atom through LangChain against DeepSeek — chat, streamed tokens, a tool round trip, and pydantic-typed output — and you learn exactly where a tool call stops being an agent.

Your win this lesson You can send a system + human conversation, stream the reply, hand the model a tool and complete the round trip with a ToolMessage, and get a validated SupportTicket object back — all through one model handle you can point at DeepSeek, OpenAI, or Anthropic by changing one line.

The atom is still a list of messages

Forget the framework for a second. An LLM call is a list of messages, each with a role, and the model returns the next assistant message. That's the whole protocol — LangChain just gives each role a class instead of a dictionary:

LangChain classRole on the wireWho writes it
SystemMessagesystemYou — standing rules, persona, output contract
HumanMessageuserThe person (or your UI)
AIMessageassistantThe model — may carry structured tool_calls
ToolMessagetoolYour code, after it runs a tool

RAG adds retrieved documents to that list; an agent repeats the call and appends tool results. Same atom, different plumbing.

The model handle

DeepSeek's API is OpenAI-compatible, and langchain-deepseek wraps that transport in the standard LangChain chat interface. One handle, four stages:

import os
from langchain_deepseek import ChatDeepSeek

model = ChatDeepSeek(
    model="deepseek-flash",
    api_key=os.environ["DEEPSEEK_API_KEY"],   # or just set the env var and omit
    temperature=0,
    extra_body={"thinking": {"type": "disabled"}},
)

Two 2026 details matter. DeepSeek thinks by default — the extra_body above switches that off because this lesson is about plumbing, not reasoning; delete it to watch the reasoning tokens. And deepseek-flash is the current model name (served by DeepSeek-V4.1-Flash), with deepseek-v4-pro as the larger option. Login, key, and current names: DeepSeek quick start.

Why LangChain instead of calling the compatible openai client directly? Because you get one message model and one Runnable contract across providers — the same invoke() and stream() signatures whether the backend is DeepSeek, Qwen or a local Ollama model — plus tool binding and structured-output plumbing that every later lesson reuses. It is a thin layer, not magic — and Lesson 3 builds the loop explicitly from @tool, bind_tools() and ToolMessage, so you can see every step.

Stage 1 — chat: history is the memory

The model has no memory between calls. A conversation is you re-sending the growing list:

from langchain_core.messages import AIMessage, HumanMessage, SystemMessage

messages = [
    SystemMessage(content="You are a terse support assistant. Answer in one sentence."),
    HumanMessage(content="My invoice charged me twice. What should I do?"),
]
reply = model.invoke(messages)
print(reply.content)
# e.g. Send us the invoice number and we will refund the duplicate charge
#      within three business days.

thread = messages + [reply, HumanMessage(content="And how long does the refund take?")]
print(model.invoke(thread).content)
# e.g. Refunds post within three business days.

The lab prints the count so the reframe sticks: turn 1 sends 2 messages; turn 2 sends 4 — system, human, the model's own earlier answer, and the new human turn. The wording of the replies will vary between runs; the shape will not. Your database instincts apply here: the message list is the row you re-read, not server-side session state. Persisting it is your application's job — L10 makes the graph's state explicit, which is where a checkpointer later plugs in.

Stage 2 — streaming: the same answer, in pieces

invoke() waits for the whole message. stream() yields AIMessageChunk objects as tokens arrive — and the chunks are not a summary; concatenated, they are the exact reply:

baseline = model.invoke(messages).content
pieces = [chunk.content for chunk in model.stream(messages) if chunk.content]
print("".join(pieces) == baseline)   # True

Run it and print the count. Two things hold every time: the last chunk is often empty — it carries finish metadata rather than words — and joining the text chunks reproduces the invoke() reply exactly. The chunk count is provider- and model-dependent (do not pin a number in a test or a dashboard); the invariant is the join. The empty tail is what bites people: never print chunk.content as if every chunk were text, and never count chunks as words.

Streaming is a product decision before it is a transport decision: the metric users feel is TTFT — time to first token. Lesson 4 builds the FastAPI + SSE service and the React useChat shell around exactly this loop.

Stage 3 — tools: one round trip, not an agent

You declare a Python function, LangChain turns its signature and docstring into a JSON schema, and the model can ask you to run it. The model never executes code — it returns a structured request, and you remain the permission layer:

from langchain_core.tools import tool
from langchain_core.messages import ToolMessage

ORDERS = {"A-1042": "shipped from the Sydney warehouse, arriving Thursday"}

@tool
def get_order_status(order_id: str) -> str:
    """Look up an order's fulfilment status by its id, for example A-1042."""
    return ORDERS.get(order_id, f"no order found for {order_id}")

bound = model.bind_tools([get_order_status])
messages = [
    SystemMessage(content="You are a terse support assistant. Answer in one sentence."),
    HumanMessage(content="Where is order A-1042?"),
]

ai = bound.invoke(messages)
call = ai.tool_calls[0]
# e.g. {'name': 'get_order_status', 'args': {'order_id': 'A-1042'},
#       'id': 'call_...', 'type': 'tool_call'}

result = get_order_status.invoke(call["args"])
# shipped from the Sydney warehouse, arriving Thursday

thread = messages + [ai, ToolMessage(content=result, tool_call_id=call["id"])]
print(bound.invoke(thread).content)
# e.g. Order A-1042 has shipped and should arrive Thursday.

Three contracts are doing the work. The schema tells the model what it may call and which arguments exist. The tool call id pairs the result with the request — that's why ToolMessage requires tool_call_id; the id itself is generated by the provider, so read it, never hard-code it. And the second call is where the model turns the observation into an answer. The thread is 4 messages before that final call and 5 after — that count is structural, not model output.

So… is this an agent? No — and the distinction is the lesson. This is one tool round trip: model asks, code runs, model answers. An agent is the same round trip placed inside a loop that repeats until the model returns no tool calls, with a stop condition and a budget. You have the primitive now; Lesson 3 writes the loop by hand, and lessons 10–11 turn it into an explicit graph. Calling every tool call an "agent" is how demos get mistaken for systems.

Stage 4 — structured output: the model as a typed function

Free text is useless to code. Declare a pydantic model and LangChain exposes it to the model as a schema; what comes back is a validated instance, not a dictionary you hope is shaped right:

from typing import Literal
from pydantic import BaseModel, Field

class SupportTicket(BaseModel):
    category: Literal["billing", "bug", "question"] = Field(
        description="billing, bug, or question")
    urgency: int = Field(ge=1, le=5, description="1-5, 5 being most urgent")
    summary: str = Field(description="one sentence, no invented facts")
    order_id: str | None = Field(default=None, description="order id if mentioned")

classifier = model.with_structured_output(SupportTicket, method="function_calling")
ticket = classifier.invoke([
    SystemMessage(content="Classify the support ticket. Extract the order id."),
    HumanMessage(content="My invoice charged me twice for order A-1042. Fix it now."),
])
print(ticket)
# e.g. category='billing' urgency=5 summary='Duplicate charge on the invoice
#      for order A-1042.' order_id='A-1042'

Under the hood this is the tool-calling path you just learned: the pydantic model becomes a tool, the model calls it with JSON arguments, and LangChain parses and validates the result. That's why the call works on DeepSeek, which has no OpenAI-style json_schema response format — the lab passes method="function_calling" explicitly to make the mechanism visible. Literal gives you an enum; ge/le give you range validation. A value outside the contract raises instead of silently poisoning downstream code.

This SupportTicket is not a toy: it is the classifier contract a support agent needs. Twenty minutes into the course, you have its first component.

Temperature temperature=0 ≈ deterministic, higher ≈ creative. Extraction, classification, and tool arguments want boring and repeatable — 0. Creative copy is the exception, not the default. In production most calls should be boring.

Run it yourself

This lab talks to the live DeepSeek API — there is no fake-model mode. You need a key from platform.deepseek.com/api_keys, and the account needs a small balance (DeepSeek is prepaid).

Everything in the lab is also on one page: examples/0002-first-llm-api — README, pyproject.toml, langchain_lab.py and evals.py, rendered in the browser.

# 1. key, for this terminal only
$env:DEEPSEEK_API_KEY = "sk-..."        # PowerShell
export DEEPSEEK_API_KEY="sk-..."        # bash / zsh

# ...or persist it for future terminals, then reopen the terminal
setx DEEPSEEK_API_KEY "sk-..."          # Windows
echo 'export DEEPSEEK_API_KEY="sk-..."' >> ~/.zshrc

# 2. sync dependencies and run
cd assets\examples\0002-first-llm-api
uv sync                          # create .venv from pyproject.toml + uv.lock
uv run python langchain_lab.py   # four stages, live DeepSeek
uv run python evals.py           # 32 checks (+2 live when a key is set)

No venv + pip dance: uv sync reads pyproject.toml and installs the exact graph pinned in uv.lock, and uv run executes inside that environment without activation. No uv yet? winget install --id=astral-sh.uv.

Without a key the lab prints those exact commands and exits 1 — no hidden fallback, because a canned answer would teach you the wrong thing about what a model actually returns. evals.py runs the offline checks (ticket schema, tool contract, message shapes, model wiring, the missing-key message, the uv project) and, when DEEPSEEK_API_KEY is set, adds one live call; with no key it reports the smoke test as skipped.

Optional overrides: DEEPSEEK_MODEL (default deepseek-flash) and DEEPSEEK_BASE_URL (default https://api.deepseek.com) — useful for trying deepseek-v4-pro or a proxy.

Cost, concretely: deepseek-flash lists at $0.15 per 1M input tokens (cache miss, off-peak) and $0.60 per 1M output tokens off-peak; peak hours double those. The lab's handful of short calls costs a fraction of a cent. Treat the cost dashboard as part of the product from day one — that's layer 6 work you already have instincts for.

Hands-on loop (do this, not just read it) 1. Run the lab twice and diff the output. The shapes match; the wording doesn't. That gap is why evals exist.
2. Add customer_sentiment: Literal["angry", "neutral", "happy"] to SupportTicket and re-run. Watch it appear in the schema the model sees.
3. Break the contract: send an empty messages list, then a ToolMessage with a wrong tool_call_id. Read the errors.
4. Classify the same ticket ten times and diff the outputs. Any drift is why Lesson 5 exists — even temperature=0 is not a bit-identical guarantee.
