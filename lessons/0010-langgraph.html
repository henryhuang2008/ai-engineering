LangGraph: One Node, Then a Branch

A one-node graph is a chatbot wearing a diagram. The moment an edge chooses between two nodes, you have something a prompt cannot be: a program with a visible decision. This lesson builds both, in that order, with DeepSeek behind every node.

Your win this lesson You'll compile a one-node graph, then a classifier that routes NimbusDesk messages to a billing or technical specialist — and read the trace that proves which path ran. You'll also break the edge twice, because that is where the extra router node stops being a mystery.

Part 1 — The smallest graph in the world

simple.py is one model call inside one node. It is deliberately underwhelming: the point is to see all four declarations before adding anything to them.

class State(TypedDict):
    messages: Annotated[list, add_messages]


def chatbot(state: State) -> dict:
    return {"messages": [model.invoke(state["messages"])]}


graph = StateGraph(State)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)
app = graph.compile()
declarationwhat it is herewhy it exists
Statea TypedDict holding messagesthe one object every node reads and writes
reducerAnnotated[list, add_messages]how a field merges an update instead of being replaced
nodechatbot, a plain functionthe work: call the model, run the tool, read the file
edgeSTART → chatbot → ENDwho runs next; a cycle is allowed here, unlike a chain
compilegraph.compile()validates the declarations and returns a runnable app

A node returns a delta, never the new state. {"messages": [reply]} means "one more message"; add_messages merges it. If you wrote messages: list and dropped the annotation, the same line would replace the history — the graph would still run, which is what makes that bug dangerous. Try it: the run completes, and the final state holds one message instead of two.

Real run of simple.py, live DeepSeek:

question: In one sentence, what does a router do in a LangGraph?
reply:    A router in LangGraph directs the flow of execution by conditionally selecting which node(s) to run next based on the current state, enabling branching and dynamic control flow in the graph.

state: 2 messages (human, ai)
edges:
  __start__ -> chatbot
  chatbot -> __end__

Two details are worth remembering. The edges print __start__ and __end__ because those are real sentinel nodes, not comments. And compile() is not ceremony: it is where the graph checks that every edge points at a node that exists, then hands you an object with invoke, stream and batch — the same interface as any LangChain runnable from lesson 2.

Part 2 — Make it decide

A branch needs a labeled decision. Here the label is a NimbusDesk topic — billing or technical — so each route can carry its own facts and its own prompt. The label comes from a pydantic schema:

class Route(BaseModel):
    route: Literal["billing", "technical"] = Field(
        description="billing for money questions, technical for product failures"
    )

classifier = model.with_structured_output(Route, method="function_calling")

This is lesson 2's structured output doing the routing. It matters that the type is a Literal: the model cannot return "probably billing" or "refund question", because the schema has exactly two legal values. Compare that with the tempting alternative — if "refund" in reply.content — which fails on spelling, paraphrase, and a message that mentions both. The classifier is still a model call, so it can be wrong; it just cannot be malformed. Wrongness is an eval problem (lesson 5), not a graph problem.

State gains one field for the label, and the graph gains one conditional edge:

class State(TypedDict):
    messages: Annotated[list, add_messages]
    route: str | None


def classify(state: State) -> dict:
    decision = classifier.invoke(
        [SystemMessage(content=CLASSIFY_PROMPT), state["messages"][-1]]
    )
    return {"route": decision.route}


def pick_specialist(state: State) -> str:
    return state["route"] or "technical"


graph.add_conditional_edges(
    "classify",
    pick_specialist,
    {"billing": "billing", "technical": "technical"},
)

The second argument is a function; the third is the map from its return value to a node. That map is the whole branch, visible as data — and as a picture:

stream_mode="updates" yields one dict per node — {"classify": {"route": ...}}, then {"technical": {"messages": [...]}}. That is lesson 4's "watch it happen" habit one level up: not tokens, transitions. The billing run never mentions E-311, and the technical run never mentions refunds, because only one specialist ran.

Part 3 — The node you can delete

A common first version puts a third node between the classifier and the specialists:

graph.add_node("router", router)              # returns {"next": "billing"}
graph.add_edge("classifier", "router")
graph.add_conditional_edges("router", lambda state: state.get("next"), {...})

It works. It is also a decision pretending to be work. The router function calls no model, reads no file, and changes nothing a user can see; it computes a string and stores it so an edge can read it back. Move that string to where it is used:

graph.add_conditional_edges("classify", pick_specialist, {...})

Three things improve. One fewer superstep per turn — the classifier's delta routes directly. No stale field — next is not persisted, so it cannot disagree with the route a later turn computed. And the contract is explicit — the edge's return value must be a key in the map. The rule underneath: nodes do work; edges decide.

This distinction is not style. The two roles accept different return types, and the errors are blunt about it. Both of these were run against this graph:

the edge function returns…resultwhat it means
"refunds" — not in the mapKeyError: 'refunds'the map is a whitelist, not a suggestion
{"next": "billing"} — a deltaTypeError: unhashable type: 'dict'an edge returns a key; deltas belong in nodes

The second error is the node/edge split-brain case in one line: a node may return {"next": ...}, because nodes return deltas. An edge must return a node name, END, or a list of names. If you copy the router's body into the edge and forget to drop the dict, LangGraph tries to hash it as a key. The traceback tells you which role you are actually in.

Part 4 — State is not memory

A plain chat loop keeps a dict and appends each user message before invoking the graph. That is correct, and it exposes the limit: without a checkpointer, the returned state is the only memory there is. Our REPL does the same thing with the state that invoke returns:

state = app.invoke(
    {**state, "messages": state["messages"] + [HumanMessage(content=text)]}
)

Exit the process and the conversation is gone. Notice also what our specialists receive: all messages in state, not just the last one. A two-message prompt per turn would quietly throw history away. Here the state carries it and the node decides what to send — the node is the only place that choice should live.

A checkpointer plus a thread_id makes the graph read its own history back from a database, so a second process can continue the same conversation. That is the production step this lesson stops short of; the important part today is that the graph is already shaped to accept it.

Part 5 — When a branch beats an if

Honesty first: for one branch, an if statement is shorter and has no dependency. A graph earns its keep when the decision has to be visible, tested, or extended.

situationuse
one prompt, maybe one tool callplain function — lesson 3
one branch chosen from a typed labelan if is fine; a graph is already reasonable
several routes, each with its own prompt and toolsLangGraph: the map is the documentation
need per-step traces, resume, or human approvalLangGraph: the checkpointer is the deciding feature
Interview · "Why not just if/else?" "For one branch I do use if/else. I move to a graph when the routing stops fitting in one head: multiple specialists, per-node prompts and tools, and a trace that shows which path ran. The graph also gives me reducers so state merges by rule, and a checkpointer so a run can resume — the branch itself is only the visible part. The classifier is structured output, so the route is a validated label rather than a string match, and I grade the classifier separately because a wrong route is an eval failure, not a graph failure."
