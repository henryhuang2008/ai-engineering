Human in the Loop — Pause a Graph, Answer It From Anywhere

A tool call is about to write something. Someone should look at it first. LangGraph gives you one primitive for that — a pause the checkpointer remembers — and this lesson shows the same pause behind three very different transports: a blocking request, a server-sent-event stream, and an MCP tool that stops inside interrupt(). One graph, three answers, and the list of things approval still does not solve.

Your win this lesson You can add a human gate to a graph, explain why the graph ends instead of waiting, resume it after a restart in principle and after a new request in practice, and choose between the static breakpoint and the dynamic interrupt() for a given tool.

Part 1 — A pause is not a blocked thread

The first thing to get right: interrupt_before does not make invoke sit and wait. The graph runs until the node it should not enter, writes a checkpoint, and returns. The process can exit. The pause is data, not a parked coroutine. 

graph = builder.compile(
    interrupt_before=["human_feedback"],
    checkpointer=MemorySaver(),
)

config = {"configurable": {"thread_id": "thread-1"}}
result = graph.invoke({"human_request": "Explain HITL"}, config)   # returns

state = graph.get_state(config)
state.next          # ('human_feedback',)  - what did not run
state.values        # the draft, the request, the status

Three consequences follow, and most HITL bugs come from missing one:

  • You need a checkpointer. Without one there is nowhere to store the pause; the graph just runs through the breakpoint.
  • The thread_id is the handle. It is how the next request finds this exact state. Two users with the same id share a conversation.
  • Resuming is a new run, not a continuation of the old call. Same graph, same config, new input.

There are two ways to pause, and they answer different questions:

interrupt_before=[...] interrupt({...})
Where between nodes, chosen when you compile inside a node or tool, chosen at run time
What the caller sees state.next names the node that did not run the value you passed to interrupt()
How to resume write state, then invoke(None, config) invoke(Command(resume=value), config)
Good for a review step that always happens in the same place a tool that only sometimes needs a person

The static breakpoint is easier to read and to reason about. The dynamic one is the only option when the decision depends on arguments the model produces — which is every real tool.

Part 2 — The graph: draft, review, finalize

The example is deliberately small. One request goes in, a draft comes out, a person edits or approves it, and a polish step closes the run: 

START → assistant_draft → human_feedback → assistant_finalize → END
                              │
                              └─ status == "feedback" → assistant_draft

The state carries the request, the reviewer's comment, the decision, and the latest draft:

class DraftReviewState(MessagesState):
    human_request: str
    human_comment: Optional[str]
    status: Literal["approved", "feedback"]
    assistant_response: str

human_feedback is an empty node on purpose. It exists so the breakpoint has a name. The reviewer writes status (and a comment when there is one) into the checkpoint with update_state, and the router reads that field to choose the next edge: 

graph.update_state(config, {
    "status": "feedback",
    "human_comment": "Make it one short sentence.",
})

graph.invoke(None, config)      # continue from the checkpoint
Two details that bite invoke(None, config) means “continue”; passing the previous input again starts the work over. And update_state writes into the checkpoint before the next run, so a crash between the two calls leaves the decision recorded and the node unrun.

Part 3 — The pause inside one response

The blocking route is the simplest honest API. One function runs the graph and translates the state into a status: 

def run_graph_and_response(input_state, config):
    result = graph.invoke(input_state, config)
    state = graph.get_state(config)

    if state.next and "human_feedback" in state.next:
        run_status = "user_feedback"
    else:
        run_status = "finished"

    return GraphResponse(
        thread_id=config["configurable"]["thread_id"],
        run_status=run_status,
        assistant_response=result["assistant_response"],
    )

POST /graph/start creates the thread. POST /graph/resume takes the same thread_id, writes the decision, and calls the same function with None. That is the whole HITL API: two routes, one status field, one checkpoint per thread.

Note what the response does not contain: the model's reasoning, the tool list, or a token stream. For a review UI that is enough — the draft is the artifact, and the pause is a field.

Part 4 — The pause behind SSE

Streaming changes the shape of the conversation, because EventSource can only issue GET requests. A browser cannot POST the approval and read the stream in one call. The example splits it:

  1. POST /graph/stream/create stores {type: "start", human_request} and returns pending with a thread_id. Nothing has run.
  2. GET /graph/stream/{thread_id} runs the graph and streams token events, then a final status event.
  3. POST /graph/stream/resume stores the decision the same way, and the next GET applies it with graph.update_state before streaming.

The split is not decoration. The POST that would block on the model is the one you want to stream, and the cheap POST that records a decision lets the client start the long request immediately. Measured here, creating a run took 4 ms; the stream that did the work took 1.65 s and produced 163 data: lines before status: user_feedback.

The generator reads the pause from the same place the blocking route does: 

state = graph.get_state(config)
if state.next and 'human_feedback' in state.next:
    yield {"event": "status", "data": json.dumps({"status": "user_feedback"})}
else:
    yield {"event": "status", "data": json.dumps({"status": "finished"})}

One caveat, visible in the file: it calls the synchronous graph.stream(...) inside an async generator. It works, and it blocks the event loop while it runs — fine for one learner, wrong for a server with two users. The fix is astream, not a thread.

Part 5 — The pause inside a tool

The third version is the one that generalises. Instead of a review node, every MCP tool is wrapped so its body begins with interrupt(): 

@tool(main_tool.name, description=main_tool.description,
      args_schema=main_tool.args_schema)
async def call_main_tool_with_hitl(config: RunnableConfig, **tool_input):
    decision = interrupt({"awaiting": main_tool.name, "args": tool_input})

    if isinstance(decision, dict) and decision.get("approved"):
        return await main_tool.ainvoke(tool_input, config)

    return ("Cancelled by human. Continue without executing that tool "
            "and provide next steps.")

The pause payload is the decision material: which tool, with which arguments. The caller resumes with the answer: 

Command(resume={"approved": True})

That value is what interrupt() returns, and the tool continues from that line — not from the beginning of the graph. Rejection is a first-class result, not an exception: the tool returns a sentence, the model reads it and plans something else.

The pause is detected differently here. There is no state.next to inspect, because the graph did not stop between nodes; it stopped inside one. The resume comes back with __interrupt__ in the result (the route reads interrupts[0].value), which is why the MCP lesson cannot reuse the blocking route's status check.

Part 7 — What approval still has to decide

The graph gives you the pause. It does not give you an approval system, and the example is honest about the gap: the resume routes are open, the checkpointer is in memory, and a thread id is the only thing identifying the reviewer.

QuestionThis labWhat a real system adds
Who may resume? anyone with the thread_id authentication plus an authorisation check per thread
How long may a pause live? until the process exits a durable checkpointer and an expiry on pending approvals
What exactly was approved? the draft text, or the tool name and arguments a recorded payload hash, so the decision matches what ran
What if approval arrives twice? the run resumes twice a single-use token keyed by interrupt id
What if the human edits arguments? not supported; feedback re-plans instead an edit path with validation, and a new approval for the edit

That last row is the one people skip. Approving a tool call is not approving the tool: the arguments are the payload, and a gate that only checks the name can be talked into anything the schema allows.

Part 8 — What breaks

SymptomCauseFix
the graph never pauses compile() had no checkpointer pass one; the breakpoint needs somewhere to store state
resuming runs the first node again invoke(original_input, config) instead of invoke(None, config) None means continue; any other input starts over
state.next is empty but the run is not done the pause is inside a node (interrupt()), not between nodes read __interrupt__ / state.interrupts instead
a resume lands on the wrong thread a new thread_id, or a missing one one id per conversation; treat it as part of the request contract
two pauses, one decision one turn hit two interrupt() calls resume by interrupt id, one value per id
the server answers one request at a time sync graph.stream inside an async generator astream, or run the sync call in a worker
every pause vanishes on restart MemorySaver PostgresSaver, the way Lesson 19 does it

Part 9 — What was verified

  • Live, blocking: DeepSeek deepseek-flash drafted, paused with run_status: user_feedback, revised on feedback, finished on approved.
  • Live, SSE: a 4 ms create, then a 1.65 s stream with 163 data: lines, a status: user_feedback event, a feedback stream, and a final status: finished.
  • Live, MCP: the shipped config needs Docker, which was not running here. The same path was exercised with a local stdio MCP server — MultiServerMCPClient, the same interrupt() wrapper, Command(resume=...) — and the config was restored afterwards. Approve returned the tool's data as prose; reject returned a plan without it.
  • Error paths: a review_action outside the declared Literal returns 422; an unknown route returns 404.
  • Not verified: Docker/GitHub MCP end to end, a durable checkpointer for this graph, and anything about who is allowed to resume.

What's next

This is the last lesson, so “next” is the approval layer the lab leaves open. Three things build directly on it: put PostgresSaver behind the graph so a pause survives a restart (Lesson 19 has the code); authenticate and expire the resume endpoint, with one single-use token per interrupt id; and record what was approved — payload hash, reviewer, timestamp — because “someone clicked approve” is not an audit trail. The boundary map is the checklist for that last part, the skill map places the gate beside tools and memory, and Lesson 1 is the way back to the start.

Before you ship a human gate: name who may resume, how long a pause lives, and what exactly the person saw when they said yes. The graph gives you the pause; those three are the system.
