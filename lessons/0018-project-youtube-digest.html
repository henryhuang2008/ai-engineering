Project: AI News Digest — from YouTube RSS to a Scheduled Email

The brief is an AI news aggregator: pull from several sources, store everything in PostgreSQL, and every day email a digest of the last 24 hours summarized to your own editorial instructions. The repository implements the first vertical slice — one curated YouTube channel, run by hand — and its todo.md keeps the rest as explicit, unchecked phases. That split is the lesson. A plan that separates what is built from what is next is worth more than a demo that implies both. And two of the sources you cannot control are genuinely hostile: an RSS endpoint that intermittently returns 404, and a caption endpoint that blocks cloud IPs.

Your win this lesson You'll be able to turn a product brief into a phased checklist with acceptance checks, lay out an app/ package that keeps ingestion, generation and delivery apart, model sources and articles in SQLAlchemy with Alembic owning the schema, isolate a flaky source instead of letting it abort the run, design a transcript fallback that keeps the digest useful, bound model input by characters, validate model JSON and URLs before rendering, and gate an email side effect with a record and an idempotency check — then decide honestly what a scheduler would change.

Part 1 — A batch pipeline, not a chat product

The capstone is interactive and read-only: a user asks, retrieval and validation happen inside the request, and the failure mode is a refusal. This project is the opposite shape. It runs on a timer, writes to the database, sends an email, and has to report partial failure honestly. A failed run is not a refused answer; it is a day with no digest. That difference changes almost every design decision.

dimension capstone (lesson 17) digest (this lesson)
trigger authenticated request daily scheduler (target); manual CLI (shipped slice)
state Supabase Postgres with RLS PostgreSQL 16 in Docker
external inputs one audited filing corpus many channel feeds and caption endpoints
failure policy fail closed before streaming isolate the failed source, keep last-good state, report and exit non-zero
side effect none — read-only answers email delivery, which cannot be un-sent
idempotency one saved turn per request one successful send per UTC date; --force adds an attempt
test seam fake retrieval, no live providers dummy RSS fixture, injectable clock, temporary SQLite, mocked SMTP

The brief is bigger than the repository, and the gap is the point. The brief asks for multiple sources, a daily scheduler, and summaries shaped by your own editorial instructions. The shipped slice is Python 3.12, one curated channel, local Postgres, and a command you run yourself. The scheduler, a second source kind and per-user profiles are named phases in docs/todo.md — unchecked, not features in the code. Keeping them visible as unbuilt is more honest than quietly widening the demo until it looks finished.

The narrow slice exists for a reason. Scheduling adds duplicate sends, time-zone edge cases, credential rotation and alerting, and it removes the human who can see that today's feed returned 404. You want the failure behavior understood and tested before you take the human out of the loop. That is why this lesson builds the pipeline, proves it by hand, and only then asks what a cron entry would change.

The example's default command is a preview. It reads saved rows, calls DeepSeek, prints the digest, and does not send or persist anything. Email is an explicit opt-in. This is the same trust instinct as the capstone's fail-closed validator, applied to a side effect: make the safe action the default, and make the irreversible action a separate decision.

Part 2 — The brief becomes todo.md

The brief is a paragraph of product intent, not a build order. Turning it into a checklist is the first engineering act, and the one most likely to be skipped. Here is the prompt that produces the plan — the product brief, unchanged, plus the rules that make the output verifiable: 

I want to build an AI news aggregator that pulls content from multiple
sources, such as YouTube channels. The system will scrape these sources
and store the data into a structured PostgreSQL database containing
entities like sources and articles.

On a daily basis, a cron job or scheduler will fetch all articles
collected within the last 24 hours to generate a daily digest. An LLM
will summarize this content based on custom user insights defined in an
AI agent system prompt. The final daily digest will consist of short,
punchy snippets, each accompanied by a link back to the original source.

For data ingestion, the system will track a curated list of YouTube
channels and fetch their latest videos using their respective YouTube
RSS feeds.

Add project structure in the plan.

Technical requirements:
- Backend: fully built in Python.
- Database: PostgreSQL with SQLAlchemy models for the tables and
  Alembic migrations for every schema change.
- Project structure: all application logic in app/; a separate docker/
  folder for a minimal PostgreSQL container.
- Delivery: once the digest is generated, email it to my personal inbox.

Now write docs/todo.md. Give me the phases in build order. Say what each
phase blocks. For every item:
- name the files or modules it touches
- give an acceptance check (a command, a row count, a response, or a test)
- label it implementation, verification, or deployment
- leave the box unchecked until the acceptance check has actually run

Do not write application code yet.

Two instructions in that prompt do the real work. "Add project structure in the plan" forces the folder layout to be decided before modules start importing each other, and it makes the boundary between app/ and docker/ explicit. "Leave the box unchecked until the acceptance check has actually run" is what stops a checklist from becoming a list of intentions.

Part 3 — RSS is an undocumented, unstable boundary

The discovery source is the public channel feed:

https://www.youtube.com/feeds/videos.xml?channel_id=UC...

It is convenient and free, but it is not a contract with a published availability guarantee. A long-running Google AI developers forum thread documents intermittent 404 responses from this endpoint starting in December 2025 and still being reported months later. The reported pattern is worth knowing:

  • the channels are active and public, and the same URL works in a browser during the failure;
  • errors cluster around 09:00–12:00 UTC, then clear;
  • different channels are affected on different days;
  • the response is a 404 HTML page, not a feed with zero entries;
  • no root cause or documented rate limit is published in the thread.

So the first rule is interpretive: a 404 does not mean the channel was deleted. It does not mean the channel ID is invalid, either. Treating it as either one is how a transient upstream problem turns into deleted data or a deactivated source.

What the project does

The feed fetch and the database write are deliberately separate. _fetch_feeds calls the fetcher once per channel, catches OSError and ValueError, and records a FeedFailure instead of aborting the run: 

for channel in channels:
    try:
        feed = feed_fetcher(channel.channel_id)
        if feed.channel_id != channel.channel_id:
            raise ValueError("feed channel ID did not match configuration")
    except (OSError, ValueError) as error:
        failures.append(FeedFailure(..., error=f"{type(error).__name__}: {error}"))
    else:
        feeds.append((channel, feed))

Only the successful feeds reach the upsert. The transaction still refreshes every configured channel, marks channels removed from channels.json inactive, and writes the videos it did receive. A channel whose feed failed stays active and keeps its existing rows. The CLI then prints each failure to stderr and exits non-zero if there was any failure, even when other channels succeeded. That is the correct partial-success contract: the run did useful work, and it did not pretend the work was complete.

The parser validates more than the HTTP status. It requires a channel ID matching UC[A-Za-z0-9_-]{22}, rejects a feed whose channel ID does not match the configured one, rejects an entry with no video ID, and converts the published tuple to an aware UTC timestamp. A 404 HTML page will fail parsing rather than being stored as an empty feed.

The fixture is part of the design

uv run python -m app.ingest.seed --dummy-data reads app/data/dummy_youtube_feed.xml instead of requesting YouTube. It prints that no RSS requests were made, and it rejects a channel configuration that does not match the fixture. The unit tests use the same parser against the fixture and a temporary SQLite database. This is how the project stays testable while the real endpoint is unreliable: the parser and upsert contract are deterministic, and the network is a separate, replaceable input.

What is still missing

The example does not retry, back off, or remember a per-source last_success and last_error. For a manual run that is a defensible scope cut. Before you put this on a schedule, add the missing operational layer:

  1. Retry the fetch a small number of times with jittered backoff. A 404 in the reported window is a reason to try later, not a reason to delete anything.
  2. Persist fetch outcomes per source, so "no new videos" is distinguishable from "the feed has failed for three days."
  3. Keep last-good state. A failed feed must never cascade into deleting articles or deactivating a channel.
  4. Have a fallback discovery path if the feed stays down: the YouTube Data API has a quota cost, and PubSubHubbub can push notifications, but neither is free of operational work. Choose one deliberately.

None of these belong in the first vertical slice. The first slice should prove the parse-and-upsert contract against a fixture; the retry policy is a second decision, made when the run is actually scheduled.

Part 4 — Captions have a different failure mode: your IP

youtube-transcript-api does not use an official captions API. Its own documentation warns that it uses an undocumented part of the YouTube web client and that there is no guarantee it will keep working. The more immediate problem is network identity: YouTube blocks many IP ranges belonging to cloud providers, and a self-hosted machine making too many requests can be blocked too. The library surfaces this as RequestBlocked or IpBlocked.

The documented workaround is a rotating residential proxy. Static proxies get banned after extended use, so a static proxy is not a fix; it is a delay. The library exposes WebshareProxyConfig for a Webshare residential package and GenericProxyConfig for any HTTP, HTTPS or SOCKS proxy. That is a paid dependency and an operational decision, not something to hide inside a retry loop.

What the project does

The project treats a transcript as an enhancement, never a requirement. fetch_transcript catches CouldNotRetrieveTranscript — the base class of RequestBlocked and IpBlocked — and returns None. Then get_video_content chooses the best available content and labels where it came from: 

transcript = fetch_transcript(video_url, languages=languages)
if transcript and transcript.text:
    return VideoContent(text=transcript.text, source="transcript", transcript=transcript)
if description.strip():
    return VideoContent(text=description.strip(), source="description")
return VideoContent(text="", source="unavailable")

The label travels with the content. The article row stores the transcript text, its language and whether it was generated, while the RSS description remains in its own column. Re-running ingestion refreshes RSS metadata but deliberately does not overwrite a transcript that is already stored. The digest input then prefers the transcript and falls back to the description. A failed caption fetch degrades the summary; it does not fail the run.

That is the right user-facing behavior for a personal digest. It is not sufficient observability. The current seam returns None without recording why, so a permanent IP block looks exactly like "this video has no captions." If every video falls back to its description, the digest still sends, but it is summarizing marketing copy instead of the talk. Log the exception class and count transcript-versus-description fallbacks before you trust the output at scale.

Where a proxy would go

The example does not ship a proxy layer. If you deploy it to a cloud IP, the change belongs at the transcript seam, not scattered through the pipeline. Keep credentials in the settings module, never in code: 

from youtube_transcript_api import YouTubeTranscriptApi
from youtube_transcript_api.proxies import WebshareProxyConfig

api = YouTubeTranscriptApi(
    proxy_config=WebshareProxyConfig(
        proxy_username=settings.proxy_username,
        proxy_password=settings.proxy_password,
    )
)
fetched = api.fetch(video_id, languages=languages)

Two constraints make this safe. First, the proxy is an explicit configuration choice; a missing credential should fail loudly, not silently fall back to a direct request that will be blocked. Second, the fallback still exists. A proxy reduces the chance of a block; it does not make the external dependency reliable.

Part 5 — PostgreSQL, SQLAlchemy, and Alembic

Three tables carry the product. The names are boring on purpose; the constraints are where the behavior lives.

table what it holds constraint that matters
sources channel identity, feed URL, active flag channel_id unique, so a channel is upserted rather than duplicated
articles video metadata, RSS description, optional transcript and caption metadata, publication time video_id unique; source_id cascades on delete; index on published_at
digests UTC window, subject, text and HTML bodies, model, article count, status, recipient, send time status restricted to sent, failed, empty

SQLAlchemy models describe the tables, and Alembic owns the schema history. There is no create_all in the application path. uv run python -m app.database.migrate upgrades to head; run assumes the schema is already there. The initial revision creates the three tables, the foreign key, the unique constraints, the status check and the publication index. A second revision drops the unique constraint on digests.run_date: 

def upgrade() -> None:
    op.drop_constraint("uq_digests_run_date", "digests", type_="unique")

def downgrade() -> None:
    op.create_unique_constraint("uq_digests_run_date", "digests", ["run_date"])

That migration is not cosmetic. The first schema enforced one digest row per UTC date, which made --force impossible to record without overwriting history. Dropping the constraint is the schema change that lets an intentional second attempt coexist with the first. The application-level check for "already sent today" still prevents a normal duplicate; the database no longer makes a forced attempt illegal. Product behavior and schema changed together, in a reviewed revision.

The models themselves

The brief asks for SQLAlchemy models, and the models are where the product's rules stop being prose. These are the real definitions, with imports and docstrings trimmed:

Read the constraints as decisions. channel_id unique makes ingestion an upsert instead of a duplicate factory. video_id unique plus ondelete="CASCADE" ties an article to exactly one source and removes it with that source. published_at is nullable because a feed can omit it, and indexed because every digest query filters on it. The status check constraint is the product rule that a digest is sent, failed or empty — never "maybe".

The multi-source seam, and its cost sources.kind is the field the aggregator brief needs: a YouTube channel and, later, a blog or newsletter are both sources. But articles.video_id is YouTube-specific naming, and the only collector implemented is YouTube. Ship one kind first; when the second lands, rename to a generic external_id and key the uniqueness constraint on (source_id, external_id). Do that in a migration, and say in the plan that the rename is coming — that is cheaper than pretending the schema is already general.

Part 6 — Ingestion is an upsert, not an append

The ingestion job is deliberately boring: load and validate app/data/channels.json, fetch each feed, then write in one transaction. The details are the lesson.

  1. Validate the curated list before touching the network. Every entry needs a non-empty name and a valid UC... channel ID. Duplicate IDs and an empty list are rejected. A bad configuration should fail before it makes requests or writes rows.
  2. Fetch outside the transaction. A slow or failed feed should not hold a database transaction open. The fetches produce a list of successes and a list of failures.
  3. Upsert channels by channel_id. The configured name and feed URL are refreshed and the channel is marked active. Channels no longer present in the file are marked inactive, not deleted.
  4. Upsert articles by video_id. Title, URL, description and publication time are refreshed. The set_ list deliberately omits transcript, transcript_language and transcript_is_generated, so a later RSS refresh cannot erase them.
  5. Report counts and failures. The report distinguishes channels synced, feeds succeeded, videos upserted and failed feeds. The CLI exits non-zero if any feed failed, while still committing the channels that worked.

The dialect switch is a small but useful test seam. _insert_for_dialect selects PostgreSQL or SQLite insert, so the same upsert logic can run against a temporary SQLite database in unit tests and against Postgres in the real run. The tests cover channel upserts, article inserts and updates, duplicate video IDs, inactive channels, a failed feed, and the dummy-feed path that writes and reads rows back from SQLite.

Product limit: a channel RSS feed returns roughly the latest fifteen videos, not the archive. The 24-hour digest window is a subset of that. If you stop running for a week, you do not get the week back. A daily digest is not a backfill, and a "missing" old video is not a retrieval bug.

Part 7 — From rows to a bounded prompt

Generation starts with a time window, not with the whole table. get_digest_window requires an aware datetime, converts it to UTC, and returns [now - 24 hours, now]. The query includes both bounds, excludes rows with a null published_at, and orders by publication time and ID for deterministic tests. The tests cover the inclusive boundary, a naive timestamp rejection, and the empty case.

Then the input builder applies a character budget:

limit value why
per-video content 12,000 characters one long transcript cannot crowd out every other video
total input 48,000 characters the prompt stays inside a predictable context and cost envelope
content preference transcript, then RSS description, then an explicit unavailable marker the model is told what it actually has
truncation marked with [Content truncated.] the model is not handed a silent cut

Only articles whose blocks fit become part of the prompt, and the allowed URLs are exactly the URLs of those included articles. If the total budget is exhausted, later articles are left out of both the prompt and the allowlist. That coupling is what makes the next validation step meaningful: the model cannot cite an article it never saw.

The plan mentions an article-count cap; the implementation's real bound is characters. That is the behavior to test. It also bounds the prompt-injection surface: article text is untrusted input, so less of it is easier to reason about, and the system prompt explicitly says to treat it as source material rather than instructions.

Custom insights are a prompt file, not a setting

The brief says the LLM summarizes "based on custom user insights defined in an AI agent system prompt." In the repository that is literal: app/agent/prompts/digest_system.md holds the editorial instructions — what to prioritize, how blunt to be, how long a snippet may run — and load_system_prompt() reads it at call time. Change the file, run again, and the digest changes. No code edit, no redeploy.

That is the cheapest possible version of the feature, and it is worth being precise about its limits. The prompt is global: one file, one editorial voice, one recipient. The "user" in "custom user insights" is you, the operator. A product with real users needs a digest_profiles table, a profile-to-recipient relation, and a test that each profile produces its own prompt — which is a schema change and a scheduler change, not a prompt tweak. Say that in the plan rather than calling the file a personalization feature.

The other half of "short, punchy snippets" is enforced structurally, not editorially: the parser caps each summary at 600 characters and each title at 200. The prompt asks for brevity; the validator guarantees an upper bound. When you want a different tone, edit the prompt. When you want a different contract, change the code and its tests.

uv run python main.py run --raw prints the saved article records in the window as JSON without calling DeepSeek, sending email, or recording an attempt. Use it when the digest looks wrong: first prove the window and the stored content, then prove the model contract. Mixing those two debugging steps is how a data problem gets misdiagnosed as a prompt problem.

Part 8 — One strict model contract

The model call is intentionally small. DeepSeek deepseek-chat is reached through the openai SDK pointed at https://api.deepseek.com. The package is a transport detail; the provider is DeepSeek. app/agent/prompts/digest_system.md is loaded at runtime by load_system_prompt(), so the editorial voice is editable without touching Python. There is no per-run override flag yet: the file path is a function argument with a fixed default, which is enough for one operator and one digest.

The system prompt defines the only acceptable shape:

{
  "subject": "A concise email subject",
  "entries": [
    {
      "title": "A concise title",
      "summary": "A useful, factual summary",
      "url": "An exact URL copied from one of the provided article records"
    }
  ]
}

The parser is the enforcement, not the prompt. It checks all of the following before anything is rendered:

  • the response is a JSON object, not prose wrapped around JSON;
  • subject is a non-empty single line of at most 120 characters;
  • entries is a non-empty array;
  • each title is at most 200 characters and each summary at most 600;
  • each URL is an exact member of the input allowlist, not a normalized or shortened variant;
  • no URL is repeated, and every allowed URL appears exactly once;
  • every allowlisted URL is HTTPS on a known YouTube host, with no credentials and no unusual port.

The renderer then builds the plain-text and HTML bodies in code. Every article- and model-provided string is passed through html.escape, and the only value inserted into an href is a URL that already passed the allowlist. The model never emits HTML. That separation is the whole defense: a summary containing markup is text, not structure.

One drift worth noticing The design document mentions response_format: json_object on the DeepSeek call. The current service asks for JSON in the system prompt and relies on the strict parser instead. That is not unsafe — malformed output raises, the attempt is recorded as failed, and no email is sent — but adding the parameter is a cheap hardening. The lesson is to compare the plan with the code, not to assume the plan is what runs.

What this contract does not prove: a URL allowlist protects link integrity, not truth. The model can still write an inaccurate summary about a real video. The digest is a summary product, not a citation-backed analyst, and the right next check is an eval set of representative videos with human-scored summaries. The parser guarantees shape and provenance of links; it does not guarantee semantic accuracy.

Part 9 — Email is a side effect: gate it, record it, key it

Email is the first action in the course that cannot be taken back. The project treats it accordingly. run without flags prints a preview and writes nothing. --send-email opts into delivery. --force is rejected unless --send-email is present, and --raw cannot be combined with sending. Those argument checks are not pedantry; they prevent a debugging invocation from becoming a real send.

The delivery attempt is persisted before the work starts, as failed. That row is then updated with the generated subject and bodies. Only after SMTP returns without raising does the status become sent and sent_at get a timestamp. If generation or delivery raises, the row stays failed and the CLI exits non-zero. An empty window is recorded as empty and does not call DeepSeek or send mail. A failed or empty attempt does not block a later retry that day.

status meaning what the operator should do
sent SMTP accepted the message nothing; a normal rerun on the same UTC date skips
failed generation or delivery raised read the error, fix it, retry; --force is not needed for a failed row
empty no articles in the window nothing; no mail was sent

The idempotency check is simple: before a normal run, look for a sent row with the same UTC run_date; if one exists, skip. --force bypasses the check and creates a new attempt. This is the right shape for a personal digest, but be precise about what it guarantees. It is a check-then-send, not a distributed lock. Two concurrent runs can both pass the check, and a crash after SMTP accepts the message but before the sent commit can produce a duplicate on the next run. For customer mail or money, you would need an outbox, a unique claim or a provider idempotency key. For a daily digest to yourself, the record plus a single trigger is a reasonable trade — and when that trigger becomes cron, add the lock.

The SMTP details are ordinary but easy to get wrong. The connection uses STARTTLS on port 587, authenticates, and sends a multipart message with both plain text and HTML alternatives. The authentication error path explicitly explains the Gmail app-password mistake, because a server disconnect during login is more often a credential format problem than a network problem. Unit tests mock the SMTP client, so the suite never sends real mail and never needs credentials.

Gate: with local Postgres migrated and credentials configured, run uv run python main.py run --send-email, confirm the inbox and the sent row, then run it again and confirm it skips. The example's checklist still marks live delivery and the second-run observation as open, so the lesson does not claim them.

Part 10 — Scheduling: the phase that changes the contract

The brief says "a cron job or scheduler." The repository ships neither, and that is a decision, not an omission. While a human runs the command, the human is the retry policy, the alerting system and the duplicate check. A cron entry removes all three at once. Everything that was acceptable interactively becomes a production requirement.

concern manual run scheduled run
duplicate send you see the skip and stop two overlapping triggers both pass the check — you need a lock, not just a lookup
failure visibility non-zero exit in your terminal nobody is watching; you need an alert or a dead-man check
time zone you pick the moment cron fires in the host's zone; the digest window is UTC — state both, explicitly
partial ingestion you notice a 404 and rerun later a silent 404 becomes a thin digest; persist per-source outcomes
secrets .env on your laptop a secret store or an environment file with tight permissions

The minimum honest scheduler is two lines and a log. Run ingestion, then generation, and keep the two exit codes separate so a partial ingestion does not look like a clean run: 

# 07:00 UTC daily — the host must run in UTC, or set CRON_TZ
0 7 * * * cd /srv/ai-news-digest && \
  uv run python -m app.ingest.seed; \
  uv run python main.py run --send-email >> /var/log/digest.log 2>&1

The ; is deliberate. If one feed 404s, ingestion exits non-zero but the transaction has already committed the other channels and preserved last-good state; you still want the digest built from what landed. Using && instead gives you "no digest when any feed fails", which is a defensible but different product decision. Write the choice down, because it is the same last-good-state rule from Part 3 expressed as a shell operator.

Equivalents: a systemd timer with OnCalendar and Persistent=true (it catches up after downtime), Windows Task Scheduler, or a hosted cron. A GitHub Actions schedule is convenient but puts your database credentials and SMTP password in a third party and gives you a shared runner IP — which is exactly what the caption endpoint in Part 4 dislikes. A small always-on VM next to the Postgres volume is the least surprising home for this pipeline.

What is still missing No cron file, no lock, no alerting and no per-source fetch history exist in the repository. Before you add the trigger, add the three things that make an unattended failure visible: a flock (or an advisory lock) around the run, a persisted last_success and last_error per source, and a way to hear about a failed or empty digest. A scheduler without those is a machine that fails quietly at 07:00 and takes you a week to notice.

Part 11 — AI coding: phases are prompts with gates

This repository does not have the capstone's multi-service instruction hierarchy. It has two design documents, a todo list and a single Python package. That is enough. The working prompt for a phase is narrow and evidence-based: 

Work only on the transcript phase. Before writing code, restate the files
and interfaces you will touch, the acceptance checks, and what this phase
must not include. Implement the smallest change, then run:

uv run python -m unittest discover -s tests -p test_transcript.py -v

Do not mark the phase complete until you can show the output that passes
each check. Do not add a scheduler or a frontend in this phase.

The more interesting AI-coding habit is how the project makes a flaky dependency testable without faking the product:

  • feed_fetcher is a parameter, so --dummy-data can substitute the fixture and tests can inject a failure.
  • now is injectable, so the 24-hour window and its boundaries are deterministic.
  • The database tests use a temporary SQLite engine through the same models, so no Docker or Postgres is required.
  • SMTP is a callable dependency, so success and failure are both testable without a mailbox.
  • The digest generator is injectable, so window selection and input bounds can be tested without DeepSeek.

That is the transferable pattern: put a seam at the boundary, then test the deterministic side. Do not "mock the world" inside business logic, and do not replace the live model in the running app. The suite is credential-free by design, which is why it can run on every change.

The current suite reports 54 passing tests in well under a second. That is evidence for the schema, window, input bounds, parser, renderer, CLI guards, persistence and mocked delivery. It is not evidence that the RSS endpoint is reachable, that DeepSeek returns a good summary, or that Gmail accepts the message. Those are live gates, and the todo keeps them separate.

Three live gates remain: apply the digest-attempt migration and verify the upgraded schema; deliver a real email and confirm the saved sent row; run again the same UTC day and confirm the skip, then confirm --force records a second attempt. Two external risks are not gates you can close once: the RSS endpoint can return 404 again next week, and a cloud IP can start being blocked. The design response is not "make the network reliable"; it is "keep the failure local, keep last-good state, and report what happened."

And two phases from the brief are simply not code yet. The scheduler and the second source kind are the difference between "a pipeline I run" and "an aggregator that runs itself." Leaving them on the scorecard as not built is what makes the finished rows credible.

What this project demonstrates is different from the capstone and worth having in a portfolio for that reason. It shows that you can build a batch data product with a real side effect, bound an LLM prompt, validate model output, keep ingestion idempotent, and distinguish a failed send from a successful one. The code is small; the honesty about the two fragile sources is the senior part.

Part 13 — The project checklist

  1. Write the checklist first, and put the deferrals in it: the scheduler, extra source kinds and per-user profiles are named phases with acceptance checks, not silent omissions.
  2. Fix the project structure before writing modules: all logic in app/, infrastructure in docker/, and dependencies pointing one way.
  3. Treat RSS 404 as transient: isolate the channel, keep its rows, keep it active, report the failure, exit non-zero.
  4. Build against a fixture before the live feed. The parser and upsert contract should be testable with no network.
  5. Make transcripts optional. Prefer them, fall back to the RSS description, and store which one was used.
  6. Let Alembic own the schema. Change a constraint in a reviewed revision when product behavior requires it.
  7. Upsert by stable external IDs, and whitelist the columns a refresh may overwrite. Never erase a transcript with RSS metadata.
  8. Bound the prompt by characters, label truncation, and derive the URL allowlist from exactly the articles that fit.
  9. Parse model output strictly. Reject unknown URLs, duplicate entries and missing articles before rendering.
  10. Escape all model- and article-provided text; never let the model emit HTML.
  11. Gate email behind an explicit flag, record every attempt, and know the difference between at-most-once and exactly-once.
  12. Schedule last. Add a lock, per-source fetch history and an alert before you hand the run to cron.
