Ollama + LlamaIndex: A Local RAG Agent, No API Key

The cloud is a dependency: a key, a bill, a rate limit, and a network. A local model is a file and a process. This lesson installs Ollama, uses Qwen3 4B Instruct as a small non-thinking model, and builds the same RAG shape from lesson 7 with LlamaIndex — embeddings, vector store, chat, and sources all on your machine.

Your win this lesson You'll install and verify Ollama, pull qwen3:4b-instruct plus a 274 MB embedding model, ingest 20 reviews into a local Chroma index with LlamaIndex, and ask grounded questions with source titles. You'll also know which model to pick for 8, 16 or 32 GB of RAM, and when local is the wrong trade.

Part 1 — What Ollama actually is

Ollama is not a model. It is a local server and model manager: it downloads quantized weights, loads them into RAM or VRAM, exposes an HTTP API on 127.0.0.1:11434, and unloads a model after an idle period. The CLI is a client for that server.

piecewhat it does
ollama pulldownloads a model tag into the local store
ollama runpulls if missing, then starts a chat in the terminal
ollama list / pswhat is on disk / what is loaded in memory
ollama servestarts the API server (the desktop app does this for you)
POST /api/chat, /api/embedthe endpoints LlamaIndex uses under the hood

It is the easiest local runtime, not the fastest at scale. vLLM wins for batched GPU serving, llama.cpp is the engine underneath many tools, and a cloud API still wins on quality. For a laptop RAG prototype, Ollama is the shortest path from a model name to a working endpoint.

Part 2 — Install and verify

Windows (PowerShell):

winget install Ollama.Ollama
# or download the installer from https://ollama.com/download
ollama --version
ollama list

macOS: download the app from ollama.com/download (or brew install ollama). The app runs the server in the background.

Linux:

curl -fsSL https://ollama.com/install.sh | sh
sudo systemctl status ollama

The server listens on http://localhost:11434. Check it directly:

curl http://localhost:11434/api/tags

Do not expose that port. Ollama has no authentication; OLLAMA_HOST=0.0.0.0 publishes an open model server to your network. Keep it on loopback, or put an authenticated proxy in front of it.

Part 3 — Pick a small model that fits your machine

The original lab used llama3.2 (September 2024). It still runs, but the small-model class moved. For this RAG lab the default is qwen3:4b-instruct: the non-thinking Qwen3 4B Instruct variant (~2.5 GB, 256K context). It answers directly instead of emitting a reasoning trace first, which is what a grounded Q&A pipeline wants.

chat modeldownloadpick it when
qwen3:4b-instruct~2.5 GBdefault here: non-thinking, fast, 256K context, fits an 8 GB machine
qwen3.5:4b~3.3–4.0 GBnewer Qwen, vision + tools; the upgrade on a 16 GB machine
qwen3.5:2b~2.7–3.1 GB8 GB laptop; a little weaker than 4B
qwen3.5:0.8b~1.2–1.3 GBlow RAM or a smoke test; shallow answers
qwen3:4b~2.5 GBQwen3 4B with thinking mode; slower for RAG
phi4-mini~2.5 GBreasoning and maths over chat; text only
llama3.2:3b~2.0 GBthe original lab's model; fast and familiar, older

Embedding models are a separate pick, and size matters less because they are small:

qwen3-embedding:0.6b~639 MB1024newer, 32K context, multilingual — the upgrade

ollama pull qwen3:4b-instruct
ollama pull nomic-embed-text
ollama list
ollama show qwen3:4b-instruct   # context, parameters, quantization

How to choose by RAM: 8 GB → qwen3:4b-instruct (2.5 GB) or qwen3.5:2b; 16 GB → qwen3.5:4b for the newer model; 32 GB → 4b comfortably, 9b if you need more quality. Quantization (usually Q4) is why a 4B model fits in 2.5–4 GB; ollama show tells you what you actually downloaded.

Do not judge by the publisher's benchmark. Pull two candidates and run the same ten questions from your corpus. Latency and groundedness on your data decide, not a leaderboard.

Part 4 — The local RAG pipeline

This is lesson 7's shape with the cloud swapped out. Ollama serves both models; LlamaIndex owns the documents, the index, and the retrieve-then-synthesize query engine.

data/reviews.csv
      │  ingest.py
      ▼
LlamaIndex Documents ── OllamaEmbedding(nomic-embed-text) ──▶ Chroma(chroma_db/)
                                                                 │
question ── VectorStoreIndex.as_query_engine(k=4) ───────────────┘
      │
      ▼
Ollama(qwen3:4b-instruct) ──▶ answer + source_nodes

The ingestion side:

documents = [
    Document(
        text=f"{row['Title']}. {row['Review']}",
        metadata={"title": row["Title"], "rating": int(row["Rating"]), "date": str(row["Date"])},
    )
    for _, row in frame.iterrows()
]

collection = chromadb.PersistentClient(path="chroma_db").get_or_create_collection("nimbus_reviews")
vector_store = ChromaVectorStore(chroma_collection=collection)
storage = StorageContext.from_defaults(vector_store=vector_store)
VectorStoreIndex.from_documents(documents, storage_context=storage)

The query side:

Settings.embed_model = OllamaEmbedding(model_name="nomic-embed-text")
Settings.llm = Ollama(model="qwen3:4b-instruct", temperature=0)

index = VectorStoreIndex.from_vector_store(vector_store)
engine = index.as_query_engine(similarity_top_k=4)
response = engine.query(question)
print(response.response)
for node in response.source_nodes:
    print(node.metadata["title"])

Settings.embed_model and Settings.llm are process-wide: configure them once at startup. The query engine is LlamaIndex's retrieve-then-synthesize pipeline; response.source_nodes is the evidence list you print.

The one rule that bites everyone: use the same embedding model for indexing and querying. Vectors from different models do not share a space; changing OLLAMA_EMBED_MODEL means deleting the store and re-ingesting. The chat model can change freely.

Part 5 — Run it

cd assets\examples\0014-ollama-local-rag
uv sync
Copy-Item .env.example .env         # first time only

uv run python ingest.py
uv run python ask.py "Is the gluten-free pizza good?"

ingest.py embeds all 20 reviews once. ask.py builds a LlamaIndex query engine over the index, retrieves four reviews, and calls the local model. Both scripts preflight the server and print the exact ollama pull command if a model is missing, so the failure mode is a fix, not a traceback.

Expected shape of the answer:

querying 4 local chunks with qwen3:4b-instruct ...

Yes - one reviewer calls the gluten-free base "the best I have had locally"
and notes that it does not fall apart and is cooked on a separate tray
[Great gluten-free option].

sources:
  [Great gluten-free option] rating=5 2026-09-14
  [Staff know the menu] rating=5 2026-10-14
  [Great lunch special] rating=5 2026-10-23
  [Best crust in town] rating=5 2026-09-02

The source list is the verification surface. A grounded answer cites reviews you can open; an ungrounded one is a fluent guess. If the reviews do not contain the answer, the prompt tells the model to name the gap instead of inventing one.

Part 6 — Local vs cloud is a trade, not a religion

constraintlocal winscloud wins
privacydata never leaves the machineonly with a contract and a DPA
offlineworks on a plane or an air-gapped boxneeds a network
cost at low volumeone download, no per-token billpay only for what you use
quality4B is not a frontier modelfrontier quality per token
latencyno network hop, but CPU/GPU boundfast, with a network hop
operationsyou own the model files and the hostthe provider owns uptime

Hybrids are common and sensible: local embeddings plus a cloud chat model (documents stay local, answers get better), or a local model for classification/routing and a cloud model for the final draft. The interface is the same LangChain shape; only the model handle changes.

Part 7 — Operational details that save an afternoon

  • Model load is the first latency. The first call loads weights; later calls reuse them. ollama ps shows the loaded model; OLLAMA_KEEP_ALIVE controls how long it stays.
  • Context costs memory. qwen3:4b-instruct advertises 262K, but asking for all of it allocates a KV cache of tens of GB; LlamaIndex defaults to the model's full context, and llama-server dies with out-of-memory ... failed to allocate buffer for kv cache. common.py sets context_window=4096 (override with OLLAMA_NUM_CTX); 4096 is plenty for a handful of reviews.
  • Disk adds up. Each tag is a full model; ollama rm is the cleanup. A 4B model plus an embedding model is roughly 3 GB.
  • CPU is usable; GPU is better. 15–30 tokens/second on a modern CPU is fine for one user. Concurrency is not Ollama's strength — batch jobs belong on vLLM or a queue.
  • Settings is process-wide. LlamaIndex reads Settings.llm and Settings.embed_model at call time; configure them once at startup, not inside a request handler that changes them per call.
  • Version the model, not just the name. A tag can move. Pin a digest from ollama show in production notes.
