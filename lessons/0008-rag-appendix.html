RAG Appendix: Chunking Tools and Vector Stores

Two decisions outlive the tutorial you copied them from: how the corpus is cut into chunks, and where those chunks are stored. This appendix is the reference for both — the chunking framework, the four tools that do the cutting, and the six stores you are actually choosing between.

Your win this lesson You'll be able to defend a chunk unit and a store from the document type and the ops model, instead of inheriting defaults — and name the tool that parses a PDF properly before anything is embedded.

Part 1 — How to chunk content

Structure first; fixed windows are the fallback. Your documents already know where the seams are — headings, clauses, Q&A pairs, function boundaries, table rows. A chunker that ignores that structure is guessing at boundaries the document already published.

Document typeChunk unitSize guide
Docs / KB articlesheading section100–400 tokens
FAQsone Q + A pair, never splitsmall, atomic
Policies, legalclause / bullet groupparagraph level
Codefunction or classnever mid-function
Tableswhole table + header rownever split a table
Long narrativeparagraph + sliding windowthe fallback

The course default is a 400–600 token budget, because that holds one idea plus the context needed to interpret it. Short atomic units — an FAQ pair, a single clause — legitimately land smaller. The rule is one idea per chunk, not one size for the corpus.

Four rules transfer to every tool:

  • Context promotion. The title and heading path travel inside every chunk, so a paragraph about refunds still knows it sits under Billing → Refunds when retrieved alone.
  • Overlap only where windows slide. Fixed windows get 10–15% overlap as boundary insurance; structure-aware chunks do not need it, because they are not sliding. Dedupe overlap downstream if you keep it.
  • Metadata at write time. Source, page, section, date and tenant are cheap to store now and impossible to reconstruct later. They are what filters run on.
  • Tune on your own questions. Chunk size is an empirical choice: the same document set can prefer different boundaries for different queries.

Three names worth knowing for interviews and design reviews: semantic chunking (split where consecutive embeddings shift), small-to-big (retrieve the small chunk, return its parent section), and late chunking (embed the whole document first, pool into chunks afterwards). None of them replaces structure — they are refinements on top of it.

Part 2 — Tools that chunk

There are two jobs here, and tools differ in which one they do: parsing (bytes → structured text) and splitting (structured text → chunks). Confusing the two is why "PDF chunking" goes badly — a splitter cannot recover a table that the parser already flattened.

ToolInputWhat it gives youReach for it when
DoclingPDF, DOCX, PPTX, XLSX, HTML, Markdownreading order, headings, tables, page anchors, then HybridChunkerthe source is a PDF or Office file, or tables matter
LangChain splittersplain text, Markdown, HTML, coderecursive, header-aware, token-aware splittingthe text is already clean and you want no extra dependencies
LlamaIndex node parsersdocuments / nodessentence, semantic and hierarchical parsing with rich metadatayou want small-to-big retrieval or semantic boundaries
html-to-markdownraw HTMLclean Markdown, GFM tables kept as tablesthe corpus is a website, help centre or CMS export

Docling: parse and chunk in one pass

Docling is the only tool in this list that does both jobs on a PDF. It walks the document hierarchy, keeps tables intact and reports page anchors, then HybridChunker merges small neighbours up to the token budget and starts a new chunk at a heading:

from docling.chunking import HybridChunker
from docling.document_converter import DocumentConverter

doc = DocumentConverter().convert("handbook.pdf").document
chunker = HybridChunker(max_tokens=512, merge_peers=True)
chunks = list(chunker.chunk(dl_doc=doc))
text = chunker.contextualize(chunks[0])   # heading path + chunk text

Cost: it is the heaviest dependency in this appendix — PyTorch plus layout models, and a first run measured in tens of seconds. That is the price of reading a two-column PDF correctly.

LangChain splitters: cheap, format-blind, already installed

LangChain splits text you have already extracted. It does not parse a PDF. Its character-based default is the trap: chunk_size=1200 means 1200 characters, not tokens.

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1200,          # characters, not tokens
    chunk_overlap=180,        # ~15%
    separators=["\n## ", "\n\n", "\n", " "],
)
chunks = splitter.split_text(markdown)

If the text is Markdown with real headings, MarkdownHeaderTextSplitter splits on the heading hierarchy and keeps the headers as metadata — the cheapest way to get context promotion without a parser. TokenTextSplitter exists when you want the budget counted in tokens instead of characters.

LlamaIndex node parsers: metadata and small-to-big

LlamaIndex wraps splitting into nodes that carry relationships to their neighbours and parent. That is what makes small-to-big retrieval a configuration rather than a project:

from llama_index.core.node_parser import (
    SentenceSplitter, HierarchicalNodeParser,
)

nodes = SentenceSplitter(chunk_size=512, chunk_overlap=50).get_nodes_from_documents(docs)
parents = HierarchicalNodeParser.from_defaults(
    chunk_sizes=[2048, 512, 128]
).get_nodes_from_documents(docs)

SemanticSplitterNodeParser is also here, and it is the honest way to try semantic chunking: it embeds adjacent sentences and cuts where similarity drops. Expensive, corpus-specific, and worth measuring before adopting.

html-to-markdown: fix the HTML before you split it

Help centres, docs sites and CMS exports are HTML. Feeding raw tags to a splitter produces chunks full of navigation and attributes. Convert first, then split the Markdown with any of the tools above:

from html_to_markdown import convert

result = convert(raw_html)      # .content is Markdown, .metadata is page metadata
markdown = result.content       # tables come out as GFM tables

It repairs real-world markup — unclosed tags, nested tables, broken entities — which is most of what a scraper actually captures. The output is Markdown, so MarkdownHeaderTextSplitter or Docling's Markdown path can take it from there.

Which one

  1. PDF, DOCX, PPTX, or tables that matter → Docling. Parse and chunk together; do not hand its output to a blind splitter.
  2. Already-clean Markdown or plain text → LangChain splitters. Keep the heading splitter, not the character one, when headers exist.
  3. You need parent/child retrieval → LlamaIndex node parsers. The hierarchy is built in.
  4. The source is a web page → html-to-markdown first, then whichever splitter matches the result.

Part 3 — Selecting a vector database

The first distinction is not a benchmark: who runs it. Four families cover almost every real decision, and the family decides your ops life before features enter the conversation.

FamilyWhat it isWins whenWatch out for
Chromaembedded; a folder on diskdev, prototypes, notebooks — zero ops, one line to startvector-only (no BM25 ranking); one writer; not multi-pod
Qdrantself-hosted serverproduction with rich filtering and hybrid (dense + sparse) in one querya service to deploy, secure, back up and keep alive
pgvectorPostgres extensionyou already run Postgres: a vector column beside your rows, one system to operateyou now tune Postgres for vectors too; hybrid needs tsvector + fusion in SQL
Pinecone / managedSaaSthe team has no infra appetite and will pay per usagecost at scale, vendor lock-in, data leaves your network

Two more are worth naming because they keep coming up:

OptionWhat it really isPick it when
Supabasemanaged Postgres + pgvector, with auth, storage and a dashboard on topyou want a backend as a service and vectors in the same database as your app rows
LanceDBembedded columnar store with BM25 and vectors in one tablelocal-first or edge, and you want hybrid search without running two systems — it is what lesson 7 uses

Rule of thumb: Chroma while learning → Qdrant or pgvector in production → managed when you refuse to own the ops. Supabase is the pgvector branch with a dashboard attached; LanceDB is the embedded branch that also gives you BM25.

Pick by constraint, not by feature matrix

Your situationStart withWhy
Following this course, one machineLanceDBone table, vectors + BM25, no service to run

Three questions settle most arguments. Is the store rebuildable from documents? If yes, it is an index and can be simple; if it is the system of record, durability and backups decide. Does retrieval need exact terms? Then the store must rank text (BM25), not merely filter it — Chroma cannot, LanceDB and Qdrant can, pgvector can with tsvector. How many writers? Embedded stores have one; that limit, not vector count, is what forces the move to a server.
