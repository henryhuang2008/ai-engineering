Memory in Agents — When to Use Short-Term and Long-Term Memory

An agent has two kinds of memory, and they answer different questions. Short-term memory answers “what did we say a minute ago?” inside one conversation. Long-term memory answers “what do I know about this user from last week?” across conversations. This lesson explains when each one is worth building, walks the example in assets/examples/0019-memory-agents-langgraph, and moves both into PostgreSQL.

Your win this lesson You can decide which memory a feature needs, run the example's three demos without a database, explain what happens on one turn, and wire PostgresSaver and PostgresStore so both memories survive a restart.

Part 1 — Short-term memory: when and why

Short-term memory is the conversation. It is the list of messages for one thread_id, saved by a checkpointer after every step and reloaded on the next turn.

Use it when the next turn depends on an earlier turn:

  • follow-ups: “what about the second one?”, “make it shorter”;
  • iterative work on one artifact — a draft, a query, a plan;
  • multi-step forms or debugging, where answers build on each other;
  • any chat where the user expects the agent to remember the session.

Skip it when the task is one-shot:

  • classify this text, translate this page, extract these fields;
  • independent requests that never refer to each other;
  • cases where your application already builds the prompt from its own data.

The reason to use a checkpointer rather than a list in your own code is simple: the model is stateless between requests. Something has to resend the history, and the checkpointer does it per thread, including on a restart when the backend is PostgreSQL. 

graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "thread-1"}}
graph.invoke({"messages": [HumanMessage("Hi, my name is Alice")]}, config)

Two thread ids, one graph, two histories. The cost is that the stored thread grows forever, while the prompt cannot. Part 6 covers the fix: store everything, send a bounded window.

Part 2 — Long-term memory: when and why

Long-term memory is the user. It is a small set of facts kept in a store under a user_id, readable from any conversation.

Use it when a fact should outlive the conversation:

  • identity and role: “I'm a data scientist”;
  • preferences: language, tone, tools, formats;
  • constraints: timezone, accessibility needs, budget;
  • ongoing projects and decisions the user will refer to again.

Do not use it when:

  • an authoritative profile database already holds the fact — read it there;
  • the user has not agreed to have personal data stored;
  • facts change often and you have no conflict-resolution rule;
  • the information only matters for the current session.

The reason short-term memory is not enough: a new thread starts empty. The reason a long system prompt is not enough: it goes stale, grows with every user, and cannot answer “what do I know about this one person?” 

namespace = (user_id, "facts")
key = sha256(normalised_text)[:16]

store.put(namespace, key, {"fact": text, "thread_id": thread_id})
store.search(namespace, limit=5)
store.delete(namespace, key)

Two details make this last: the key is a hash of the text, so re-extracting the same fact overwrites instead of duplicating, and the namespace is the user, so one person's facts never leak into another's. A delete path is part of the design, not an afterthought.

Part 3 — The example, and how to run it

The example is small enough to read in one sitting:

app/
├── stm.py        # message graph + checkpointer; thread isolation
├── history.py    # trim, summarize with RemoveMessage, delete
├── ltm.py        # namespace store, extraction, dedupe, recall, forget
├── graph.py      # compress → retrieve → agent → extract
├── postgres.py   # PostgresSaver + PostgresStore over one pool
├── config.py     # env settings
└── cli.py        # demo | facts | chat | forget

Run it from the example folder:

uv sync
Copy-Item .env.example .env      # set OPENAI_API_KEY; macOS/Linux: cp

uv run python main.py demo       # short-term: two threads
uv run python main.py facts      # long-term: two threads, one user
uv run python main.py chat       # both, interactive
uv run pytest -q                 # 19 passed

demo is the short-term test. Alice talks on thread-1, Bob on thread-2:

thread-1: "Hi! My name is Alice" → "What's my name?" → "Remind me my name"
thread-2: "Hi! My name is Bob"   → "What's my name?"

thread-1 messages stored: 6
thread-2 messages stored: 4

Bob is never called Alice, and Alice's third turn still knows her name. The only difference between the two runs is the thread_id.

facts is the long-term test. One user, user-alice, in two different threads:

thread A: "I'm a data scientist working in Python and machine learning."
stored facts: ['Works as a data scientist',
               'Uses Python for data science work',
               'Works with machine learning']

thread B: "What should I focus on learning next?"
bot> ... advice that uses the role and the stack ...

Thread B has no messages of its own, but the answer is personalized. The facts were written under the user, not the thread.

chat asks for a user id and a thread id, then runs the combined graph. Use the same user with a new thread to see recall, and the same thread to see the conversation continue.

Part 4 — What happens on one turn

The combined graph has four nodes:

START → compress → retrieve → agent → extract → END
node reads writes
compress the stored messages, when they pass the token threshold summary, plus removals for the old messages
retrieve user_id and the newest human message memory_context — the facts, one per line
agent system prompt, facts, summary, trimmed message window the assistant reply
extract the newest human message and the thread_id new facts under the user's namespace

In the facts demo, the first turn runs with memory_context set to (nothing yet). It answers, then extract asks the model for durable facts and writes three of them. The second turn, in a different thread, runs retrieve first, so the prompt already contains the role and the stack before the model sees the question.

Two implementation details are easy to miss. Every state key a node writes must be declared on the state class — an undeclared key is dropped without an error, so a retrieval node can appear to work while changing nothing. And the store is passed at compile time with compile(store=store), not read from a module global: 

class MemoryState(MessagesState):
    user_id: str
    memory_context: str
    summary: str

graph = builder.compile(checkpointer=checkpointer, store=store)

Part 5 — Put both memories in PostgreSQL

InMemorySaver and InMemoryStore lose everything when the process exits. PostgreSQL keeps both, and the graph code does not change — only the two objects you construct.

Start the database:

docker compose -f docker/docker-compose.yml up -d
psql "postgresql://postgres:postgres@localhost:5432/agent_memory" \
  -c "CREATE EXTENSION IF NOT EXISTS vector;"

Set DATABASE_URL in .env, then construct both objects over one shared pool: 

pool = ConnectionPool(conninfo=DATABASE_URL, kwargs={"autocommit": True})

# short-term: conversation state, keyed by thread_id
checkpointer = PostgresSaver(conn=pool)
checkpointer.setup()

# long-term: facts, keyed by namespace and key
store = PostgresStore(conn=pool)
store.setup()

graph = builder.compile(checkpointer=checkpointer, store=store)

setup() creates the tables on first run and can stay in the startup path. The checkpointer writes checkpoints, checkpoint_blobs and checkpoint_writes. The store writes store, plus store_vectors when you configure an index.

Run any command against the database with the flag before the subcommand:

uv run python main.py --postgres facts
uv run python main.py --postgres chat
uv run python main.py --postgres forget user-alice

The test that matters: run --postgres facts, stop the process, run it again. The second process reloads the thread from the first, so the opening answer already knows the earlier conversation. That is the difference between persistence and a cache. Then forget deletes the user's facts — long-term memory without a delete path is a privacy problem.

Semantic recall is separate: pass an index to the store, with an embedder and matching dimensions. Without one, search(query=...) accepts the query and ignores it, returning score=None. DeepSeek serves no embeddings, so the example's semantic mode uses Qwen text-embedding-v4 at 1536 dimensions.

This path is a gate, not a claim No Docker daemon was available on this machine, so the PostgreSQL code above is read from the library source and the project's own module, not measured here. The example marks it not verified. Running the two commands and the restart test is the evidence.

Part 6 — What breaks

symptom cause fix
the prompt keeps growing the checkpointer stores every message; the model gets all of them trim by tokens before calling the model; summarize what falls out
the summary appears twice, or the recent window duplicates a node returns [summary] + recent; the reducer merges by id remove old messages with RemoveMessage and keep the summary in its own key
the retrieval node changes nothing it writes a state key the state class does not declare declare every written key; LangGraph drops the rest silently
semantic search returns everything with score=None no embedding index on the store build the store with an index and an embedder, or label the result unranked

Part 7 — What was verified

  • Live, short-term: DeepSeek deepseek-chat ran demo; Alice and Bob stayed separate, with 6 and 4 messages stored.
  • Live, long-term: facts extracted three facts and reused them in a new thread for the same user.
  • Semantic recall: Qwen text-embedding-v4, 1536 dimensions, returned ranked results with real scores.
  • Offline: 19 tests pass with no network, no database and no key.
  • Not verified: the PostgreSQL path (no Docker daemon), fact-quality evals, TTL and conflict resolution.
