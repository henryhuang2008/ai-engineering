Memory That Survives the Conversation — Short-Term, Long-Term, and the Scope Mistake

“Memory” is two different systems wearing one word. Short-term memory is the conversation: a message list tied to a thread, bounded by tokens, forgotten when the thread ends unless something checkpoints it. Long-term memory is the user: facts in a store, retrieved by meaning, shared across every thread. Build the first and call it the second — or the reverse — and the agent fails in ways that look like model problems. This lesson takes a popular LangGraph memory guide, runs its architecture, and fixes the five places where its code does not do what its prose says.

Your win this lesson You'll be able to separate thread scope from user scope, wire a checkpointer and a store into one graph, bound a growing conversation with trimming and summarization, write long-term facts idempotently and delete them on request, and tell the difference between a semantic search and a prefix listing that happens to accept a query.

Part 1 — Two memories, two scopes

The article's central distinction is correct and worth stating before any code:

Short-term memory Long-term memory
scope one thread_id one user_id, across threads
mechanism checkpointer store with namespaces
holds messages, intermediate state facts, preferences, history
retrieval load the thread lookup or similarity search
growth unbounded unless managed unbounded by design; curated
lifetime the conversation until deleted

The failure mode is a scope mistake. Store the conversation in the user scope and every thread inherits every other thread's small talk. Store facts in the thread scope and the agent forgets your name the moment you open a new chat. The two systems need different identifiers, different lifetimes and different deletion rules.

Everything below is implemented in Example 0019, The section-by-section notes list every deviation.

Part 2 — Short-term memory is the checkpointer

LangGraph does not give you a memory object for conversations. It gives you a checkpointer: a component that saves the graph state after every step and reloads it for a given thread. The identifier is not the user; it is the conversation. 

config = {"configurable": {"thread_id": "thread-1"}}

builder = StateGraph(MessagesState)
builder.add_node("agent", agent)
builder.add_edge(START, "agent")
builder.add_edge("agent", END)

graph = builder.compile(checkpointer=InMemorySaver())

MessagesState is smaller than the article claims. It contains one field, messages, annotated with the add_messages reducer: 

class MessagesState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

The article's comment says it also includes user_input: Optional[str]. It does not. That matters, because the same article later adds user_id by subclassing — which is exactly the right move, and the earlier comment hides it.

The reducer is the other half. add_messages appends new messages, updates existing ones by id, and honours RemoveMessage deletions. You never manually rebuild the list.

Part 3 — Thread isolation, demonstrated

The article's Alice and Bob demo is a good test because it fails loudly if the scope leaks. Two threads, same graph, nothing shared: 

send(graph, "thread-1", "Hi! My name is Alice")
send(graph, "thread-2", "Hi! My name is Bob")
send(graph, "thread-1", "What's my name?")   # Alice, not Bob

Under the hood, the second call on thread-1 reloads the first two messages plus the new one. The example asserts the exact counts: the model sees 1 message on the first call, 3 on the second, 5 on the third. If those numbers drift, the checkpointer is not doing its job.

What the checkpointer does not do It does not summarise, trim or rank. It faithfully stores a growing list. That is the next problem.

Part 4 — Persistence: the same contract, a different backend

InMemorySaver loses everything when the process exits. PostgresSaver keeps it, and the graph code does not change — only the checkpointer does: 

pool = ConnectionPool(conninfo=DATABASE_URL, kwargs={"autocommit": True})
checkpointer = PostgresSaver(conn=pool)
checkpointer.setup()          # creates its tables once
graph = builder.compile(checkpointer=checkpointer)

Three details decide whether this works in production. The pool is shared, not created per request. setup() runs once, not on every call. And the thread_id must be stable across restarts — if your web app generates a new thread id per session, persistence buys you nothing.

Gate: start the pgvector container in docker/, run the same thread id from a new process, and confirm the history is there. The example marks this unverified: no Docker daemon was available in this build, so the PostgreSQL path is a documented gate, not a claim.

Part 5 — Bounding short-term memory

A checkpointer stores everything. The prompt cannot. Three strategies, and the article's code gets two of them wrong.

strategy what it costs when to use
trim to a token budget loses old context entirely fast, predictable, most chats
delete by id fine-grained; easy to over-delete removing noise or a specific turn
summarize the old window one extra model call; summary loses nuance long, quality-critical conversations

Trimming is the safest default:

trimmed = trim_messages(
    messages,
    strategy="last",
    token_counter=count_tokens_approximately,
    max_tokens=MAX_CONTEXT_TOKENS,
    start_on="human",
)

The article's delete helper is wrong twice. It computes to_remove = msgs[-keep_count:], which selects the newest messages, and then returns {"messages": msg}, where msg is undefined. The import is wrong as well: RemoveMessage lives in langchain_core.messages, not langchain.messages. The corrected form is explicit: 

def delete_messages(message_ids):
    return [RemoveMessage(id=message_id) for message_id in message_ids]

Summarization has a subtler bug. The article returns {"messages": [summary] + recent} from a node. add_messages does not replace the list — it merges. Messages that already exist are updated in place, and the summary lands wherever the merge puts it, which is not the front. The recent window gets re-added as duplicates. The fix is to remove the old messages and keep the summary in its own state key: 

def summarize_history(messages, model, *, keep_last=6, threshold_tokens=3000):
    if count_tokens_approximately(messages) < threshold_tokens:
        return None
    old, recent = messages[:-keep_last], messages[-keep_last:]
    transcript = "\n".join(f"{m.type}: {m.content}" for m in old)
    summary = model.invoke([{"role": "user", "content": SUMMARY_PROMPT + transcript}])
    removals = [RemoveMessage(id=m.id) for m in old if m.id]
    return str(summary.content), removals

Then the agent builds its prompt as system + summary + trimmed window. The checkpointer still holds the full thread; only the prompt is compressed. That separation — stored vs visible — is the point.

Part 6 — Long-term memory is a store, not a transcript

A store is a key-value system with namespaces. The namespace is how you scope by user, and the key is how you make writes idempotent. 

namespace = (user_id, "facts")

store.put(namespace, key, {"fact": "Works as a data scientist", "thread_id": "t1"})
store.get(namespace, key)
store.search(namespace, limit=5)
store.delete(namespace, key)

Two design choices matter more than the API:

  1. The key. The article uses str(uuid.uuid4()) for every extracted fact. Extract the same fact twice and you store it twice. Hashing the normalised text makes the write idempotent: sha256("works as a data scientist")[:16] is the same key forever.
  2. The delete path. Personal facts need an erase route from day one. The example ships forget_user and a CLI command; the article has no deletion story at all.

Part 7 — Semantic search is a property of the index

This is the most expensive misunderstanding in the article. It creates a plain InMemoryStore, calls store.search(query=...), and describes the result as semantic retrieval. Without an embedding index, LangGraph accepts the query and ignores it. Every item comes back with score=None. 

>>> store.search(("user", "facts"), query="what is their job", limit=5)
[Item(..., score=None)]

That is not a bug; it is the documented contract. To get ranking, build the store with an index and an embedder: 

store = InMemoryStore(index={
    "dims": 1536,
    "embed": embeddings,
    "fields": ["fact"],
})

Which raises the practical problem the article never mentions: the model you use for chat may not serve embeddings. DeepSeek does not. A working setup needs a second provider, a second key and a dimension that matches the model. The example makes this optional and reports which mode it is in rather than pretending.

Part 8 — Writing memory: extract, dedupe, delete

Long-term memory is not a log. It is a curated set of facts, which means three operations, not one.

Extract. Ask for a JSON array of durable facts and parse it defensively — models wrap JSON in prose. Cap the number and the length. The example allows three facts per turn and 240 characters each.

Dedupe. Normalise case and whitespace, hash the text, use the hash as the key. A repeat becomes a no-op instead of a duplicate.

Delete. Namespace-scoped deletion, exposed to the operator. This is the difference between a demo and something you can run for real people.

What the example does not do, and the lesson does not pretend: no confidence score, no expiry, no conflict resolution when the user changes jobs. Those are the next three items on its list.

Part 9 — The combined graph

The article's final finance agent wires retrieval, generation and extraction into one graph. The shape is right and the wiring is not. 

START → compress → retrieve → agent → extract → END
  • compress summarises the old window and stores the summary in state.
  • retrieve reads the user's facts and writes memory_context.
  • agent builds system + summary + trimmed messages and calls the model.
  • extract pulls new facts from the human turn and writes them to the store.

Two corrections are structural. First, memory_context must be declared on the state class — the article returns an undeclared context key, which LangGraph silently drops, so its retrieval node has no effect and the agent re-reads the store itself. Second, the graph should be compiled with store=store, not close over a module global; the dependency should be visible at the edge. 

class MemoryState(MessagesState):
    user_id: str
    memory_context: str
    summary: str

graph = builder.compile(checkpointer=checkpointer, store=store)

Notice what stays out of the store: the conversation. The store holds facts; the checkpointer holds the thread. The graph reads both and writes each to the right one.

Part 10 — What breaks at scale

Memory is the part of an agent that degrades quietly. Four failure modes worth naming:

  1. Token growth — the stored thread is unbounded. Trim what the model sees, compress what you keep, and measure the prompt size, not the message count.
  2. Cost — summarization adds a model call per compression. At scale that is a real line item; batch it or run it on a cheap model.
  3. Bad facts — extraction asks a model what is worth remembering. It will save preferences as facts and guesses as history. There is no eval in the example for fact quality, and that is the honest gap.
  4. Privacy — a user namespace is not a deletion policy. Decide retention, export and erase before the first real user, not after the first request.

The article is a solid tour of the architecture and a weak source of runnable code. That is normal for a 20-minute guide, and it is why the rebuild matters: the difference between “I read about checkpointer and store” and “I can show you the test that proves thread isolation” is the difference an interviewer hears.

Part 12 — The checklist

  1. Name the scope before the mechanism: thread_id for the conversation, user_id for the person.
  2. Put the checkpointer on the graph, not in a module global.
  3. Treat the stored thread and the visible window as two different things.
  4. Trim by tokens, not by message count; start the window on a human turn.
  5. Summarize by removing old messages and storing the summary in its own key.
  6. Declare every state key a node writes; undeclared keys are dropped silently.
  7. Key facts by content hash so extraction is idempotent.
  8. Pass a query only when the store has an embedding index; otherwise say “unranked”.
  9. Ship a delete path with the first fact you store.
  10. Test the failure the demo hides: a second thread, a second user, a restart.
