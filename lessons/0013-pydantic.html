Pydantic: Make Bad Data Fail at the Boundary

Every AI bug you cannot reproduce starts as an unvalidated dict. Pydantic is the contract layer: it decides what a Ticket is, refuses anything else, and gives the same schema to FastAPI, your database code, and the model. This lesson builds that layer from one model to a validated DeepSeek reply.

Your win this lesson You'll build a model, tighten it with field and model validators, nest it, generate its JSON Schema, load typed settings from the environment, and parse a live DeepSeek extraction into the model. You'll also leave with the five habits that keep validation at the boundary instead of scattered through the code.

Part 1 — A dataclass stores; a model checks

Python's type hints are documentation until something enforces them. A @dataclass generates an __init__ and stops there:

@dataclass
class DataUser:
    name: str
    age: int

raw = DataUser(name="Alice", age="not a number")
print(raw.age)          # "not a number" - no complaint

A Pydantic BaseModel looks the same and behaves differently: it validates on construction, coerces only when the type allows it, and raises a structured error otherwise.

class User(BaseModel):
    name: str = Field(min_length=1, max_length=50)
    age: int = Field(ge=0, le=120)
    email: EmailStr | None = None

User(name="Alice", age="not a number")
# ValidationError: Input should be a valid integer

User(name="Alice", age="25").age   # 25, an int - coercion is allowed

That coercion is a feature at a boundary: form data and JSON often send numbers as strings. It is not a license to be vague — ConfigDict(strict=True) turns it off when you need exact types. (EmailStr needs the email-validator package; the lab's pyproject.toml includes it.)

model_validate versus Model(**data): both construct; model_validate takes the dict as one value and exposes options. Use **data in small scripts, model_validate at a real boundary where the payload arrives as a dict.

When validation fails, read the errors as data rather than as a stack trace:

try:
    User(name="", age=41)
except ValidationError as error:
    for item in error.errors():
        print(item["loc"], item["type"], item["msg"])

# ('name',) string_too_short String should have at least 1 character

loc is the path — the field, a list index, or a nested model. That path is usually the whole debugging session.

Part 3 — Constraints first, validators second

Most rules are declarative. Field puts them in the type, the JSON Schema, the FastAPI docs, and the error message at once:

class Signup(BaseModel):
    username: str = Field(min_length=3, max_length=20)
    plan: Literal["free", "team", "enterprise"]
    seats: int = Field(default=1, ge=1, le=500)
constraintfor
gt, ge, lt, lenumber ranges
min_length, max_lengthstrings and lists
patternregex on a string
EmailStr, HttpUrlthe formats you would otherwise hand-check
Literal[...]a closed set of labels — routes, statuses, categories

Use a field_validator for business logic one field can see; use a model_validator when the rule spans fields:

class Signup(BaseModel):
    username: str

    @field_validator("username")
    @classmethod
    def no_spaces(cls, value: str) -> str:
        if " " in value:
            raise ValueError("username cannot contain spaces")
        return value.lower()


class DateRange(BaseModel):
    start: int
    end: int

    @model_validator(mode="after")
    def ordered(self) -> "DateRange":
        if self.start > self.end:
            raise ValueError("start must be <= end")
        return self

A validator returns the value to accept it, or raises ValueError to reject it. Returning a transformed value (lowercased, stripped) is the quiet superpower: the model normalizes on the way in, so no other code has to remember.

Part 4 — Nested models and lists

Real payloads are nested. Use a model as a field type and Pydantic validates the whole tree:

class Address(BaseModel):
    city: str
    country: str

class Customer(BaseModel):
    name: str
    address: Address

class LineItem(BaseModel):
    sku: str
    quantity: int = Field(ge=1)
    unit_price: float = Field(ge=0)

class Order(BaseModel):
    order_id: str = Field(pattern=r"^ORD-\d+$")
    customer: Customer
    items: list[LineItem]
    note: str | None = None

order = Order.model_validate(payload)
order.customer.address.city     # Amsterdam
order.items[0].sku              # WIDGET

model_dump() recursively converts nested models to dicts; model_dump_json() does the same to a JSON string. If you need to validate a bare list without a wrapper, use TypeAdapter(list[LineItem]).

The schema is a public artifact. Order.model_json_schema() lists the required fields, the nested $defs, and every constraint. FastAPI publishes it as OpenAPI; LangChain hands it to a model as a tool schema. You write the model once and three systems consume it.

Part 5 — Settings: fail at boot, not at the first request

os.getenv returns str | None. Every service ends up with a pile of manual casts and defaults — or a crash when a typo reaches production. pydantic-settings makes configuration a model:

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_prefix="APP_", env_file=".env", extra="ignore"
    )

    api_key: SecretStr
    database_url: str
    max_retries: int = Field(default=2, ge=0, le=5)
    debug: bool = False

settings = Settings()   # APP_API_KEY, APP_DATABASE_URL, ...

Field names map to uppercase environment variables; the prefix avoids collisions. Types are converted ("true" to True, "8080" to 8080), constraints apply, and a missing required value raises at import time. SecretStr prints as **********; call get_secret_value() only where the client needs it.

Wrap the loader in @lru_cache so the process parses the environment once. In production the values come from the platform's secret store, not a committed .env.

Part 6 — Structured output: the schema is the prompt

This is where Pydantic earns its place in an AI application. Define the object you want; LangChain converts it to a tool schema; DeepSeek calls that tool; Pydantic validates the arguments:

class Ticket(BaseModel):
    order_id: str = Field(description="Order id, for example A-1042")
    category: Literal["billing", "technical", "other"] = Field(
        description="billing for money, technical for product failures"
    )
    urgency: int = Field(ge=1, le=5, description="1 low, 5 urgent")
    wants_refund: bool = Field(description="True only if a refund is requested")
    summary: str = Field(description="One sentence, using only facts in the message")

extractor = model.with_structured_output(Ticket, method="function_calling")
ticket = extractor.invoke([SystemMessage(content=SYSTEM), HumanMessage(content=TEXT)])

Real run from the lab:

type:    Ticket (validated instance)
order:   A-1042
route:   billing
urgency: 5
refund:  True
summary: Order A-1042 was charged twice this month and the customer wants a refund today.

as JSON:
{
  "order_id": "A-1042",
  "category": "billing",
  "urgency": 5,
  "wants_refund": true,
  "summary": "Order A-1042 was charged twice this month and the customer wants a refund today."
}

Three things make this reliable. Descriptions are prompt text — they tell the model what "urgency" means. Literal is a closed set — the model cannot return "probably billing". And validation is automatic — you get a Ticket, not a string to parse.

What Pydantic does not do: it checks shape, not truth. A perfectly valid Ticket can still have the wrong order id or an invented summary. That is the eval layer's job (lesson 5). Keep the two separate: validation catches malformed data; evals catch wrong data.

If a provider cannot do native structured output, ask for JSON and call Ticket.model_validate_json(reply). On failure, send the ValidationError back to the model and retry once — a repair loop beats regex. Never hand-parse the prose.

Part 7 — Judgment: where Pydantic stops

situationright tool
an HTTP body, queue message, or LLM replyPydantic model at the edge
environment and secretspydantic-settings + SecretStr
a million rows of numeric workpandas / numpy; validate the boundary, not each row
a stable internal function between two typed functionsplain type hints are enough
a schema that changes weeklya dict at the storage edge, plus a versioned model when it stabilizes

Two small settings worth knowing. ConfigDict(extra="forbid") rejects unknown keys, which is what you want for a strict inbound contract and usually wrong for a forward-compatible API. Field(alias="user_id") maps an external key to a Python field name without renaming your codebase.

Performance is rarely the reason to avoid Pydantic v2: validation is Rust-backed. The real cost is designing the schema, and that cost buys you one place where the shape of the data is decided.

The five habits

  1. Model every boundary: inbound HTTP, outbound LLM JSON, environment. Inside, trust the type.
  2. Declare constraints before writing validators: they appear in the schema and are enforced by every consumer.
  3. Use model_validator for rules that span fields — ranges, totals, refunds.
  4. Load settings once, typed, with SecretStr — fail at boot, not at request 3.
  5. Give the model the same schema you validate with — descriptions and Literal are part of the prompt.
