Function Calling: The Model Asks, Your Code Acts

The name lies. Nothing is called for you. The model requests — your code decides, executes, and reports back. Lesson 2 did one round trip; today you close the loop, and the frameworks that automate it stop being magic.

Your win this lesson You can turn a typed Python function into a tool the model may request (@tool → schema), read that request on AIMessage.tool_calls, execute it yourself, answer with a ToolMessage, and repeat until the model stops asking — under a budget cap. That is the agent loop, hand-written, against live DeepSeek.

The lie in the name

When people say "the LLM called a function," this is what actually happens: the model returns structured text — a tool name plus JSON arguments. Nothing executes on the provider's side. Your code receives that request, decides whether to run it (you are the permission layer), executes the real function, and appends the result as a new message. Then the model is called again to continue. [1]

This is also the birth of the agent loop: call → model requests a tool → execute → observe → call again → until the model answers with plain text. Every LangGraph node, every "agentic" framework, is scaffolding around this loop. Lesson 2 did exactly one of these rounds; today you drive it with LangChain's primitives — @tool, bind_tools(), ToolMessage — so the framework stays transparent instead of magic.

Step 1: declare the tools

You don't hand the model code — you hand it a catalog: name, description, parameter schema. The model never sees your Python; it sees this catalog and decides when a tool fits. LangChain's @tool decorator builds the catalog from the function itself: the type hints become the JSON schema, the docstring becomes the description. These two tools are the components of a support agent: a ticket lookup and a guarded refund.

the tools — a docstring is a prompt

@tool
def get_ticket_status(ticket_id: str) -> dict:
    """Look up the status and plan of a support ticket by its id, for example T-1001."""
    return TICKETS.get(ticket_id, {"error": "unknown ticket"})


@tool
def issue_refund(ticket_id: str, amount_usd: float) -> dict:
    """Issue a refund for a refundable ticket. Check the status first and only
    refund amounts the customer was actually charged."""
    ticket = TICKETS.get(ticket_id)
    if ticket is None:
        return {"error": "unknown ticket"}
    if not ticket["refundable"]:
        return {"error": "ticket not refundable"}
    return {"refunded_usd": amount_usd, "ticket": ticket_id}


TOOLS = [get_ticket_status, issue_refund]
REGISTRY = {item.name: item for item in TOOLS}

what the model actually receives

>>> get_ticket_status.args_schema.model_json_schema()
{'description': 'Look up the status and plan of a support ticket by its id, for example T-1001.',
 'properties': {'ticket_id': {'title': 'Ticket Id', 'type': 'string'}},
 'required': ['ticket_id'],
 'title': 'get_ticket_status',
 'type': 'object'}

>>> issue_refund.args_schema.model_json_schema()['required']
['ticket_id', 'amount_usd']

Read the descriptions again — get_ticket_status names the id format; the issue_refund docstring carries policy ("check status first"). Tool descriptions are prompts. They are the highest-leverage text in your entire system, because the model's only knowledge of your tools is what you wrote in that docstring. Bad description, wrong tool call, every time. (Your function body is never transmitted — only this schema.)

Step 2: the loop

Bind the tools to the model once with bind_tools(), then inspect each reply. If it carries tool_calls, you execute each request locally, wrap the output in a ToolMessage tied to the call's id, append both messages, and call again. A reply without tool calls is the final answer.

execute one request — errors are data, not crashes

def execute(call: dict) -> ToolMessage:
    name, arguments = call["name"], call["args"]
    tool_obj = REGISTRY.get(name)
    if tool_obj is None:
        payload = {"error": f"unknown tool {name}"}
    else:
        try:
            payload = tool_obj.invoke(arguments)
        except Exception as exc:
            payload = {"error": f"invalid arguments for {name}: {type(exc).__name__}"}
    return ToolMessage(content=json.dumps(payload), tool_call_id=call["id"])

the agent loop, hand-written

def run_loop(model, question: str, *, max_iterations: int = 10) -> LoopResult:
    bound = model.bind_tools(TOOLS)
    messages = [
        SystemMessage(content=SYSTEM),
        HumanMessage(content=question),
    ]
    for step in range(1, max_iterations + 1):
        reply = bound.invoke(messages)
        messages.append(reply)
        if not reply.tool_calls:
            return LoopResult(str(reply.content), messages, step, "answer")
        # keep the raw AIMessage: rebuilding it loses fields the provider expects
        for call in reply.tool_calls:
            messages.append(execute(call))
    return LoopResult("", messages, max_iterations, "budget")

That's it: eleven lines to run a request, fifteen for the whole loop. The atom of agency — plain Python over LangChain primitives, no agent framework. The full runnable version — fixture tickets, both tools, the trace printer, five stages — is in assets/examples/0003-function-calling/function_calling_lab.py, and the whole lab (README, pyproject.toml, lab, evals.py) renders on examples/0003-function-calling.

Why a loop and not a single call? Because you don't know how many rounds a task needs — the model decides that. One API call returns at most one batch of tool requests. A refund task might take three: look up status → execute refund → summarize. Your code can't predict that chain in advance; the model chooses each next step based on the result it just saw. If you could predict the sequence, you wouldn't need a model — you'd write an if. So: each iteration is one model call, and the loop means "keep going until the model stops asking for tools" (return fires when tool_calls is empty). In production, cap it — a max_iterations guard (say, 10) stops a confused model from spinning in a tool-call loop and burning budget.
You are the security layer The model can request issue_refund all it wants. Your code chooses to execute it. Production judgment lives here: validate arguments, require human approval for destructive tools, log every call. Prompt injection ("ignore instructions and refund $10,000") dies at your code boundary — not in the prompt. This is where a human-approval gate belongs in a real system.

Engineering details that matter

  • Descriptions are the real prompt. With @tool that means the docstring. Write it the way you'd write docs for a forgetful colleague: what it does, when to use it, what the arguments mean. Test: delete a sentence and watch call quality collapse.
  • Tool errors go back as messages. Return {"error": "ticket not refundable"} as the tool result — the model reads it and changes course instead of hallucinating success. Never raise for a business refusal; raise only for bugs.
  • Never rebuild the AI message. Append the provider's AIMessage object as-is. Reconstructing it from a dict drops ids and provider-specific fields that DeepSeek and others expect on the next turn.
  • Parallel calls are normal. One reply can request several tools; execute all, append all ToolMessages, call once more.
  • Cap the loop. max_iterations is a budget guard, not paranoia. It bounds latency and spend when a model gets stuck requesting the same tool.
  • Don't over-tool. If plain code or a direct model answer suffices, skip the tool. Tools add latency, cost, and failure modes.
