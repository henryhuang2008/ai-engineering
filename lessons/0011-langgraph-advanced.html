LangGraph, Advanced: Fan-Out, Fan-In, and the Join That Fires Early

Lesson 10 ended with one node choosing between two. Real agents do not choose once: they ask three services at the same time, read the answers, and reconcile them. Drawing that is easy. Making the reconciliation wait for the right things — and only the right things — is the advanced part.

Your win this lesson You'll build a multi-source research agent — five nodes by default, nine with the optional Reddit branch: Google and Bing (and Reddit, when enabled) fan out, a structured-output selector picks Reddit threads, comments are fetched, the analyses run in parallel, and one synthesis writes the answer. Then you'll break the join on purpose, watch synthesis run twice with partial data, fix it with one list edge, kill a source, and measure whether "more parallel" actually made the run faster.

Part 1 — The shape

This is the graph the lab builds. The model is DeepSeek; the source layer reads recorded snapshots by default, or calls BrightData with --live. Reddit is optional and off by default (REDDIT_ENABLED=false): a default run is Google + Bing → two analyses → synthesis, five nodes. The diagram and traces below show the full graph with REDDIT_ENABLED=true.

stagenodeswhat makes it a stage
fan-outsearch_google, search_bing, search_reddit (optional)two or three edges leave START; all enabled searches run in the same superstep

fan-out againanalyze_google, analyze_bing, analyze_reddit (optional)edges from the search nodes (and fetch_reddit when enabled)
final joinsynthesizewaits for every enabled analysis, then writes the answer

The state carries one field per source, plus one field that all three analyzers write at the same time. That last field needs a reducer:

def merge_analyses(left: dict[str, str], right: dict[str, str]) -> dict[str, str]:
    return {**left, **right}


class State(TypedDict):
    question: str
    google_results: list[dict]
    bing_results: list[dict]
    reddit_results: list[dict]
    selected_urls: list[str]
    reddit_posts: list[dict]
    analyses: Annotated[dict[str, str], merge_analyses]
    answer: str

Why a reducer here? Three nodes in one superstep all return {"analyses": {"google": ...}}. Without the annotation, LangGraph refuses the concurrent write:

InvalidUpdateError: At key 'analyses': Can receive only one value per step.
Use an Annotated key to handle multiple values.

With it, each analyzer contributes one key and the graph merges them. This is the same reducer idea as lesson 10's add_messages, applied to a dictionary instead of a list — and it is what makes a fan-in possible without three near-identical state fields.

The wiring is short because the topology is in the edges, not in the node bodies:

for source in ("google", "bing", "reddit"):
    graph.add_edge(START, f"search_{source}")

graph.add_edge(
    ["search_google", "search_bing", "search_reddit"], "select_reddit_urls"
)
graph.add_edge("select_reddit_urls", "fetch_reddit")
for source in ("google", "bing", "reddit"):
    graph.add_edge("fetch_reddit", f"analyze_{source}")

graph.add_edge(
    ["analyze_google", "analyze_bing", "analyze_reddit"], "synthesize"
)
graph.add_edge("synthesize", END)

The list argument is not cosmetic. It is the difference between "wait for all three" and "run whenever a predecessor finishes" — Part 3 is entirely about that difference.

The source layer: one interface, two providers

The graph never touches a search API. A provider is an object with four members:

class SourceProvider(Protocol):
    name: str
    def search(self, engine, question, limit=5) -> list[dict]: ...
    def reddit_search(self, question, limit=5) -> list[dict]: ...
    def reddit_threads(self, urls) -> list[dict]: ...
    def check(self) -> None: ...
providerwhere the data comes fromneeds
snapshot (default)data/*.json, ranked by query overlap; deterministicnothing — no key, no network
brightdataSERP request for Google/Bing; Reddit discovery and comments through the datasets APIBRIGHTDATA_API_KEY + a SERP zone

Choose a provider by precedence: --provider NAME, then --live (BrightData shorthand), then SEARCH_PROVIDER in .env, then snapshot.

uv run python agent.py                      # local JSON
uv run python agent.py --live               # BrightData
uv run python agent.py --provider snapshot  # same as the default

Keys go in .env next to the script (copy .env.example):

DEEPSEEK_API_KEY=...
BRIGHTDATA_API_KEY=...
BRIGHTDATA_ZONE=your_zone_name
REDDIT_ENABLED=false

REDDIT_ENABLED controls the third branch: false (default) runs Google + Bing only; true adds the selector, comment fetch and Reddit analysis. --check reports reddit disabled (REDDIT_ENABLED=false) when it is off, and skips the BrightData Reddit trigger entirely.

BrightData needs a SERP / Web Scraper API zone from your account; ai_agent2 is not a default, and leaving it in place gives HTTP 400: zone "ai_agent2" not found. Run uv run python agent.py --zones to list active zones (no active zones means create one) and uv run python agent.py --check to test the key, zone and Reddit trigger without any DeepSeek calls — a 400 prints the API's own message.

Live Reddit calls are asynchronous snapshots — trigger, poll, download — so they are slower; any provider error inside a node becomes an empty source rather than a crashed run (Part 4). The Reddit dataset ids default to BrightData's public ones and can be overridden with BRIGHTDATA_REDDIT_DATASET and BRIGHTDATA_COMMENTS_DATASET.

Adding another provider (Oxylabs, SerpAPI, your own index)

No third adapter is implemented, on purpose: the interface is the extension point. Write a class with those four members, then register it in sources.py:

from oxylabs_provider import OxylabsProvider

PROVIDERS["oxylabs"] = OxylabsProvider

Return {title, url, snippet} from the two search methods and {title, url, comments} from reddit_threads (dropping URLs it does not recognize); make check() raise a clear error when a key is missing. Then --provider oxylabs works, and the graph, prompts and state do not change.

Part 2 — One run, two supersteps

A superstep is the unit of execution: every node whose incoming edges are satisfied runs in that step, and their updates merge at the end. Here is a real run with REDDIT_ENABLED=true:

question: Should a small support team build its agent on LangGraph or a plain tool loop?
graph:    reference (fan-out, fan-in)
source:   snapshot
reddit:   on

[   0.0s] search_bing          5 results
[   0.0s] search_google        5 results
[   0.0s] search_reddit        5 results
[   1.6s] select_reddit_urls   3 urls
[   1.6s] fetch_reddit         3 threads / 9 comments
[   4.1s] analyze_bing         analyses += bing
[   4.4s] analyze_google       analyses += google
[   4.4s] analyze_reddit       analyses += reddit
[   6.6s] synthesize           180 words

sources: google=5 bing=5 reddit=5 | urls=3 | threads=3
graph: bing, google, reddit | nodes=9 | 6.6s

Read the timestamps as superstep boundaries, not node durations. The three searches share the first, so they all report at 0.0 s. The three analyses share the step after the fetch, so they report within 0.2 s of each other. A fast node that shares a step with a slow one appears late — remember that before you attribute latency to the wrong box.

The final line proves the reducer worked: analyses holds bing, google and reddit, merged from three concurrent writes. If one key is missing, that analyzer never ran or was skipped; if it holds a placeholder, the source returned nothing.

Part 3 — The join that fires early

With REDDIT_ENABLED=true, the tempting optimization is this: Google and Bing analyses do not read Reddit, so why wait for Reddit selection and fetching? Move them onto their own edges from their searches (--critical). The graph is cleaner. Then wire the final join the obvious way — separate edges:

for source in ("google", "bing", "reddit"):
    graph.add_edge(f"analyze_{source}", "synthesize")

That is not a barrier when its predecessors start in different supersteps. Real trace, --critical --loose-join:

[   2.4s] analyze_bing         analyses += bing
[   2.7s] analyze_google       analyses += google
[   5.2s] synthesize           179 words     <- fires with two analyses
[   7.6s] analyze_reddit       analyses += reddit
[   9.9s] synthesize           180 words     <- fires again with all three
...
nodes=10 | 9.9s

synthesize ran twice. The first answer was discarded, and the run paid for an extra DeepSeek call. The second run is the one you see, so the output looks fine — the waste is only visible in the trace.

This is not a model quirk. A handful of nodes and a sleep reproduce it with no LLM at all: a fast branch reaches the join, which runs, then the slow branch reaches it and it runs again.

a     sees []
b     sees []
c     sees ['a', 'b']
slow  sees ['a', 'b']
d     sees ['a', 'b', 'c', 'slow']
e     sees ['a', 'b', 'c', 'slow']        <- first fire, d is missing
e     sees ['a', 'b', 'c', 'slow', 'd', 'e']  <- second fire

The fix is one argument: pass the predecessors as a list, which LangGraph treats as an explicit join.

graph.add_edge(
    ["analyze_google", "analyze_bing", "analyze_reddit"], "synthesize"
)

The rule: a fan-in that must see every branch is a list edge, or a dedicated join node with a counter you can assert on. Separate edges do not create a global barrier across supersteps. And the failure is silent: no exception, just an extra call and a wrong intermediate answer.

Part 4 — Failure is a branch too

A fan-out multiplies your exposure: each provider is another chance to time out. The graph should still finish. --fail bing injects an empty result for one source (trace with REDDIT_ENABLED=true):

[   0.0s] search_bing          0 results
[   1.6s] analyze_bing         analyses += bing
...
**Missing/empty sources:** Bing returned no results.
sources: google=5 bing=0 reddit=5 | urls=3 | threads=3 | nodes=9 | 6.3s

Three things make that work. The source node returns [] instead of raising. The analyzer sees an empty payload and writes a placeholder without calling the model. Synthesis is told to name any missing source. The join completes, and the answer is honest about its evidence.

Raising inside a node would fail the run, so every other branch's work would be lost with it. Normalize failure at the boundary — empty data plus a recorded gap — and let the graph decide what an answer with two sources is worth.

Part 5 — More parallel is not automatically faster

With Reddit enabled, the critical-path shape looks faster: Google and Bing analyses finish at ~2.3 s instead of ~3.5 s. But the final answer still waits for the Reddit branch:

[   1.4s] select_reddit_urls   3 urls
[   2.1s] analyze_google       analyses += google
[   2.3s] analyze_bing         analyses += bing
[   2.3s] fetch_reddit         3 threads / 9 comments
[   4.7s] analyze_reddit       analyses += reddit
[   6.7s] synthesize           167 words

In our runs the reference shape took 5.9–6.6 s and the critical-path shape 6.7 s. No speedup — because Reddit was the critical path. Moving Google and Bing earlier cannot shorten a run whose last branch is Reddit selection plus fetch plus Reddit analysis. The restructuring is still correct (those dependencies genuinely do not exist), but the stopwatch is the judge.

situationdoes fan-out help?
independent, I/O-bound branches (three searches, two stores)yes — that is the case it was built for
branches that share a rate limit or a connection poolnot necessarily — you moved the queue, not the work
one slow branch and two fast onesonly if you shorten the slow branch; the join waits for it
cheap local functionsno — the scheduling overhead is the cost
Interview · "How do you make an agent faster?" "I find the critical path first. Fan-out helps when the branches are independent and I/O-bound, but the join waits for the slowest one, so moving fast branches earlier buys nothing. In our research agent, restructuring Google and Bing off the Reddit branch looked right and measured the same — Reddit was still the long pole. The other half is correctness: with separate edges the final synthesis fired twice with partial state, so fan-ins that need every branch use an explicit list edge. I'd rather measure one run than add arrows."
