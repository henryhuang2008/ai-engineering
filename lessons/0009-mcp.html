MCP: Write the Tool Once, Call It From Any Client

You already know function calling: describe a tool, let the model choose it, run it in your process. MCP does not add a new capability — it moves the tool out of your process and gives every client the same address. This lesson builds a server, calls it with no model at all, lets DeepSeek drive it by hand, then points LangChain's MCPAdapter at a one-tool server and lets create_agent run the loop.

Your win this lesson You'll ship an MCP server exposing a tool, a resource and a prompt; call it from a raw client in nine lines; connect the same server to DeepSeek without writing a provider-specific adapter; and point LangChain's MCPAdapter at a one-tool server in one small script.

What MCP is, without the hype

MCP is a standard, not a model feature. It defines how a host (Claude Desktop, an IDE, your Python app) talks to servers that expose capabilities. The client owns the connection; the server owns the data and the code. One client session talks to one server, and a host can hold several sessions.

primitivewho decidesexample in this lab
toolthe modelsearch_kb(query), add(a, b)
resourcethe applicationkb://nimbusdesk/all — the full knowledge base
promptthe useranswer_from_kb(question) — a reusable template

That split matters. A tool is offered to the model and may be called without a human. A resource is addressed by the application, like a file. A prompt is chosen by a person, like a slash command. Most tutorials only show tools; the other two are how a server becomes a product surface instead of a function list.

Three transports, one rule: stdio for local, HTTP for remote.

stdioclient launches the server as a subprocess; stdin/stdout carry the protocollocal tools, editors, this lab

Part 1 — the server

FastMCP turns type hints into the tool's JSON schema and the docstring into its description. There is no registration boilerplate: the decorator is the schema.

from mcp.server.fastmcp import FastMCP

mcp = FastMCP(
    "NimbusDesk",
    host="127.0.0.1",
    port=8050,
    log_level="ERROR",     # stderr stays quiet while the client prints
)

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers together."""
    return a + b

@mcp.tool()
def search_kb(query: str, limit: int = 3) -> str:
    """Search the NimbusDesk knowledge base and return matching entries."""
    ...

if __name__ == "__main__":
    mcp.run(transport="stdio")

Stdout is the protocol. A stray print() in a tool does not print a message — it corrupts the JSON-RPC stream and the client disconnects. Logs go to stderr. That is the single most common way a working server "mysteriously" fails once it is launched by a client instead of by hand.

The same file exposes a resource and a prompt, which cost three lines each:

@mcp.resource("kb://nimbusdesk/all")
def whole_kb() -> str:
    """The entire NimbusDesk knowledge base as JSON."""
    return KB_PATH.read_text(encoding="utf-8")

@mcp.prompt()
def answer_from_kb(question: str) -> str:
    """Template for answering a product question from the knowledge base."""
    return f"Answer using only the knowledge base.\n\nQuestion: {question}"

Inspector, optional. uv run mcp dev server.py opens a browser UI for listing and calling the tools. It needs Node.js and downloads @modelcontextprotocol/inspector through npx on first run, which can take minutes; open the exact URL printed in the terminal, including ?MCP_INSPECTOR_API_TOKEN=… — bare http://127.0.0.1:6274 shows an empty page. mcp dev always wires the Inspector to a stdio server, so its UI has no transport picker; to inspect SSE, start server.py sse and run npx --yes @modelcontextprotocol/inspector --web --transport sse --server-url http://127.0.0.1:8050/sse. The Python clients in this lab do not need it.

Part 2 — the client with no LLM in the loop

Before adding a model, prove the protocol works. The client launches the server, initializes a session, lists capabilities and calls one tool:

No FastMCP import in this file. FastMCP is the server class — the client uses the SDK transport (stdio_client, sse_client or streamablehttp_client) and then a ClientSession. The standalone fastmcp package is a different, higher-level client; this lab keeps the protocol visible instead of hiding it.

params = StdioServerParameters(command=sys.executable, args=[str(SERVER)])

async with stdio_client(params) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()

        tools = await session.list_tools()
        result = await session.call_tool("add", arguments={"a": 2, "b": 3})
        print(result.content[0].text)

Two things are worth noticing. The client did not start a server in another terminal — the subprocess is part of the connection. And search_kb returned the right entry without any embedding model: this server does keyword scoring over eight Q&A pairs, which is enough to demonstrate the protocol before lesson 7's retrieval stack gets involved.

The same server, two HTTP doors

Stdio is one transport, not the protocol. The server already accepts a transport argument, and the client changes only the connection helper:

# terminal 1 - pick one
uv run python server.py sse
uv run python server.py streamable-http

# terminal 2
uv run python client-sse.py               # http://127.0.0.1:8050/sse
uv run python client-streamable-http.py   # http://127.0.0.1:8050/mcp

Terminal 1 confirms the bind before it waits — FastMCP runs on uvicorn, but the lab's log_level="ERROR" hides uvicorn's banner, so the server prints its own line:

serving over sse at http://127.0.0.1:8050/sse
press Ctrl+C to stop
from mcp.client.sse import sse_client
from mcp.client.streamable_http import streamablehttp_client

async with sse_client("http://127.0.0.1:8050/sse") as (read, write):
    ...

async with streamablehttp_client("http://127.0.0.1:8050/mcp") as (read, write, _):
    ...   # the third value is a session-id getter

Both print the same tools and the same 2 + 3 = 5; only the connected to … line differs. Keep SSE for servers that still speak it, and use Streamable HTTP for anything new. Both bind 127.0.0.1:8050, so stop one server before starting the other.

A 502 from 127.0.0.1 usually means a system proxy is intercepting loopback, or something else owns the port. The clients add localhost to NO_PROXY before connecting, so the proxy case is handled; a ConnectError instead means the server simply is not running.

Part 3 — DeepSeek drives the tools by hand

This is where the protocol pays off. MCP already publishes a JSON schema for every tool (inputSchema), which is the exact shape a chat model expects for function calling. The bridge is a list comprehension, not an adapter library:

def as_function_tools(tools):
    return [
        {
            "type": "function",
            "function": {
                "name": tool.name,
                "description": tool.description,
                "parameters": tool.inputSchema,
            },
        }
        for tool in tools
    ]

model_with_tools = model.bind_tools(as_function_tools(listed.tools))

Then it is the lesson-3 loop with one substitution: instead of calling a Python function, the client calls session.call_tool and returns the text as a ToolMessage.

reply = await model_with_tools.ainvoke(messages)
messages.append(reply)

for call in reply.tool_calls:
    result = await session.call_tool(call["name"], arguments=call["args"])
    messages.append(
        ToolMessage(content=text_of(result), tool_call_id=call["id"])
    )

Live output, temperature=0:

tools: add, search_kb
question: What does E-311 mean?
  tool search_kb({"query": "E-311 error code"})
  -> Q: What does error E-311 mean?
answer: E-311 means the mailbox storage quota was exceeded. To fix it, archive
conversations or raise the seat storage limit.

The model chose the tool and the query, but it never saw the knowledge base file and cannot call anything the server did not publish. That boundary — not the model — is the security surface. Ask something outside the corpus ("What is the SLA for the mobile app?") and it says it does not know, because the only evidence it received was an irrelevant entry.

Part 4 — LangChain calls MCP with MCPAdapter

LangChain ships an MCP adapter of its own: langchain.mcp.MCPAdapter. It launches a server, lists its tools, and converts them for create_agent. The example is a separate small uv project in langchain-agent/ because the adapter currently requires MCP v2, while the server above pins the v1 SDK.

server.py — one tool:

from fastmcp import FastMCP

mcp = FastMCP("Calc")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers together."""
    return a + b

if __name__ == "__main__":
    mcp.run(transport="stdio", show_banner=False)

agent.py — the whole client:

async with MCPAdapter(SERVER) as adapter:
    tools = await adapter.list_tools()
    agent = create_agent(build_model(), tools)
    result = await agent.ainvoke({"messages": [HumanMessage(question)]})

Run it:

cd assets\examples\0009-mcp\langchain-agent
uv sync
$env:DEEPSEEK_API_KEY = "sk-..."
uv run python agent.py "What is 2 + 3?"

Real output:

tools: add
question: What is 2 + 3?
  1 human  -> What is 2 + 3?
  2 ai     -> add({"a": 2, "b": 3})
  3 tool   -> 5
  4 ai     -> 2 + 3 = **5**
answer: 2 + 3 = **5**

Four messages. list_tools() did the schema conversion; create_agent compiled the model → tools → model loop; ainvoke() ran it. There is no for loop and no session.call_tool in agent.py.

SSE instead of stdio

Stdio is only the default target. The server accepts a transport argument, and the agent accepts a URL with --url. FastMCP infers SSE from the /sse suffix; other HTTP URLs use Streamable HTTP.

# terminal 1
uv run python server.py sse

# terminal 2
uv run python agent.py --url http://127.0.0.1:8050/sse "What is 2 + 3?"

Use server.py http and http://127.0.0.1:8050/mcp for Streamable HTTP. Both bind 127.0.0.1:8050, so stop one server before starting the other. The tools, the four messages and the answer are identical — only the target passed to MCPAdapter changes.

The langchain.mcp namespace is beta and prints a LangChainBetaWarning on import. That is why this example is a separate project: you can try the new adapter without moving the lesson's v1 server and clients. The guide is docs.langchain.com/oss/python/langchain/mcp.

MCP vs plain function calling

The honest comparison: at small scale, MCP is more machinery for the same result. It wins when the tool needs to exist outside one process.

plain function callingMCP
tool livesin your processin a server process
reusecopy the codepoint another client at the server
language boundarysame runtimeany MCP client
latencya direct calla protocol round trip
setupone decoratorserver + client + transport

Use MCP when the tool is shared across apps, remote, written by another team, or when you want the ecosystem's existing servers. Keep plain @tool for one app with three local functions — the ceremony is not free.

Lifecycle: initialize, operate, terminate

The context managers are the lifecycle, and initialize() is not optional — it negotiates the protocol version before any request:

async with stdio_client(params) as (read, write):     # connect
    async with ClientSession(read, write) as session:
        await session.initialize()                     # negotiate
        ...                                            # list / call
# session closed, subprocess terminated

For resources that should live as long as the server — a database pool, a loaded embedding model — FastMCP's lifespan opens them once at startup and closes them at shutdown, instead of reconnecting per tool call. Tools receive the lifespan context through Context.

The default you must not ship

This server binds HTTP transports to 127.0.0.1 and has no authentication. That is correct for a local lab and wrong for anything reachable. A remote MCP server needs TLS, explicit trusted hosts and origins, and an auth layer — publishing a port is not a security model. Stdio is different but not safer by default: the server inherits the client's permissions, so only launch servers you trust.
