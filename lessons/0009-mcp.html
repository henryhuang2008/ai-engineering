MCP: Write the Tool Once, Call It From Any Client

You already know function calling: describe a tool, let the model choose it, run it in your process. MCP does not add a new capability — it moves the tool out of your process and gives every client the same address. This lesson builds a server, calls it with no model at all, lets DeepSeek drive it by hand, points LangChain's MCPAdapter at a one-tool server, and then assembles all of it into a CRM agent with three servers, a Postgres database and a human approval gate.

Your win this lesson You'll ship an MCP server exposing a tool, a resource and a prompt; call it from a raw client in nine lines; connect the same server to DeepSeek without writing a provider-specific adapter; point LangChain's MCPAdapter at a one-tool server in one small script; and read a working agent whose entire tool layer is a JSON file and whose writes stop for approval.

What MCP is, without the hype

MCP is a standard, not a model feature. It defines how a host (Claude Desktop, an IDE, your Python app) talks to servers that expose capabilities. The client owns the connection; the server owns the data and the code. One client session talks to one server, and a host can hold several sessions.

primitivewho decidesexample in this lab
toolthe modelsearch_kb(query), add(a, b)
resourcethe applicationkb://nimbusdesk/all — the full knowledge base
promptthe useranswer_from_kb(question) — a reusable template

That split matters. A tool is offered to the model and may be called without a human. A resource is addressed by the application, like a file. A prompt is chosen by a person, like a slash command. Most tutorials only show tools; the other two are how a server becomes a product surface instead of a function list.

Three transports, one rule: stdio for local, HTTP for remote.

stdioclient launches the server as a subprocess; stdin/stdout carry the protocollocal tools, editors, this lab
SSEHTTP POST up, Server-Sent Events downolder HTTP servers; compatibility
Streamable HTTPone /mcp endpoint, bidirectional streamingnew remote integrations

Part 1 — the server

FastMCP turns type hints into the tool's JSON schema and the docstring into its description. There is no registration boilerplate: the decorator is the schema.

from mcp.server.fastmcp import FastMCP

mcp = FastMCP(
    "NimbusDesk",
    host="127.0.0.1",
    port=8050,
    log_level="ERROR",     # stderr stays quiet while the client prints
)

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers together."""
    return a + b

@mcp.tool()
def search_kb(query: str, limit: int = 3) -> str:
    """Search the NimbusDesk knowledge base and return matching entries."""
    ...

if __name__ == "__main__":
    mcp.run(transport="stdio")

Stdout is the protocol. A stray print() in a tool does not print a message — it corrupts the JSON-RPC stream and the client disconnects. Logs go to stderr. That is the single most common way a working server "mysteriously" fails once it is launched by a client instead of by hand.

The same file exposes a resource and a prompt, which cost three lines each:

@mcp.resource("kb://nimbusdesk/all")
def whole_kb() -> str:
    """The entire NimbusDesk knowledge base as JSON."""
    return KB_PATH.read_text(encoding="utf-8")

@mcp.prompt()
def answer_from_kb(question: str) -> str:
    """Template for answering a product question from the knowledge base."""
    return f"Answer using only the knowledge base.\n\nQuestion: {question}"

Inspector, optional. uv run mcp dev server.py opens a browser UI for listing and calling the tools. It needs Node.js and downloads @modelcontextprotocol/inspector through npx on first run, which can take minutes; open the exact URL printed in the terminal, including ?MCP_INSPECTOR_API_TOKEN=… — bare http://127.0.0.1:6274 shows an empty page. mcp dev always wires the Inspector to a stdio server, so its UI has no transport picker; to inspect SSE, start server.py sse and run npx --yes @modelcontextprotocol/inspector --web --transport sse --server-url http://127.0.0.1:8050/sse. The Python clients in this lab do not need it.

Part 2 — the client with no LLM in the loop

Before adding a model, prove the protocol works. The client launches the server, initializes a session, lists capabilities and calls one tool:

No FastMCP import in this file. FastMCP is the server class — the client uses the SDK transport (stdio_client, sse_client or streamablehttp_client) and then a ClientSession. The standalone fastmcp package is a different, higher-level client; this lab keeps the protocol visible instead of hiding it.

params = StdioServerParameters(command=sys.executable, args=[str(SERVER)])

async with stdio_client(params) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()

        tools = await session.list_tools()
        result = await session.call_tool("add", arguments={"a": 2, "b": 3})
        print(result.content[0].text)

The same server, two HTTP doors

Stdio is one transport, not the protocol. The server already accepts a transport argument, and the client changes only the connection helper:

# terminal 1 - pick one
uv run python server.py sse
uv run python server.py streamable-http

# terminal 2
uv run python client-sse.py               # http://127.0.0.1:8050/sse
uv run python client-streamable-http.py   # http://127.0.0.1:8050/mcp

Terminal 1 confirms the bind before it waits — FastMCP runs on uvicorn, but the lab's log_level="ERROR" hides uvicorn's banner, so the server prints its own line:

serving over sse at http://127.0.0.1:8050/sse
press Ctrl+C to stop
from mcp.client.sse import sse_client
from mcp.client.streamable_http import streamablehttp_client

async with sse_client("http://127.0.0.1:8050/sse") as (read, write):
    ...

async with streamablehttp_client("http://127.0.0.1:8050/mcp") as (read, write, _):
    ...   # the third value is a session-id getter

Both print the same tools and the same 2 + 3 = 5; only the connected to … line differs. Keep SSE for servers that still speak it, and use Streamable HTTP for anything new. Both bind 127.0.0.1:8050, so stop one server before starting the other.

A 502 from 127.0.0.1 usually means a system proxy is intercepting loopback, or something else owns the port. The clients add localhost to NO_PROXY before connecting, so the proxy case is handled; a ConnectError instead means the server simply is not running.

Part 3 — DeepSeek drives the tools by hand

This is where the protocol pays off. MCP already publishes a JSON schema for every tool (inputSchema), which is the exact shape a chat model expects for function calling. The bridge is a list comprehension, not an adapter library:

def as_function_tools(tools):
    return [
        {
            "type": "function",
            "function": {
                "name": tool.name,
                "description": tool.description,
                "parameters": tool.inputSchema,
            },
        }
        for tool in tools
    ]

model_with_tools = model.bind_tools(as_function_tools(listed.tools))

Then it is the lesson-3 loop with one substitution: instead of calling a Python function, the client calls session.call_tool and returns the text as a ToolMessage.

reply = await model_with_tools.ainvoke(messages)
messages.append(reply)

for call in reply.tool_calls:
    result = await session.call_tool(call["name"], arguments=call["args"])
    messages.append(
        ToolMessage(content=text_of(result), tool_call_id=call["id"])
    )

Live output, temperature=0:

tools: add, search_kb
question: What does E-311 mean?
  tool search_kb({"query": "E-311 error code"})
  -> Q: What does error E-311 mean?
answer: E-311 means the mailbox storage quota was exceeded. To fix it, archive
conversations or raise the seat storage limit.

The model chose the tool and the query, but it never saw the knowledge base file and cannot call anything the server did not publish. That boundary — not the model — is the security surface. Ask something outside the corpus ("What is the SLA for the mobile app?") and it says it does not know, because the only evidence it received was an irrelevant entry.

Part 4 — LangChain calls MCP with MCPAdapter

LangChain ships an MCP adapter of its own: langchain.mcp.MCPAdapter. It launches a server, lists its tools, and converts them for create_agent. The example is a separate small uv project in langchain-agent/ because the adapter currently requires MCP v2, while the server above pins the v1 SDK.

server.py — one tool:

from fastmcp import FastMCP

mcp = FastMCP("Calc")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers together."""
    return a + b

if __name__ == "__main__":
    mcp.run(transport="stdio", show_banner=False)

agent.py — the whole client:

async with MCPAdapter(SERVER) as adapter:
    tools = await adapter.list_tools()
    agent = create_agent(build_model(), tools)
    result = await agent.ainvoke({"messages": [HumanMessage(question)]})

Run it:

cd assets\examples\0009-mcp\langchain-agent
uv sync
$env:DEEPSEEK_API_KEY = "sk-..."
uv run python agent.py "What is 2 + 3?"

Real output:

question: What is 2 + 3?
  1 human  -> What is 2 + 3?
  2 ai     -> add({"a": 2, "b": 3})
  3 tool   -> 5

Four messages. list_tools() did the schema conversion; create_agent compiled the model → tools → model loop; ainvoke() ran it. There is no for loop and no session.call_tool in agent.py.

SSE instead of stdio

Stdio is only the default target. The server accepts a transport argument, and the agent accepts a URL with --url. FastMCP infers SSE from the /sse suffix; other HTTP URLs use Streamable HTTP.

# terminal 1
uv run python server.py sse

# terminal 2
uv run python agent.py --url http://127.0.0.1:8050/sse "What is 2 + 3?"

Use server.py http and http://127.0.0.1:8050/mcp for Streamable HTTP. Both bind 127.0.0.1:8050, so stop one server before starting the other. The tools, the four messages and the answer are identical — only the target passed to MCPAdapter changes.

The langchain.mcp namespace is beta and prints a LangChainBetaWarning on import. That is why this example is a separate project: you can try the new adapter without moving the lesson's v1 server and clients. The guide is docs.langchain.com/oss/python/langchain/mcp.

Part 5 — A working agent: three servers, one config file

Parts 1–4 isolate one mechanism each: a server, a raw client, a model loop, an adapter. 5.1 — The graph: LangGraph, and one provider-specific line

The state is three fields, and one of them is a policy:

class AgentState(BaseModel):
    messages: Annotated[List[BaseMessage], add_messages] = []
    protected_tools: List[str] = ["create_campaign", "send_campaign_email"]
    yolo_mode: bool = False

messages is the only field with a reducer (add_messages appends and de-duplicates by id). protected_tools is the list the router consults, and yolo_mode is the switch that turns the whole gate off. Putting policy in state rather than in a prompt is the important part: a prompt can be talked out of a rule, an if cannot.

The graph is the Part 4 loop, opened up:

client = MultiServerMCPClient(connections=mcp_config["mcpServers"])
tools = await client.get_tools()

llm = ChatOpenAI(
    model="gpt-4.1-mini-2025-04-14",
    temperature=0.1
).bind_tools(tools)

builder = StateGraph(AgentState)
builder.add_node(assistant_node)
builder.add_node(human_tool_review_node)
builder.add_node("tools", ToolNode(tools))

builder.add_edge(START, "assistant_node")
builder.add_conditional_edges("assistant_node", assistant_router,
                              ["tools", "human_tool_review_node", END])
builder.add_edge("tools", "assistant_node")

return builder.compile(checkpointer=MemorySaver())

Three nodes, and one conditional edge with three exits. ToolNode(tools) is the prebuilt executor that saves you the for call in reply.tool_calls loop from Part 3; assistant_router is the only decision:

def assistant_router(state: AgentState) -> str:
    last_message = state.messages[-1]
    if not last_message.tool_calls:
        return END
    if not state.yolo_mode and any(
        call["name"] in state.protected_tools
        for call in last_message.tool_calls
    ):
        return "human_tool_review_node"
    return "tools"

OpenAI is two lines, not an architecture. The import and the constructor above are the only place a provider is named; every tool arrives as a schema and every message is a LangChain object. Swapping in the model the rest of this course uses is an import plus a constructor:

from langchain_deepseek import ChatDeepSeek

llm = ChatDeepSeek(
    model="deepseek-flash",
    temperature=0.1,
    extra_body={"thinking": {"type": "disabled"}},
).bind_tools(tools)

If that swap does not work, the problem is in the tool schemas or the model's tool-calling, seldom in the graph. That is what bind_tools abstracts, and it is why Part 3 could build the same loop by hand.

5.2 — Human in the loop: interrupt, not a polite prompt

The system prompt says “Before sending any email, you must always first analyze the customer's data…”. That sentence is advice. The gate is a node:

def human_tool_review_node(state: AgentState) -> Command[Literal["assistant_node", "tools"]]:
    last_message = state.messages[-1]
    tool_call = last_message.tool_calls[-1]

    human_review: dict = interrupt({
        "message": "Your input is required for the following tool:",
        "tool_call": tool_call
    })

    review_action = human_review["action"]
    review_data = human_review.get("data")

    if review_action == "continue":
        return Command(goto="tools")

    elif review_action == "update":
        updated_message = AIMessage(
            content=last_message.content,
            tool_calls=[{
                "id": tool_call["id"],
                "name": tool_call["name"],
                "args": json.loads(review_data)
            }],
            id=last_message.id
        )
        return Command(goto="tools", update={"messages": [updated_message]})

    elif review_action == "feedback":
        tool_message = ToolMessage(
            content=review_data,
            name=tool_call["name"],
            tool_call_id=tool_call["id"]
        )
        return Command(goto="assistant_node", update={"messages": [tool_message]})

interrupt() does not block a thread. It raises: the node stops, the checkpointer saves the run, and the caller gets control back with the payload above. Nothing executes until someone resumes that same thread_id with Command(resume=…). This is why the graph is compiled with MemorySaver() — a graph without a checkpointer cannot be paused, so interrupt has nowhere to keep the state.

Three actions, three different futures:

actionnode returnswhat happens
continueCommand(goto="tools")the call runs exactly as the model wrote it
updatea rewritten AIMessage, then goto="tools"the call runs with your arguments instead, same call id
feedbacka ToolMessage holding your text, then goto="assistant_node"the tool never runs; the model re-plans with your note as its “result”

The feedback branch is the one worth understanding. The model's last message is an AIMessage that claims a tool call with an id. Chat APIs reject a conversation where that id has no matching tool result. Re-sending a rejection as a plain human message breaks the transcript; sending it as the ToolMessage for that id keeps it valid and tells the model what a human thought. That is a protocol constraint shaping product behaviour.

The client side is a loop over the paused state — no callbacks, no threads:

thread_state = graph.get_state(config=config)

while thread_state.interrupts:
    pending = thread_state.interrupts[0]
    print(json.dumps(pending.value, indent=2, ensure_ascii=False))

    action = input("Action (continue, update, feedback): ")
    data = None if action == "continue" else input("Data: ")

    async for response in stream_graph_responses(
        Command(resume={"action": action, "data": data}), graph, config=config
    ):
        print(response, end="", flush=True)

    thread_state = graph.get_state(config=config)

Four limits, so you do not over-trust the gate:

  • It reviews one call — always the last. The node reads last_message.tool_calls[-1]. If the model emits two calls and the protected one is not last, you approve an unprotected call while the protected one runs unreviewed.
  • It trusts the caller. yolo_mode=True in the input state skips every check. In chat_local.py it is set once at startup — one boolean between a gated agent and an autonomous one.
  • It is not an audit log. The resumed value is used and discarded; the checkpoint keeps messages, not who approved what or when. Compliance needs a separate record.
  • It reviews arguments, not consequences. You see {"campaign_id": …, "customer_id": …, "subject": …}, not how many rows it will touch or what the HTML looks like rendered.

5.3 — Supabase behind two servers

The database is the UCI Online Retail II sample, reshaped into six tables: customers (100 rows), items (2,132), transactions (8,683), rfm (100), plus marketing_campaigns and campaign_emails for the agent's own writes.

The read side is a borrowed server. @modelcontextprotocol/server-postgres exposes exactly one tool, query(sql), and it opens BEGIN TRANSACTION READ ONLY before running your statement. That single line is the safety model: the agent can read anything the connection can see and change nothing. It has no row cap, no statement timeout and no keyword whitelist — the guard from Lesson 21 is still missing, and it matters more here, because this connection can read every customer's email address.

The write side is yours. marketing_server.py is 96 lines: a SQLAlchemy engine from SUPABASE_URI, FastMCP("marketing"), and two tools. create_campaign inserts a row and returns its UUID; send_campaign_email inserts a row into campaign_emails and returns a confirmation string. There is a # TODO: Send email via MCP where the actual delivery goes. Read that before a demo: in this build “sent” means a row exists.

Two schema traps are worth meeting in a lab rather than in production:

  • Quoted identifiers. Columns are "Customer ID", "InvoiceDate", "StockCode" — mixed case, preserved by the quotes. Unquoted, Postgres folds them to lowercase and the query fails with column "customer id" does not exist. The system prompt repeats the schema so the model quotes them too, which is why the prompt carries SQL.
  • RLS is not your control here. The migration runs ALTER TABLE … ENABLE ROW LEVEL SECURITY on all six tables and creates no policies. The connection string is the table owner, and an owner is not constrained by its own RLS policies — so the “read-only” boundary is the transaction in the Postgres server, not the database.

5.4 — mcp_config.json is the server registry

Three servers, one file, no Python:

{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "${SUPABASE_URI}"],
      "transport": "stdio"
    },
    "marketing": {
      "command": "python",
      "args": ["src/ralph/my_mcp/servers/marketing_server.py"],
      "transport": "stdio"
    },
    "slack": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-slack"],
      "env": {
        "SLACK_BOT_TOKEN": "${SLACK_BOT_TOKEN}",
        "SLACK_TEAM_ID": "${SLACK_TEAM_ID}"
      },
      "transport": "stdio"
    }
  }
}

The key name mcpServers and the command/args/env/transport shape are the same ones Claude Desktop and most MCP hosts already read. That portability is the point: this registry can be handed to another client unchanged.

detailwhy it is written that way
${SUPABASE_URI} in argsthe connection string, password included, stays in .env, not in a JSON file you might commit
relative .py pathreadable in the file; resolved to an absolute path before launch, because the child process does not share this working directory
"command": "python"inherits PATH. Correct under uv run, wrong if you launch the chat with a Python that lacks mcp
slack with no valuesthe server is dropped at load time, so an optional integration costs nothing when unconfigured

config.py is the loader, and it does three jobs in order: resolve every ${VAR} from the environment, turn relative .py arguments into absolute paths (it finds the project root by walking up to pyproject.toml), and delete any server whose variables are missing:

env_var_value = os.environ.get(env_var_name, None)
if env_var_value is None or env_var_value == "":
    print(f"\nEnvironment variable {env_var_name} is not set\n")
    print(f"Skipping server {server_name}\n")
    skipped_servers.append(server_name)
    continue

# ...and after the loop
for server_name in set(skipped_servers):
    del config["mcpServers"][server_name]

Measured on the lab machine: with SUPABASE_URI set and no Slack variables, importing the module prints two warnings and returns a two-server config — postgres with the DSN substituted into args, marketing with an absolute path, and no slack key at all. The agent starts with what it has instead of failing on what it does not.

Then one line connects them all:

client = MultiServerMCPClient(connections=mcp_config["mcpServers"])
tools = await client.get_tools()

get_tools() returns one flat list, so the model never learns which server a tool came from — query and create_campaign sit in the same namespace, and ToolNode routes each call back to its own subprocess. Two costs to keep in mind: names must not collide (add two Postgres servers and you have two query tools), and startup spawns one child process per configured server — three when Slack is wired — one of which may download a package the first time through npx -y. The DSN also appears in that child process's command line, visible to other local processes — a reason to use a read-only role rather than the owner.

5.6 — What to take from the build

The registry is the lesson. Adding a server is a config edit plus an entry in protected_tools if it can write; removing one is deleting a key. The graph does not change, the prompt does not change, and the approval gate keeps working because it decides by tool name, not by which server the name came from.

The gate is also the honest limit of this example. It shows you where a human belongs; it does not yet show you what a reviewer decided, how much a call may change, or what happens when the model asks for two writes in one turn. Those are the three things to add before anyone points this at a real customer list.

A second build of the same gate puts the decision behind HTTP: assets/examples/human-in-the-loop runs this graph on DeepSeek with one local filesystem server and exposes the terminal loop as two requests — POST /chat sends a message and returns either an answer or the pause, POST /chat/{thread_id}/resume answers it with continue, update (new JSON arguments), feedback, reject or exit. Read it after this section: the router is unchanged, and the loop is the one chat_local.py already runs in your terminal.

MCP vs plain function calling

The honest comparison: at small scale, MCP is more machinery for the same result. It wins when the tool needs to exist outside one process.

plain function callingMCP
tool livesin your processin a server process
reusecopy the codepoint another client at the server
language boundarysame runtimeany MCP client
latencya direct calla protocol round trip
setupone decoratorserver + client + transport

Use MCP when the tool is shared across apps, remote, written by another team, or when you want the ecosystem's existing servers. Keep plain @tool for one app with three local functions — the ceremony is not free.

Lifecycle: initialize, operate, terminate

The context managers are the lifecycle, and initialize() is not optional — it negotiates the protocol version before any request:

async with stdio_client(params) as (read, write):     # connect
    async with ClientSession(read, write) as session:
        await session.initialize()                     # negotiate
        ...                                            # list / call
# session closed, subprocess terminated

For resources that should live as long as the server — a database pool, a loaded embedding model — FastMCP's lifespan opens them once at startup and closes them at shutdown, instead of reconnecting per tool call. Tools receive the lifespan context through Context.

The default you must not ship

This server binds HTTP transports to 127.0.0.1 and has no authentication. That is correct for a local lab and wrong for anything reachable. A remote MCP server needs TLS, explicit trusted hosts and origins, and an auth layer — publishing a port is not a security model. Stdio is different but not safer by default: the server inherits the client's permissions, so only launch servers you trust.
