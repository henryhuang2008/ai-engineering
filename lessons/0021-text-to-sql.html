Text to SQL — The Model Proposes, the Guard Decides

In a text-to-SQL system the model does not answer the question. It writes a query, the database answers, and a second model call turns the rows into a sentence. That changes where the risk lives: not in the wording of the answer, but in the query you are about to run. This lesson builds the agent, then spends most of its time on the guard, the retry loop, and the one question a good agent must refuse.

Your win this lesson You can run a text-to-SQL agent end to end, explain every layer that stands between the model and the database, read the SQL behind an answer, and decide when the correct output is “the schema cannot answer that”.

Part 1 — What text-to-SQL is good for

The job is narrow and valuable: a person asks a question in English, the answer already exists in a relational database, and writing the SQL is the bottleneck. Counts, filters, joins, group-bys, rankings and time comparisons are the sweet spot.

works well fails, or needs a human
“How many orders were completed?” “What is the refund rate?” — no refunds table or status exists
“Which customer placed the most orders?” “Which customers are about to churn?” — no definition, no label
“Revenue by category last quarter” “Is this customer profitable?” — cost data lives elsewhere
“Show the ten largest orders” “Show me everything” — no row-level permission model

The distinction is not “simple versus complex SQL”. It is whether the question's terms exist in the schema. A model can write a beautiful WHERE status = 'refunded' even when no such status exists, and the query returns zero rows without an error. That is the failure mode this lesson keeps returning to: a wrong answer that looks exactly like a right one.

Two model calls make the system:

  1. Write the query. The model sees the schema and the question, and calls a run_query tool. If the schema cannot answer, it must say so instead of guessing.
  2. Write the answer. After the rows come back, a second call turns them into one or two sentences, using only values that appear in the result.

Splitting the calls is not ceremony. The first call is where correctness is decided, so it gets a strict contract and a guard. The second call is where presentation is decided, so it gets the rows and nothing else. Mixing them lets the model narrate a query it never ran.

Part 2 — The example and its data

The lab is assets/examples/0021-text-to-sql. It builds a SQLite file from four CSV files, so the data is local and every answer is reproducible: 

customers   8 rows   customer_id, name, region, signup_date
products    6 rows   product_id, name, category, unit_price
orders     12 rows   order_id, customer_id, ordered_at, status
order_items 19 rows  order_id, product_id, quantity, unit_price

Four tables are enough for joins and aggregates, and small enough that you can check every number by hand. The statuses are completed, cancelled and pending; dates are ISO text. Two facts drive most of the demo:

question correct answer what it tests
How many orders were completed? 10 a filter on one table
Total revenue from completed orders? 3111.0 a join plus SUM(quantity * unit_price)
Average order value? 311.1 dividing by COUNT(DISTINCT order_id), not by rows
Which customer ordered most? Ava Chen, 3 group, count, order, tie-break
Top product by revenue? 27-inch Monitor, 987.0 join through order_items
Customers in the West? 3 a filter the model usually gets right

Build it once, then look at exactly what the model is allowed to see:

cd assets/examples/0021-text-to-sql
uv sync
Copy-Item .env.example .env        # macOS/Linux: cp

uv run python main.py build
uv run python main.py schema

schema prints the DDL plus row counts — no sample rows. Withholding the rows matters: a model that has seen three orders can pattern-match an answer instead of writing a query. The guard is the other reason the corpus is small; a wrong join is visible in a nineteen-row table and invisible in a million-row one.

Part 3 — The graph

The reference tutorial builds a ReAct-style loop with tools and dedicated nodes. This example keeps the loop but makes every step a node, so the retry limit and the approval point are visible in the graph: 

START → load_schema → generate → (SQL? review : END)
             ↑                        │
             │                        ▼
          execute ←─────────────── review
             │
   (error, attempts left) → generate
   (ok)                    → answer → END
   (attempts exhausted)    → fail   → END
node reads writes
load_schema the database file schema, the system prompt, the question
generate messages the reply, sql, tool_call_id, attempts
review sql, attempts approved, possibly an edited sql
execute sql result or error, a tool or user message
answer question, sql, result the final assistant message
fail error, attempts a plain-language failure message

The state is the whole contract. Every key a node writes is declared here, because LangGraph drops undeclared keys without an error — a mistake that makes a node look like it works while changing nothing: 

class SqlState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    question: str
    schema: str
    sql: str | None
    tool_call_id: str | None
    result: str | None
    error: str | None
    attempts: int
    approved: bool

The routing is two conditional edges. After generate, a reply with SQL goes to review; a reply without SQL is the model's final answer and ends the run. After execute, success goes to answer, a failure with attempts left goes back to generate, and the last allowed failure goes to fail: 

builder.add_conditional_edges(
    "generate", route_after_generate, {"review": "review", "end": END}
)
builder.add_conditional_edges(
    "execute",
    route_after_execute,
    {"answer": "answer", "generate": "generate", "fail": "fail"},
)

The retry prompt is deliberately blunt. On failure, execute appends the SQLite error and the attempt number to the message list, so the next generate call sees what went wrong: 

That query failed: OperationalError: no such column: nope
Rewrite it. Attempt 1 of 3.

Three attempts is a policy, not a law. The point is that the loop is bounded: the tutorial's graph can cycle forever between run_query and generate_query, and a model that keeps producing the same broken join will do exactly that.

Part 4 — The prompt is a contract

The SQL prompt is short because it is specific. It names the dialect, the allowed statement shape, the date format, the status values, and the definition of revenue. It also names the escape hatch: 

Call the run_query tool exactly once with the query.
Do not explain the SQL in the same turn.
If the schema cannot answer the question, do not guess. Reply with exactly:
  INSUFFICIENT_SCHEMA: <the table or column that is missing>

A sentinel is a small piece of prompt engineering that buys a large correctness win. Without it, the model has two options: guess, or answer in prose that the graph cannot distinguish from a real result. With it, “I cannot answer” is a parseable outcome, and the graph can end without running anything.

Live, against DeepSeek deepseek-chat:

uv run python main.py ask "What is the refund rate?" --show

INSUFFICIENT_SCHEMA: refunds table (no refund/refunded column or table exists)

That is the correct output. The database has no refund concept, so any number would be invented. A weaker run returns WHERE status = 'refunded' and zero rows; the guard cannot catch that, because the SQL is valid. Only the sentinel, the visible SQL, and a human reading it can.

The tool contract is the other half. The model is bound to a run_query(query: str) tool, so the usual reply is a structured call with a query argument. The example also accepts a ```sql fence, because providers differ; both forms go through the same guard. What it never accepts is prose that merely looks like SQL.

The answer prompt is separate and smaller: question, SQL, formatted rows, and an instruction to use only values in the result. It is a summarizer, not an analyst. If the row set is empty, it must say so rather than fill the gap.

Part 5 — The guard is the security boundary

The tutorial says it plainly: its database tools are “minimal wrappers for demonstration purposes only… not intended to be secure”. A sqlite3.connect with write access, executing model_output, is the whole risk in one line. This example adds six layers, and each one stops something different:

layer what it stops what it does not stop
file:…?mode=ro any write, at the filesystem level reads you did not intend
PRAGMA query_only = ON writes that slip past the text check the same
one statement, SELECT/WITH only stacked statements, DDL, ATTACH a valid but wrong SELECT
forbidden-keyword scan INSERT, DELETE, DROP, PRAGMA obfuscated keywords
outer LIMIT 50 unbounded result sets a slow aggregate with one row
progress handler, 2 s runaway joins and recursive CTEs a query that is slow on purpose but under the cap

Read the first row carefully. The read-only URI is the layer that does not depend on parsing: even if the model writes a statement the guard misclassifies, SQLite refuses the write. The text checks exist for clarity and early errors, not as the last line of defense. 

uri = f"file:{path.as_posix()}?mode=ro"
connection = sqlite3.connect(uri, uri=True)
connection.execute("PRAGMA query_only = ON")

connection.set_progress_handler(stop_when_late, 1_000)
cursor = connection.execute(f"SELECT * FROM (\n{sql}\n) LIMIT {max_rows + 1}")

The outer limit is applied by the runner, not requested in the prompt. That distinction is the lesson: a prompt instruction is a request, and a wrapper is an enforcement. The model is told not to add a LIMIT; the runner caps the result whether the model complied or not. The extra row is how the code knows the result was truncated.

The progress handler runs every thousand SQLite virtual-machine instructions and returns non-zero once the deadline has passed, which aborts the query. Without it, one recursive CTE or one accidental cartesian join can hold the process until it is killed.

Still not a sandbox A read-only connection still sees every row in the file. If users must see different rows, that is a permissions problem: use views, a per-tenant database, or a server that enforces row-level security. No amount of prompt text substitutes for a grant.

Part 6 — Human review, when a query is about to run

The guard handles structure. It cannot know that SUM(quantity * unit_price) is the wrong revenue definition for your business, or that a query touches a sensitive table. That is what review is for, and LangGraph makes it a first-class pause: 

def review_node(state: SqlState) -> dict:
    if not review:
        return {"approved": True}
    decision = interrupt({
        "question": state["question"],
        "sql": state["sql"],
        "attempt": state["attempts"],
    })
    ...

interrupt stops the graph and stores its state. The process can exit; nothing is lost. A later call resumes with Command(resume=…), and interrupt returns whatever payload was passed. That is why review needs a checkpointer, and why the example compiles the graph with InMemorySaver even when review is off: 

state = graph.invoke({"question": question, "attempts": 0}, config)
while "__interrupt__" in state:
    payload = state["__interrupt__"][0].value
    decision = ask_the_human(payload)
    state = graph.invoke(Command(resume=decision), config)

The CLI offers three answers. Approve runs the query as written. Edit replaces the SQL and then runs it. Reject skips execution and takes the failure path, so the model's next turn sees that a human said no: 

uv run python main.py ask "How many customers are in the West region?" --review --show

proposed SQL (attempt 1):
SELECT COUNT(*) AS customer_count FROM customers WHERE region = 'West'

[a]pprove · [e]dit · [r]eject > a
There are 3 customers in the West region.

The reference tutorial wraps the query tool in another tool and interrupts inside it. Both designs pause before execution; the differences are where the pause lives and what the resume payload looks like. The tutorial's second graph also replaces the model-based check_query node with human review, which is a useful way to see the trade: a checker costs another model call and catches more mistakes mechanically; a reviewer costs attention and catches meaning.

One detail from the tutorial is worth keeping even if you skip the checker. Its check_query node rewrites the query and assigns the original message id, so add_messages replaces the tool call instead of appending a second one: 

response.id = state["messages"][-1].id

Without that line, the graph carries two queries for one question, and the next tool node runs the stale one.

Part 7 — What breaks

symptom cause fix
a confident answer with a wrong number the query ran; nobody checked what it computed always show SQL and rows; add an evaluation set
revenue is roughly double joining orders to order_items and another table fans out rows aggregate at the right grain; pre-aggregate or use DISTINCT deliberately
“0” reported as “none” the filter names a status or category that does not exist refuse when the term is absent; show the rows so zero is visible
the model writes DELETE the prompt was treated as a permission system read-only URI, query_only, statement whitelist
a request never returns cartesian join or recursive CTE with no bound progress handler and a deadline
the agent loops on the same error no attempt cap counter plus a fail node
every question costs 40k prompt tokens the whole schema is pasted into every call table selection: list tables, then fetch only the relevant DDL

The last row is where the reference tutorial's list_tables → get_schema step earns its place. Four tables fit in one prompt; four hundred do not. The example loads the whole schema because the corpus is tiny, and the lesson says so instead of pretending the shortcut scales.

Part 8 — What was verified

  • Live model: DeepSeek deepseek-chat answered five questions. Four ran on the first attempt; the refund question returned INSUFFICIENT_SCHEMA and executed nothing.
  • Numbers cross-checked: 10 completed orders, revenue 3111.0, AOV 311.1, top product 27-inch Monitor at 987.0, top category Accessories at 1110.0, three West customers.
  • Review: a live run paused on the proposed SELECT COUNT(*) … WHERE region = 'West', accepted a, and resumed to “There are 3 customers in the West region.”
  • Offline: 29 tests pass with no network, no key and no database server. They cover the guard, the caps, the retry loop and all three review decisions.
  • Not verified: SQL correctness at scale (no evaluation set), the tutorial's check_query node, PostgreSQL, and the guard as a sandbox. Those are documented as gaps in the example's agent notes.
