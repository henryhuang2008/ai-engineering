Memory in agents — short-term and long-term, rebuilt

A runnable implementation of the article's architecture: a checkpointer for thread-scoped short-term memory, a namespace store for cross-thread long-term memory, trimming and summarization, and one combined agent. The structure is the article's. The code paths that do not run as written are corrected, and every correction is listed below.

The one-line model STM is the thread. LTM is the user. A checkpointer stores everything that happened in one conversation; a store keeps facts that survive the conversation. Mixing the two scopes is how agents forget the right things and remember the wrong ones.

The two memories

Short-term Long-term
scope one thread_id one user_id, across threads
mechanism InMemorySaver / PostgresSaver InMemoryStore / PostgresStore
holds messages and state keys facts extracted from turns
bounded by trimming and summarization namespace and recall limit
survives restart only with Postgres only with Postgres

What is in the tree

path role

app/ltm.py namespace store, fact extraction, dedupe, recall, forget

app/postgres.py PostgresSaver + PostgresStore over one pool
app/cli.py demo · facts · chat · forget
tests/ 19 tests, no network, no database
docs/article-notes.md section-by-section notes and exact deviations

Run it

cp .env.example .env      # set OPENAI_API_KEY
uv sync

uv run python main.py demo        # STM: two threads, separate state
uv run python main.py facts       # LTM: same user, new thread
uv run python main.py chat        # both, interactive
uv run pytest -q

demo needs no database. facts and chat use in-memory stores unless you pass --postgres (before the subcommand) with DATABASE_URL set to the pgvector container in docker/.

What changed from the article

article here why
MessagesState includes user_input only messages Current LangGraph defines just the message list; extra keys need a subclass.
Nodes return {"context": ...} memory_context is declared Undeclared keys are silently dropped, so the retrieval node has no effect.
store.search(query=...) on a plain store query passed only when an index exists Without embeddings the query is ignored and score is None.
delete helper uses msgs[-keep_count:] delete_messages(ids) The original deletes the newest messages and references an undefined msg.
[summary] + recent appended to messages summary in its own state key add_messages keeps existing ids, so the append duplicates the recent window.
two nodes re-read the store one retrieve node, compile(store=...) Duplication hides which node owns retrieval.
random UUID per fact hash of normalized text Re-extracting the same fact should overwrite, not duplicate.

What the tests prove

  • two threads keep separate histories, and a returning thread reloads its own;
  • trimming keeps the recent window and starts on a human message;
  • summarization removes old messages instead of appending duplicates;
  • fact extraction survives a non-JSON reply and caps count and length;
  • storing the same fact twice writes one row;
  • facts do not cross user namespaces;
  • memory_context is declared state, not a dropped key;
  • search(query=...) without an index returns score=None.

Known limits

  • The PostgreSQL path needs Docker and pgvector; no daemon was available here, so it remains a documented gate.
  • Verified live against DeepSeek deepseek-chat and Qwen text-embedding-v4: thread isolation, fact extraction, cross-thread recall and ranked search with real scores. One run, not a benchmark.
  • No eval for "is this fact worth remembering", no TTL, no conflict resolution between contradictory facts.
  • DeepSeek does not serve embeddings; semantic recall needs a second provider (Qwen here).

The companion lesson is Lesson 19 — Memory That Survives the Conversation. For the graph mechanics underneath, read Lesson 10; for the retrieval contract, Lesson 7.

Before you store a fact: decide its namespace, its key, its expiry, and how it gets deleted. A memory without a delete path is a privacy incident waiting for a support ticket.
