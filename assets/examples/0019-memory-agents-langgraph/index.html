Memory in agents — run it

Four commands, in order. demo shows short-term memory across two conversations. facts shows long-term memory across two conversations for one user. chat runs both together. The last step is the test suite.

The one-line model Short-term memory is the thread. Long-term memory is the user. The checkpointer follows one thread_id; the store follows one user_id across every thread.

Setup

cd assets/examples/0019-memory-agents-langgraph
uv sync

# Windows PowerShell
Copy-Item .env.example .env

# macOS / Linux
cp .env.example .env

Set OPENAI_API_KEY in .env. DeepSeek is the default endpoint. Everything else can stay empty; the database and the embedding provider are optional.

The workflow

Step 1 — short-term memory across two threads

uv run python main.py demo
=== thread-1 (Alice) ===
you> Hi! My name is Alice
bot> Hi Alice! It's nice to meet you...
you> What's my name?
bot> Your name is Alice!
you> Remind me my name
bot> Your name is Alice.

=== thread-2 (Bob) ===
you> Hi! My name is Bob
bot> Hi Bob! It's nice to meet you...
you> What's my name?
bot> Your name is Bob!

thread-1 messages stored: 6
thread-2 messages stored: 4

Thread 2 never sees thread 1's messages. Inside thread 1, the third turn still knows the name from the first. That is the whole test: same graph, two thread_id values, two separate histories.

Step 2 — long-term memory across two threads

uv run python main.py facts
=== thread A: introduce yourself ===
bot> ...
stored facts: ['Works as a data scientist',
               'Uses Python for data science work',
               'Works with machine learning']

=== thread B: a new conversation, same user ===
bot> ... (advice that uses the facts)
facts after turn: [...]

Thread B starts with no messages, yet the answer reflects the job and the stack. The facts live under user-alice, not under either thread.

Step 3 — both memories, interactive

uv run python main.py chat

Enter a user id and a thread id, then talk. Use exit to stop; the facts for that user are printed at the end. Start a second session with the same user id and a new thread id to watch the facts carry over.

Step 4 — the tests

uv run pytest -q
19 passed

No network, no database, no key. They use a scripted model.

One turn, step by step

Every turn in facts and chat runs this graph:

START → compress → retrieve → agent → extract → END
node reads writes
compress the message list, over the token threshold a summary key plus removals for old messages
retrieve user_id and the newest human message memory_context — the facts, one per line
agent system prompt, facts, summary, trimmed messages the assistant reply
extract the newest human message and the thread_id new facts in the user's namespace

The checkpointer saves the full thread after each step. The model sees only the trimmed window plus the summary. Those are deliberately different sizes: storage is cheap, prompt tokens are not.

Save both memories in PostgreSQL

Both in-memory classes die when the process exits. The PostgreSQL versions keep the same API; only construction changes. 

docker compose -f docker/docker-compose.yml up -d
psql "postgresql://postgres:postgres@localhost:5432/agent_memory" \
  -c "CREATE EXTENSION IF NOT EXISTS vector;"

Then set DATABASE_URL in .env:

DATABASE_URL=postgresql://postgres:postgres@localhost:5432/agent_memory

And run a command with the flag before the subcommand:

uv run python main.py --postgres facts
uv run python main.py --postgres chat
uv run python main.py --postgres forget user-alice

What the code does, in five lines:

pool = ConnectionPool(conninfo=DATABASE_URL, kwargs={"autocommit": True})

checkpointer = PostgresSaver(conn=pool)
checkpointer.setup()              # once: checkpoint tables

store = PostgresStore(conn=pool)  # add index={...} for semantic recall
store.setup()                     # once: store tables

graph = builder.compile(checkpointer=checkpointer, store=store)

One pool serves both objects. setup() creates tables on the first run and is safe to leave in the startup path. The checkpointer writes checkpoints, checkpoint_blobs and checkpoint_writes keyed by thread_id. The store writes store (and store_vectors when an index is configured) keyed by the namespace prefix and the fact key.

Restart test: run --postgres facts twice. The second run reloads the thread from the previous process, so the first answer already knows the earlier conversation. That is what the in-memory version cannot do.

Not verified here This machine has no Docker daemon, so the PostgreSQL path is documented from the library source and the project's code, not measured. The --postgres flag is the gate: if the tables and the restart test pass on your machine, that is the evidence.

What the tests prove

  • two threads keep separate histories, and a returning thread reloads its own;
  • trimming keeps the recent window and starts on a human message;
  • summarization removes old messages instead of appending duplicates;
  • fact extraction survives a non-JSON reply and caps count and length;
  • storing the same fact twice writes one row, and facts do not cross user namespaces;
  • search(query=...) without an index returns score=None.

Known limits

  • PostgreSQL was not run here; it is a documented gate, not a measured claim.
  • Verified live against DeepSeek deepseek-chat and Qwen text-embedding-v4 (1536 dims): thread isolation, fact extraction, cross-thread recall, ranked search. One run, not a benchmark.
  • No eval for "is this fact worth remembering", no TTL, no conflict resolution.
  • DeepSeek does not serve embeddings; semantic recall needs a second provider.
