Human in the Loop — one pause, three ways to answer it

A LangGraph graph drafts an answer, stops before the next node, and waits for a person. This example puts that pause behind FastAPI three times: a blocking request, a server-sent-event stream, and an MCP tool call that stops inside interrupt(). DeepSeek is the model, uv is the install, and a React shell is included.

The one-line model The graph ends; it does not sleep. The pause lives in the checkpointer under a thread_id. Resuming is a second request with the same id, whether that is one second later or after a restart.

Four requests that tell the whole story

1. Start a draft. The graph runs assistant_draft, stops before human_feedback, and returns:

POST /graph/start   {"human_request": "Explain what HITL means in one sentence."}

{"thread_id": "d0e1...", "run_status": "user_feedback",
 "assistant_response": "Human-in-the-loop means people oversee an automated
   system at key points to improve accuracy, safety and accountability."}

The pause is graph.get_state(config).next containing human_feedback. Nothing is running while you read this.

2. Send a revision. Write the reviewer's decision into the state, then continue with None:

POST /graph/resume
{"thread_id": "...", "review_action": "feedback",
 "human_comment": "Make it one short sentence."}

The router reads status and sends the graph back to assistant_draft, which revises with the comment. Same pause again.

3. Approve. review_action: "approved" routes to assistant_finalize, which polishes the approved draft once and ends the run with run_status: "finished".

4. The MCP version. Here the pause is inside the tool, not between nodes: 

POST /mcp/start    {"human_request": "Call get_my_account and report my login."}

{"run_status": "user_feedback",
 "assistant_response": "I want to call the tool 'get_my_account' with arguments: {}"}

POST /mcp/approve  {"thread_id": "...", "approve_action": "approved"}

{"run_status": "finished",
 "assistant_response": "Your GitHub login is octocat ..."}

approved re-enters the tool with Command(resume={"approved": True}) and the MCP call runs. rejected returns a sentence instead, so the model continues without the side effect.

Two kinds of pause

interrupt_before=[...]interrupt({...})
Wherebetween nodes, fixed at compile timeinside a node or tool, decided at run time
What the caller seesstate.next names the node that did not runthe payload passed to interrupt()
How to resumeupdate_state, then invoke(None, config)invoke(Command(resume=value), config)
Used inlesson 1 and lesson 2 (human_feedback)lesson 3 (every MCP tool)

Limits worth naming

This is a lab, not a control plane The checkpointer is MemorySaver: a restart loses every paused thread, so a real deployment wants PostgresSaver. The resume endpoints do not authenticate anyone — the thread_id is the only capability. And lesson 3's shipped MCP config starts GitHub's server in Docker, so /mcp/* needs Docker Desktop plus GITHUB_PERSONAL_ACCESS_TOKEN; lessons 1 and 2 do not.

The React shell is upstream's and still installs with npm; Python is the part this lab teaches.

Before you call it approval: decide who may resume a thread, how long a pause may live, and what happens when the same approval arrives twice. The graph handles the pause; the rest is your API.
