Rag with Supabase — the capstone repository

An internal analyst product for a fictional research firm: ask questions across SEC 10-K filings in plain English, get answers whose factual claims cite retrieved passages, and open the passage in one click. This is a working implementation through Phase 7, not a finished production service. The pilot and deployment phases have not started, and four verification gates are still open.

Provider note: the backend depends on the openai package, but it is used as an OpenAI-compatible transport. DeepSeek is the chat model and Qwen is the embedding model. The package name is a transport detail; backend/app/config.py and backend/pyproject.toml are the source of truth for what actually runs.

Run it

# backend
cd backend
uv sync
uv run alembic upgrade head
uv run uvicorn app.main:app --reload

# fast tests: no network, no database, no provider keys
uv run pytest -q -m "not integration"

# frontend
cd frontend
pnpm install
pnpm dev

Required settings live in backend/.env; the checked-in .env.example lists the names. Startup fails explicitly when required values are missing. Ingestion commands and their cost caps are in data/README.md; the chunk job is a dry run unless --pilot or --all is passed with an approved cap.

What "grounded" means here

  1. The model may call only search_filings, read_chunk and read_surrounding_chunks.
  2. Output is a list of typed claims, each carrying one or more retrieved chunk IDs.
  3. The validator rejects unknown IDs, missing citations, malformed output and inexact quotes.
  4. Insufficient evidence returns a fixed refusal with no citations.
  5. The validated answer is persisted atomically before any text delta is streamed.

This is referential validation, not a proof of semantic entailment. Client-brief evaluation and human review remain necessary, and the project says so in docs/architecture.md.

Read in this order

  1. AGENTS.md — what the coding agent may and may not do.
  2. docs/client-brief.md — the problem, the trust contract and the acceptance questions.
  3. docs/todo.md — the build order and the honest status of each phase.
  4. docs/architecture.md — service boundaries, schema, retrieval, streaming.
  5. backend/AGENTS.md and frontend/AGENTS.md — local conventions.
  6. backend/app/grounding/validator.py and backend/app/retrieval/fusion.py — the two contracts that make trust testable.
Before you extend it: pick one open gate from docs/todo.md, write its acceptance check, and run the fast suite first. Adding features before closing a verification gate is how a capstone turns back into a demo.
