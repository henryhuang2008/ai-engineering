Text to SQL — run it

A question in English becomes a SQLite query, a result, and an answer. The graph is LangChain's custom SQL agent, with three additions the tutorial leaves as an exercise: a read-only guard, a retry limit, and a human approval interrupt.

The one-line model The model proposes. The guard decides. The graph retries. No model output reaches the database without passing the same checks, and every answer carries the SQL that produced it.

Setup

cd assets/examples/0021-text-to-sql
uv sync

# Windows PowerShell
Copy-Item .env.example .env

# macOS / Linux
cp .env.example .env

Set OPENAI_API_KEY in .env. DeepSeek is the default endpoint; any OpenAI-compatible chat model with tool calling works. The database is local, so nothing else is required.

The workflow

Step 1 — build the database

uv run python main.py build
built ...\data\northstar.db
  customers: 8 rows
  products: 6 rows
  orders: 12 rows
  order_items: 19 rows

Four CSV files become one SQLite file. The data is small on purpose: every expected number fits on a slide, so a wrong query is visible instead of plausible.

Step 2 — see what the model sees

uv run python main.py schema
-- customers (8 rows)
CREATE TABLE customers (
    customer_id INTEGER PRIMARY KEY,
    name        TEXT NOT NULL,
    region      TEXT NOT NULL,
    signup_date TEXT NOT NULL
);
...

The schema text is the whole context for the SQL step: the DDL, the row counts, and nothing else. There are no sample rows in the prompt, so the model cannot memorize an answer from the data.

Step 3 — ask one question

uv run python main.py ask "How many orders were completed?"
10 orders were completed.

Step 4 — ask again, with the SQL

uv run python main.py ask "How many orders were completed?" --show
10 orders were completed.

SQL (1 attempt(s)):
SELECT COUNT(*) AS completed_orders FROM orders WHERE status = 'completed'

Result:
completed_orders
1. 10

--show is the habit worth keeping. An answer is a claim; the SQL and rows are the evidence. Without them you cannot tell a correct count from a query that returned zero rows and a confident sentence.

Step 5 — review before executing

uv run python main.py ask "How many customers are in the West region?" --review --show

proposed SQL (attempt 1):
SELECT COUNT(*) AS customer_count FROM customers WHERE region = 'West'

[a]pprove · [e]dit · [r]eject > a
There are 3 customers in the West region.

--review pauses the graph on interrupt before the query runs. a approves, e edits the statement, r rejects it and the graph takes the failure path. The pause needs a checkpointer; the example always supplies one.

Step 6 — four questions end to end

uv run python main.py demo --show
=== 1. How many orders were completed?
10 orders were completed.

=== 2. What is total revenue from completed orders?
The total revenue from completed orders is 3111.0.

=== 3. Which customer placed the most orders, and how many did they place?
Ava Chen placed the most orders, with 3 orders.

=== 4. What is the refund rate?
INSUFFICIENT_SCHEMA: refunds table (no refund/refunded column or table exists)

The fourth question is the one to study. There is no refunds table and no refunded status, so the correct answer is a refusal. A model that writes WHERE status = 'refunded' gets zero rows and still sounds certain; the sentinel is how this example tells the two apart.

The block above is abridged: --show prints each SQL statement and its rows between the answers. The full run is in the README.

Step 7 — the tests

uv run pytest -q
29 passed

No network, no key, no database server. The graph tests use a scripted model, so the retry and interrupt paths run deterministically.

The graph, node by node

START → load_schema → generate → (SQL? review : END)
             ↑                        │
             │                        ▼
          execute ←─────────────── review
             │
   (error, attempts left) → generate
   (ok)                    → answer → END
   (attempts exhausted)    → fail   → END
node reads writes
load_schema the database file schema, the system prompt, the question
generate messages the reply, sql, tool_call_id, attempts
review sql, attempts approved, possibly an edited sql
execute sql result or error, a tool or user message
answer question, sql, result the final assistant message
fail error, attempts a plain-language failure message

execute is a node rather than a ToolNode because it owns three things a tool call should not: the read-only guard, the attempt counter, and the approval result. The run_query tool is still bound to the model — it is the contract that makes the model emit {"query": "…"} instead of prose — but SQL only runs in execute.

On a failed attempt the node appends the SQLite error and a human message that names the attempt number. The next generate call sees that message, which is the whole retry mechanism: 

That query failed: OperationalError: no such column: nope
Rewrite it. Attempt 1 of 3.

The guard

The reference tutorial says its tools are "not intended to be secure". This example makes the missing layers explicit; they run in this order.

layer what it stops
file:…?mode=ro any write, even if the SQL gets past the text checks
PRAGMA query_only = ON the same, at the connection level
one statement, SELECT/WITH only stacked statements, DDL, ATTACH
forbidden-keyword scan INSERT, UPDATE, DELETE, DROP, PRAGMA, …
outer LIMIT 50 unbounded result sets and SELECT *
set_progress_handler, 2 s runaway recursive CTEs and cartesian joins

The outer limit is applied by the runner, not requested in the prompt, so a model that ignores the instruction is still capped. The cap is a memory and latency bound, not a correctness guarantee: an aggregate query has one row and can still be wrong.

What the tests prove

  • the CSVs rebuild the same 8 / 6 / 12 / 19 rows, twice in a row;
  • the read-only connection rejects a DELETE at the database level;
  • stacked statements, writes and PRAGMA are rejected before execution;
  • a cartesian join is cut at 50 rows and marked truncated;
  • a recursive CTE is interrupted by the 2-second deadline;
  • one good query produces an answer with one attempt;
  • a bad column is retried with the SQLite error in the prompt;
  • three bad queries end in the failure message, not an endless loop;
  • INSUFFICIENT_SCHEMA ends the run without executing SQL;
  • interrupt pauses before execution, and approve, edit and reject all take the right path.

Known limits

  • No evaluation set. Five hand-checked questions is a demo, not a benchmark.
  • No check_query node. The tutorial asks a second model to proofread the SQL; this example relies on the guard and the retry loop. A query that runs but answers the wrong question is not caught.
  • SQLite only. The tutorial's Chinook file and a PostgreSQL variant are described in the notes, not run here.
  • The guard is not a sandbox. A read-only connection still sees every row in the file, and a slow query burns CPU until the deadline fires.
  • Model behavior varies. DeepSeek answered four questions on the first attempt; another provider may need the retry path more often. That is what the attempts counter is for.

Before you connect a real database: decide what the agent can read, what it can never write, how many rows it may return, and how long a query may run. The prompt is not a permission system.
