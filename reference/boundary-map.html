The Boundary Map

"Boundary" is this course's recurring insight — taught in pieces across the twenty lessons, never as one picture. This is the picture: where every boundary sits in an agent, what crosses it, the single rule each enforces, and the lesson to revisit. The claim it compresses: error handling, security, and safety are the same discipline at different lines — label what crosses, classify what fails, cap what loops, gate what's irreversible.

The agent, drawn as boundaries

untrusted text ↓ (label)                 failures ↓ (classify)
side effects   → (gate)                   budgets   → (cap)

  ┌─ intake ───┐   ┌── context ──┐         ┌─ output ──┐
  │ user msg   │──▶│  assembly   │◀──▶MODEL│ grounding │──▶ reply
  └────────────┘   └──┬───────┬──┘         └───────────┘
                      │       │
        ┌─ retrieval ─┘       └─ tool / MCP ─┐        ┌─ loop ────┐
        │ scope (server-side, narrow-only)   │◀──────▶│ step+dup  │
        └────────────────────────────────────┘  loop  │ budget    │
                                                     └───────────┘
                 ┌─ persistence ─┐      ┌─ human ──┐
                 │ DB = truth    │      │ approve  │──▶ world
                 │ window = view │      │ gate     │   (money, mail, data)
                 └───────────────┘      └──────────┘

Three flow types cross these lines, and each gets exactly one treatment: untrusted text crosses downward and must be labeled; failures cross upward and must be structured; side effects cross outward and must be gated or keyed. If you can say which of the three a crossing is, you know its rule.

The three questions (ask at every new boundary)

  1. What crosses this line? Name it as one of the three flow types — untrusted text, failure, or side effect. (If nothing crosses, it isn't a boundary; don't add machinery.)
  2. What's its treatment? text → label · failure → classify + structure · side effect → gate or idempotency key · loop → cap. One treatment per flow; none of them is "try/except everywhere."
  3. What proves it holds? Every row above has a test: malformed input that must be rejected (L13), a dead source that must degrade instead of raise (L11), a feed failure that must not deactivate the source (L18), a failed SMTP send that must record failed rather than sent (L18), a second thread that must not see another thread's history (L19), a repeated fact that must not duplicate (L19), a skill whose name disagrees with its directory that must fail the lint (L20), a file read before its skill is loaded that must be refused (L20), a citation outside the retrieved set that must fail closed (L7, L17), a re-index that must not change a chunk's provenance (L6). A boundary without an eval is a comment.

The two counting heuristics: count your try/excepts — ideally one per boundary row, zero per business function (an exception is a crash with extra steps; pure functions should fail loudly in tests). And count your receipts — every crossing that failed or was gated leaves a log line or a trace step (L7, L11): boundaries are also where your eval cases come from.

Not sure where a new feature sits? Draw its arrows first — what text enters, what fails, what leaves the system — and the boundary (and its lesson) picks itself.
